## 2. Что криво (по убыванию важности)

### 🔴 Критично

**1. `get_for_teacher_date` / `get_for_teacher_range` грузят всю таблицу.**
`infrastructure/database/repo/college_lesson.py`:
```python
return [l for l in await self.get_all_lessons() if l.date == date and ...]
```
Вызывается на **каждый тик bell-лупа** (каждые 30 сек) и на каждую рассылку.
С ростом базы это станет узким местом. Нужен SQL-фильтр по `teacher`.

**2. Нет миграций.** `Base.metadata.create_all` создаёт таблицы, но **не добавляет
колонки**. В октябре это чинили руками через `docker exec ... ALTER TABLE`.
Следующее изменение схемы = простой. Нужен alembic.

**3. Данные привязаны к дате, а не к неделе.** Модель `CollegeLesson(date, ...)`
не поддерживает чётную/нечётную неделю и замены. Это блокирует фичу старост
(см. `docs/EDITORS.md`).

**4. Секреты светились в логах.** Токен бота, Coolify-токен, admin-id фигурировали
в выводе команд. **Не ротированы.** Стоит ротировать.

### 🟠 Средне

**5. `_failed` (кулдаун битых ссылок) — в памяти.** Сбрасывается при рестарте
контейнера, а контейнер пересоздаётся при каждом деплое.

**6. Bell-луп может «проспать» событие.** Тик раз в 30 сек, сравнение `t != now_min`.
Если бот занят рассылкой на границе минуты — звонок не отправится никогда.
Нет окна «дослать просроченное в течение N минут».

**7. Обед преподавателя привязан к первой совпавшей группе 2-й пары.** Если
преподаватель ведёт группы разного курса — обед может быть неверный.

**8. `format_day` дублирует логику «пустого дня».** Внутри зашито `«Занятий нет 🙌»`,
хотя есть отдельные `format_no_lessons` / `format_not_published` / `format_site_down`.

**9. `any_text` перехватывает любой текст** и рисует меню. Не баг, но затирает
недопонимание: юзер ждёт ответа — получает меню.

**10. Дублирование курсовой логики.** `course_group_from_group` и
`course_group_from_course` почти копии; `_cg` в `bell.py` дублирует выбор.

### 🟡 Мелко

**11. Мёртвый код:** `has_source()` (после перехода на хэш), `bulk_upsert` частично.
**12. `upsert` в `BellScheduleRepo`** пишет `h1_end = h2_start` — правит только
«пару без перемены»; UI правки перемен/обеда нет.
**13. `_weekday_kb`** — хардкод сетки по одному элементу в строке; зип-дубли в `cb_photo_list`.
**14. `admin.py` — 943 строки.** Монолит, стоит разнести по модулям.
**15. Тестов почти нет** — 1 файл, 4 функции (только `course_group`). Парсер и
форматтеры не покрыты.

## 4. Ограничения, которые надо помнить

- **Сайт может лежать неделями.** Архитектура обязана работать без него.
- **Замены дают на 1–2 дня вперёд.** Файл перезаписывается, архива на сайте нет —
  историю хранит бот.
- **Чётность недели** — ✅ разобрана: верхняя строка ячейки = чётная,
  нижняя = нечётная. Чётность колледжа инвертирована к ISO (`offset=1`).
- **Данные 2–8.10** — это «временный» режим, они остаются архивом.
- `source=manual` обязателен, чтобы не потерять ручные правки при возврате сайта.

## 5. Как работать с миграциями

Схема БД ведётся через alembic — руками `ALTER TABLE` больше не нужно.

```bash
# применить всё до последней версии (обычно не требуется: бот делает это при старте)
alembic upgrade head

# откатить одну миграцию
alembic downgrade -1

# посмотреть текущую версию
alembic current

# создать новую миграцию после правки моделей
alembic revision --autogenerate -m "что изменилось"
```

**Важно:** бот применяет миграции сам при запуске
(`infrastructure/database/migrations_runner.py`). Если БД создана **до** внедрения
alembic, раннер не станет пересоздавать таблицы — он пометит её как
`0001_baseline` и применит только новые миграции. Проверено на боевой БД:
215 пользователей и 567 пар сохранились.

Проверить версию схемы на сервере:

```bash
ssh virprom-home 'sqlite3 /home/virprom/schedule-pipeline/data/database.db "select * from alembic_version;"'
# → 0002_editors
```

### Что где лежит

| Файл | Назначение |

| `migrations/versions/0001_baseline.py` | Схема «как было» до alembic (реальная, из продовой БД) |
