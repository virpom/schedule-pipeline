# Архитектура

Как устроен бот: откуда берутся данные, где они живут и кто их читает.

## Поток данных

```

┌─────────────────────────────────────────┐

│  · Листок замен.docx                    │
```

## Почему три слоя, а не один

Можно было бы держать одно расписание «на дату». Но тогда каждое утро нужно
было бы пересобирать 37 групп × 14 дней из ничего, а отличить «пару убрали»
от «пары не было» стало бы невозможно.

Слои решают три разные задачи:

| Слой | Отвечает на вопрос | Меняется |
|---|---|---|
| `base_lesson` | «что стоит по плану в этот день недели» | раз в семестр |
| `substitution` | «что изменилось именно в эту дату» | ежедневно |
| `college_lesson` | «что видит студент прямо сейчас» | каждый проход |

`college_lesson` — кэш, а не источник истины. Его можно пересобрать из двух
верхних слоёв в любой момент, что и делает `materialize()`. Сделан он потому,
что почти весь код бота читает одну таблицу по дате; переписывать два десятка
мест ради «правильной» архитектуры было бы дороже, чем один раз материализовать.

## Чётность недели

Ключевая деталь, на которой легко ошибиться.

В файле расписания колледжа ячейка содержит две строки — «нечётная неделя» и
«чётная». Вопрос: какая ISO-неделя считается нечётной?

Проверено на данных: **чётность колледжа = ISO-неделя со сдвигом на 1**.
То есть ISO-неделя 43 — это чётная неделя колледжа. Зашито в
`PARITY_OFFSET = 1` в `tgbot/services/schedule_layer.py`.

Если расписание «съедет» на неделю — почти наверняка дело в этом сдвиге.
Проверяется сравнением выдачи бота с файлом на сайте.

## Ручные правки старосты

Староста правит `base_lesson` / `substitution` с `source='manual'`.

`materialize()` при перезаписи дня сначала читает строки с
`source != 'site'`, кладёт их в результат и запоминает пары
`(группа, пара)`. Сгенерированные с сайта слоты на этих позициях
пропускаются. Так правка старосты переживает синхронизацию.

## Фоновые задачи

`main.py` поднимает две задачи через `asyncio.create_task`:

| Задача | Что делает | Период |
|---|---|---|
| `poller_loop` | опрос сайта, материализация, рассылка | `poll_interval` (300 с) |
| `bell_loop` | напоминания о звонках | 30 с |

Обе живут в одном процессе с ботом — отдельного воркера нет.

`poller_loop` внутри каждого прохода проверяет:

1. Ночная пауза (`night_start`…`night_end`) — если сейчас ночь, опрос пропускается.
2. Снапшот прошедших дней — раз в час, чтобы архив не терялся, если сайт
   обновит файл задним числом.
3. `poll_once` — если прошло больше `poll_interval` секунд.

Остановка: по сигналу задачи отменяются (`cancel`), затем
`asyncio.gather(..., return_exceptions=True)`, затем `bot.session.close()` и
`engine.dispose()`. Без этого aiogram ругался на незакрытую сессию, а SQLite
мог оставить незакрытый файл.

## Состояние источника

Отдельный модуль `tgbot/services/source_state.py` отвечает на вопрос
«насколько свежие у нас данные».

Хранится один факт — `last_sync_ok`, время последней **полностью успешной**
синхронизации. Из него выводится `is_stale()`: прошло больше 30 минут —
значит замены проверить не удалось.

Почему не флаг «сайт лежит»: флаг врёт при частичном сбое (упали замены,
но не очное) и ничего не говорит о свежести. Время — честнее.

Что показывается пользователю:

| Ситуация | Ответ |
|---|---|
| Пары есть, сайт жив | расписание |
| Пары есть, сайт лёг | расписание + предупреждение строкой |
| Пар нет, день опубликован | «Занятий нет» |
| Пар нет, не опубликован, сайт жив | «Ещё не выложено» |
| Пар нет, связи нет | «Занятий нет по постоянному расписанию» + предупреждение |

Последняя строка — важная: там, где бот **не знает**, он не утверждает,
что пар нет.

## Частичный сбой

`sync_once` обновляет каждый файл независимо, через внутренний `_step`.
Если листок замен вернул 404, звонки всё равно обновятся, а проход будет
помечен как неполный (`failed`), и успех не запишется.

Исключение — падение на скачивании самой страницы-каталога: тогда не
скачивается ничего, и это честный «сайт недоступен».

## Схема БД

15 таблиц. Главные:

| Таблица | Что хранит |
|---|---|
| `users` | роль, группа, курс, подписка, настройки уведомлений |
| `base_lesson` | базовое расписание по чётности; `weeks` — недели списком для вуза |
| `substitution` | замены на конкретную дату |
| `college_lesson` | материализованное расписание на 14 дней |
| `bell_schedule` | звонки: тип дня × поток × пара |
| `bell_lunch` | обед по курсу |
| `bell_reminder` | когда кому напомнить о звонке |
| `schedule_editor` | кому выданы права старосты |
| `schedule_edit` | журнал правок |
| `no_lessons` | заметки «занятий нет» от старосты |
| `day_snapshot` | архив прошедших дней |
| `schedule_file` | хеш файла по дате (признак «день опубликован») |
| `chats` | групповые чаты, привязанные к группе |
| `vuz_group` | группы вуза: факультет, курс, форма обучения |
| `setting` | настройки в БД: интервал, ночная пауза, дедлайн… |

Схема накатывается alembic при старте (`infrastructure/database/migrations_runner.py`).

### Два подразделения в одной схеме

Колледж и вуз живут в одних таблицах. Разделяет их **суффикс `@vuz`** в
ключе группы: `ЭК-23` — колледж, `ЭК-23@vuz` — вуз. Это разные люди с
одинаковым названием группы, и без суффикса они бы склеились.

Суффикс не виден студенту: `strip_unit()` снимает его при показе.
`is_vuz()` отвечает, к какому подразделению относится группа,
`course_group_from_group()` отдаёт для вуза отдельный поток звонков
(`VUZ`, 8 пар вместо 5).

Разделение сделано суффиксом, а не отдельными таблицами, чтобы не
переписывать 87 мест, которые читают `.group`.
Миграции: `0001_baseline`, `0002_editors`.

## Слои кода

```
common/schedule.py       форматирование, константы, чётность — без БД и сети
parsers/eios.py          разбор xlsx/docx — чистые функции, легко тестировать
infrastructure/          модели, репозитории, миграции
tgbot/services/          сеть, синхронизация, фоновые циклы
tgbot/handlers/          три роутера: admin, editor, user
```

Порядок роутеров важен: `admin` → `editor` → `user`. У `user` есть
catch-all обработчик на любой текст, поэтому он обязан быть последним.

## Почему SQLite и MemoryStorage

Данных мало (тысячи строк), читателей — сотни, запись — раз в 5 минут.
Postgres и Redis здесь были бы инфраструктурой ради инфраструктуры.

`MemoryStorage` для FSM выбран осознанно: состояния живут секунды (ввод
названия предмета, кабинета), и потеря при рестарте не страшна — диалог
просто начнётся заново.

**WAL обязателен.** В режиме `delete` (умолчание SQLite) любая запись
блокирует базу целиком: читатель ждёт писателя, писатель ждёт читателя.
При 246 пользователях `DatabaseMiddleware` пишет в `users` на каждый тап,
а пересборка держит запись несколько секунд — второй староста ловил
`database is locked` через `busy_timeout=5000`. Прагмы ставятся в
`infrastructure/database/setup.py` при подключении: `journal_mode=WAL`,
`busy_timeout=10000`, `synchronous=NORMAL` (в WAL безопасен, теряются
только последние транзакции при отключении питания).

WAL добавляет файлы `database.db-wal` и `database.db-shm`. Копировать
базу через `cp` при этом нельзя — `sqlite3 .backup` копирует и их
содержимое.
