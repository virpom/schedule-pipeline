# План 049: предупреждение «сайт не отвечает» врёт каждую ночь

**Приоритет:** средний. Не ломает расписание, но **треть суток**
показывает студенту неправду и подрывает доверие к боту.

**Трудоёмкость:** S (~10 строк).

## Проблема

`source_state.py:28`:

```python
STALE_AFTER = datetime.timedelta(minutes=30)
```

`poller.py:242` не опрашивает сайт ночью:

```python
if not _in_night(now, settings["night_start"], settings["night_end"]):
    if time.monotonic() - last_poll >= interval:
        changes = await poll_once(bot, session_pool, config)
```

Дефолты (`setting.py:8`):

```python
"poll_interval": "300",      # 5 минут
"night_start": "23:00",
"night_end": "07:00",
```

**В базе этих ключей нет** — проверил прод:

```
night_start  = (нет)
night_end    = (нет)
poll_interval = (нет)
```

Значит работают дефолты: ночью с 23:00 до 07:00 опроса **нет вовсе**.

## Что происходит

```
22:57  последний успешный опрос (last_sync_ok)
23:00  ночной режим, опрос выключен
23:27  проходит 30 минут -> is_stale() = True
07:00  ночной режим кончается
07:05  первый утренний опрос
```

С **23:27 до 07:05** — 7 часов 38 минут, то есть **треть суток** —
любой студент, открывший расписание, видит:

```
⚠️ Сайт колледжа не отвечает с 25.10 22:57.
Замены с тех пор не проверены — они могли появиться.
```

А сайт при этом жив и здоров. Просто ночь.

## Проверено на живом проде

В момент проверки:

```
last_sync_ok     = 2026-10-25T22:57:35
last_sync_ok_vuz = 2026-10-25T22:57:35
сейчас           = 2026-10-26T00:04:13
прошло 1:06:38  ->  stale(>30м) = True
```

То есть **прямо сейчас** предупреждение активно, хотя это обычная
ночь, а не сбой.

## Второй дефект: текст говорит не то

`common/schedule.py:303`:

```python
return (f"\n\n⚠️ <i>Сайт колледжа не отвечает с {when:%d.%m %H:%M}. "
        f"Замены с тех пор не проверены — они могли появиться.</i>")
```

`when` — это `last_ok`, то есть **время последнего успеха**. Фраза
«не отвечает с 22:57» читается как «сбой начался в 22:57». На деле
22:57 — момент, когда всё было **хорошо**.

Честная формулировка: «последняя успешная проверка — 25.10 в 22:57».

## Подтверждено на живом проде

Замер в 02:32 по Красноярску (внутри ночного окна):

```
NOW          2026-10-26T02:32:31
LAST_OK      2026-10-25T22:57:35     <- 3 ч 35 мин назад
LAST_OK_VUZ  2026-10-25T22:57:35
STALE_AFTER  30 мин
```

`is_stale()` = True, значит **каждый экран** в этот момент показывал
предупреждение о несвежих данных. При этом поллер здоров: он честно
спит по `_in_night`, и последний успешный проход был перед закрытием
окна.

Ключей `night_start`/`night_end` в базе нет — `get_all()` подмешивает
`DEFAULTS` (`{**DEFAULTS, **stored}`), так что окно работает. Проверил
это отдельно, чтобы не спутать с поломкой поллера.

## Что сделать

**Часть 1 — не считать ночь устареванием.** Порог должен учитывать
ночное окно:

```python
async def is_stale(repo: RequestsRepo) -> bool:
    when = await last_ok(repo)
    if when is None:
        return True
    settings = await repo.settings.get_all()
    # Ночью поллер намеренно спит, поэтому старым считается только то,
    # что старше ночного окна плюс обычный порог.
    grace = STALE_AFTER
    if _in_night(datetime.datetime.now(), settings["night_start"], settings["night_end"]):
        grace = STALE_AFTER + _night_length(settings)
    return datetime.datetime.now() - when > grace
```

`_in_night` уже есть в `poller.py` — вынести в `common/` или в
`source_state`, чтобы не дублировать.

**Часть 2 — честный текст:**

```python
return (f"\n\n⚠️ <i>Последняя успешная проверка замен — "
        f"{when:%d.%m в %H:%M}. С тех пор сайт не отвечал.</i>")
```

**Часть 3 — порог из настроек.** Сейчас `STALE_AFTER` — константа,
хотя `poll_interval` настраивается. Логичнее:

```python
grace = datetime.timedelta(seconds=int(settings["poll_interval"]) * 6)
```

Шесть интервалов — запас на разовый сбой. При дефолтных 300 с это те
же 30 минут, но если админ поставит `/setpoll 600`, порог подстроится.

## Проверено и признано корректным

**`_in_night` правильно обрабатывает переход через полночь.**
Проверил все границы для окна `23:00–07:00`:

```
23:30 -> True    00:30 -> True    06:59 -> True
07:00 -> False   07:01 -> False   12:00 -> False
22:59 -> False   23:00 -> True
```

Полуинтервал `[start, end)` соблюдён: 07:00 уже не ночь.

**`start == end` трактуется как «ночи нет»** — разумно: иначе окно
нулевой длины блокировало бы всё.

**`format_stale_warning` в одном месте защищён, в другом — нет.**
Проверил оба вызова в `user.py`:

```python
# стр. 668 — есть пары
if stale and last_ok is not None:          # ЗАЩИЩЕНО
    text += format_stale_warning(last_ok)

# стр. 681 — пар нет, но день был опубликован
if stale:                                  # НЕ ЗАЩИЩЕНО
    text += format_stale_warning(last_ok)
```

При `last_ok is None` второй путь покажет:

> ⚠️ Расписание с сайта ни разу не загрузилось. Замены не проверены.

А `published=True` означает, что файл **был** скачан и разобран — то
есть сайт работал. Текст противоречит самому условию, при котором
показан.

**На проде недостижимо:** `last_sync_ok = 2026-10-25T22:57:35` есть,
`schedule_file` — 22 строки. Но достижимо на свежей базе, где
`last_sync_ok` появится только после первого успешного опроса, а
`schedule_file` заполнится раньше. Чинится тем же условием
`and last_ok is not None`.

**Вуз и колледж разделены правильно** — у каждого свой
`last_sync_ok`/`is_stale`. Сбой колледжа не помечает вуз устаревшим.

**`mark_ok` ставится только при полном успехе** — проверял в
предыдущих раундах, `result.get("failed")` учитывается.

## Риски

- **Увеличение порога ночью может скрыть реальный ночной сбой.** Если
  сайт упал в 23:00 и не поднялся, студент узнает об этом только в
  07:05. Но ночью он всё равно не пошёл бы на пары — риск приемлем.
- **`settings.get_all()` добавляет запрос на каждый вызов
  `is_stale`.** Сейчас `is_stale` вызывается дважды на экран (для вуза
  и колледжа). Плюс два запроса к `setting` — мелочь, но заметно в
  горячем пути. Можно кэшировать на время жизни запроса.
- **Часть 3 меняет поведение при `/setpoll`.** Если админ поставит
  600 с, порог станет 60 минут — студенты будут дольше видеть свежие
  данные как «свежие». Это логично, но стоит упомянуть в подсказке
  команды.
