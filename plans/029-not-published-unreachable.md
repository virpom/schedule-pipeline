# План 029: «расписание не выложено» недостижимо, `deadline_hour` не работает

**Приоритет:** низкий (результат верный), но это хрупкая случайность —
сломается при смене `MATERIALIZE_DAYS`.

**Трудоёмкость:** S (~10 строк).

## Проблема

`user.py:671` выбирает сообщение на пустой день по пяти условиям.
Цепочка:

```python
published = await repo.schedule_files.get_hash(date) is not None
if note:          format_no_lessons(date, note)
elif published:   format_no_lessons(date)              # «занятий нет»
elif stale:       format_unverified(date, last_ok)      # «не проверено»
else:
    deadline = int(s.get("deadline_hour", 20) or 20)
    if now.hour >= deadline:  format_no_lessons(date)   # «занятий нет»
    else:                     format_not_published(date) # «не выложено»
```

Но `materialize` пишет `schedule_file` **безусловно на все 14 дней
окна**, включая пустые:

```python
if await repo.schedule_files.get_hash(date) is None:
    await repo.schedule_files.set_hash(date, f"eios-{date.isoformat()}")
```

Проверено на проде — 2 пустых дня с `published=True`:

```
2026-10-25    0 пар   <-- воскресенье, хеш есть
2026-11-01    0 пар   <-- воскресенье, хеш есть
```

Значит `published` — это **не** «сайт выложил файл», а «день попал в
окно материализации». Докстринг в `materialize` («Расписание пришло с
сайта — значит день опубликован») описывает не то, что делает код.

## Следствие 1: ветка `format_not_published` мертва

Чтобы она сработала, нужно одновременно: нет пар, нет заметки,
`published=False`, сайт жив, `now.hour < 18`. Но все даты, доступные
в UI, лежат внутри окна 14 дней:

| Экран | Даты |
|---|---|
| `day:today` / `day:tomorrow` | сегодня, завтра |
| `week` | сегодня … +6 |
| «Ближайшее» в пустом дне | +1 … +7 |
| `hist` | только прошлое |

`MATERIALIZE_DAYS = 14` покрывает всё это. Поэтому `published=True`
всегда, и «расписание ещё не выложено» студент не увидит никогда.

## Следствие 2: `deadline_hour` не делает того, что задумано

Смысл настройки: «после 18:00 сайт уже должен был выложить завтра —
если пар нет, значит их и не будет». Но до этой ветки дело не доходит,
потому что `published` перехватывает раньше.

**Отдельно:** `deadline_hour` в БД = `18`, а дефолт в коде = `20`.
Расхождение безобидно (значение из БД выигрывает), но говорит о том,
что настройку меняли, не проверив, работает ли она.

## Что сделать

Вариант А — честно назвать вещи своими именами:

```python
# schedule_file означает «день материализован», а не «сайт опубликовал».
# Для окна 14 дней это одно и то же; за окном — нет.
published = await repo.schedule_files.get_hash(date) is not None
```

и убрать недостижимую ветку с `deadline_hour`, чтобы не создавать
иллюзию работающей настройки. Заодно убрать `deadline_hour` из
`/settings`.

Вариант Б — починить семантику: писать хеш только когда день реально
пришёл с сайта. Но у колледжа расписание приходит **семестром**, а не
по дням — «день опубликован» неотличимо от «день в окне». Вариант Б
не реализуем без изменения источника.

**Рекомендация: вариант А.** Меньше кода, нет вранья в настройках.

```python
if note:
    text = format_no_lessons(date, note)
elif published:
    text = format_no_lessons(date)
elif stale:
    text = format_unverified(date, last_ok)
else:
    text = format_not_published(date)
```

## Риски

- **Если `MATERIALIZE_DAYS` уменьшат** ниже 7 (например, до 5), часть
  дат из «Ближайшее» окажется за окном и попадёт в
  `format_not_published` — это как раз правильное поведение. То есть
  ветку не обязательно удалять, но её надо осознанно оставить.
- **`deadline_hour` уже настроен в проде (18).** Удаление из `/settings`
  не удалит строку из БД — она просто перестанет читаться.
- **`schedule_file` больше нигде не читается** — проверил, только
  `user.py:674`. Так что переименование семантики безопасно.
