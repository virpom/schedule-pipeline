# План 085: чат нельзя отвязать — бот останется в списке навсегда

> **СДЕЛАНО 27.10.2026** (коммит `a8c9cae`).
>
> Оба уровня, как просил план: кнопка «Отвязать» и обработчик
> `my_chat_member` на `left`/`kicked` (`restricted` не удаляет).
> Сверх плана: middleware БД не был подключён к `my_chat_member` —
> обработчик упал бы с `KeyError` на первом же выгоне.

**Приоритет:** низкий. На проде чатов **ноль**, функциональность не
используется. Но код готов, и первое же подключение упрётся.

**Трудоёмкость:** S (~15 строк).

## Проблема

`ChatRepo` (`infrastructure/database/repo/chat.py`) умеет только писать
и читать:

```python
async def set_group(self, chat_id: int, title: str, group: str) -> None: ...
async def get_all(self) -> list[Chat]: ...
```

Метода удаления нет. Админ-экран `list_chats` (`admin.py:400`) только
печатает список:

```python
for c in chats:
    lines.append(f"{c.id} · {c.title or '—'} → {c.group or '—'}")
```

Ни кнопки «отвязать», ни реакции на то, что бота выгнали.

## Что произойдёт

1. Админ добавляет бота в группу, ставит `/setgroup ДП-26` — запись
   появляется.
2. Бота удаляют из группы (или группа распущена, или админ ошибся
   группой).
3. Запись остаётся. `poller.py:152` читает `chats.get_all()` на каждой
   рассылке.
4. `broadcast_schedule` пытается отправить — `TelegramForbiddenError`.
   `send_message` его ловит и возвращает `False`, так что **рассылка не
   падает**. Но попытка повторяется каждый раз.
5. В логах — `Target [ID:...]: got TelegramForbiddenError` после каждой
   рассылки. Вечно.

Обработчика `my_chat_member` в проекте нет — проверил `grep -rn
"my_chat_member\|chat_member"`, ноль совпадений. То есть бот не узнаёт,
что его выгнали.

## Что на проде

```
chats: 0 строк
```

Функциональность не подключена ни разу. Дефект латентный — но именно
поэтому его дешево починить сейчас, пока не выяснилось на живой группе.

## Что сделать

**Минимум** — команда отвязки:

```python
async def remove(self, chat_id: int) -> None:
    await self.session.execute(delete(Chat).where(Chat.id == chat_id))
    await self.session.commit()
```

и в `list_chats` — кнопка рядом с каждым чатом.

**Лучше** — обработчик `my_chat_member`:

```python
@admin_router.my_chat_member()
async def on_member(event: ChatMemberUpdated, repo: RequestsRepo):
    if event.new_chat_member.status in ("left", "kicked"):
        await repo.chats.remove(event.chat.id)
```

Тогда запись уходит сама, без участия админа. Это правильнее: админ
может не заметить, что бота выгнали.

**Совсем правильно** — и то, и другое: обработчик на случай выгона,
кнопка на случай «ошибся группой».

## Проверено и признано корректным

**`set_group` идемпотентен.** Проверил: `on_conflict_do_update` по
`id`, повторный вызов обновляет `title`/`group`, а не плодит строки.
То есть «перепривязать к другой группе» работает — не работает только
«отвязать совсем».

**Рассылка в чат не падает при ошибке.** `send_message` ловит
`TelegramForbiddenError` и возвращает `False`; `broadcast_schedule`
считает `sent` и идёт дальше. Проверил — цикл не прерывается.

**Пустой `group` пропускается.** `poller.py:187`:
```python
for chat in chats:
    if not chat.group:
        continue
```
Так что чат без привязки в рассылку не попадает — только висит в
списке.

**`/chats` требует админа.** Проверил `_is_admin` в `list_chats` и
`_is_admin_cb` в `cb_adm_chats` — оба на месте.

## Риски

- **`my_chat_member` требует прав.** Aiogram доставляет это событие
  только если бот в чате; при выгоне — тоже доставляет, но без
  гарантии порядка. Если событие не придёт, останется кнопка.
- **Не удалять чат при `restricted`.** Человек может ограничить бота
  временно. Удалять стоит только на `left`/`kicked`.
