# План 091: староста вводит преподавателя вслепую

> **СДЕЛАНО 27.10.2026** (коммит `8f32a11`).
>
> Подсказки из преподавателей группы, после нормализации. `suggestions`
> кладётся в FSM на всех трёх входах — ловушка плана 073 скопирована
> вместе с исправлением и стережётся тестом.

**Приоритет:** средний. Это не сбой, а отсутствие помощи там, где она
нужнее всего: фамилий 186, и опечатка в одной букве делает пару
невидимой для поиска.

**Трудоёмкость:** S (~15 строк).

## Проблема

Ввод преподавателя — свободный текст без единой подсказки:

`editor.py:948`:
```python
@editor_router.message(EditorState.teacher)
async def on_teacher(message: Message, repo: RequestsRepo, state: FSMContext):
    await state.update_data(teacher=(message.text or "").strip())
    await message.answer(
        f"{EDITOR_TITLE}\n\n🚪 <b>Кабинет</b> или «Пропустить».",
        reply_markup=_skip_kb("ed:sub_skip_room"),
    )
    await state.set_state(EditorState.room)
```

Ни `get_teachers`, ни `get_teachers_vuz` в `editor.py` не вызываются —
проверил `grep -n "get_teachers" tgbot/handlers/editor.py`, ноль
совпадений.

Для сравнения: **предмет** подсказками снабжён (`_subject_suggestions`
+ `_suggest_kb`), хотя предметов у группы 10–31, а преподавателей в
базе **186** (228 сырых значений после `_clean_teacher_names`).

## Почему это дороже, чем кажется

`teacher_matches` сравнивает только фамилию, поэтому «Коленова» найдёт
«Коленова В.А.» — опечатка в инициалах безвредна. Но:

- **Опечатка в фамилии** (`Кабышева` → `Кабышеваа`) — пара не найдётся
  ни у кого, и староста этого не увидит: он вводит текст, получает
  «Сохранено», а студент видит пару без преподавателя.
- **Двойная фамилия** — `Мурашова-Росс` пишется тремя способами
  ([план 090](090-dash-in-surname-duplicate.md)); как её наберёт
  староста, зависит от настроения.
- **Однофамильцы** — семь пар ([план 024](024-homonyms-mixed.md)),
  и выбрать нужного без списка нельзя.

## Что на проде

```
преподавателей в base_lesson: 228 сырых -> 186 после нормализации
```

Список в 186 записей в кнопки не влезет, но он и не нужен целиком —
нужны те, кто ведёт **эту группу**. Такой выборки в репозитории нет,
но её легко получить: `base_lessons.get_week(group, parity)` уже
возвращает пары группы с полем `teacher`.

## Что сделать

Собрать преподавателей группы тем же приёмом, что и предметы:

```python
async def _teacher_suggestions(repo: RequestsRepo, group: str) -> list[str]:
    seen: dict[str, int] = {}
    for parity in (PARITY_ODD, PARITY_EVEN, PARITY_ANY):
        for l in await repo.base_lessons.get_week(group, parity):
            t = (l.teacher or "").strip()
            if t:
                seen[t] = seen.get(t, 0) + 1
    return [t for t, _ in sorted(seen.items(), key=lambda kv: -kv[1])]
```

и показать в `on_subject` — там, где сейчас только «Пропустить»:

```python
suggestions = await _teacher_suggestions(repo, group)
await state.update_data(suggestions=suggestions)     # <- не забыть!
...
reply_markup=_suggest_kb(suggestions, "ed:tsug", back="ed:sub_skip_teacher")
```

**Критично:** сохранить `suggestions` в state. Именно на этом сломался
аналогичный механизм для предметов — [план 073](073-suggestions-not-stored.md):
`_suggest_kb` кладёт в `callback_data` индекс, а обработчик читает
список из состояния, которого там нет, и всегда отвечает «Устарело».
Копировать этот путь надо **вместе** с исправлением 073, иначе
подсказки преподавателей умрут так же.

## Проверено и признано корректным

**Ручной ввод работает и остаётся доступным.** `on_teacher` принимает
любой текст, `_skip_kb` даёт «Пропустить». Подсказки — дополнение, не
замена.

**Пустое имя не ломает поиск.** `get_for_teacher_date` и родственные
методы проверяют `if not (teacher_name or "").strip(): return []` —
пустая строка не превращается в `LIKE '%%'`. Проверено.

**`_clean_teacher_names` нормализует дубли.** 228 → 186, «Кокошка
И. П.» и «Кокошка И.П.» схлопываются, `Ляшко` без инициалов уходит в
пользу `Ляшко Д.В.`. Подсказки надо строить **после** нормализации,
иначе в кнопках будет два одинаковых человека.

## Про `limit=5` в подсказках предметов

Отдельно проверил утверждение [плана 073](073-suggestions-not-stored.md),
что «пять самых частых предметов достаточно». Замер на проде:

```
предметов на группу:  медиана ~13, максимум 31 (ГД - 26оз@vuz)
групп, у которых предметов больше 5:  128 из 129
групп, которые целиком влезают в лимит:  1
```

То есть подсказки обрезаны почти всегда. И сортировка по частоте в
колледже не помогает: у `ДП-26` частоты `3, 2, 2, 2, 2, 2, 2, 2, 1, 1`
— «топ-5» тут произвольные пять из десяти, а не самые нужные.

Это не делает план 073 неверным (мертвые подсказки хуже, чем
обрезанные), но после его правки обрезка станет заметной. Стоит либо
поднять лимит до 8–10, либо сортировать по алфавиту — предсказуемее,
чем по частоте, которая у колледжа почти не различается.

## Риски

- **Ещё одна кнопка на экран.** У группы с 20 преподавателями
  клавиатура станет длинной. Лимит 5–8 обязателен.
- **Дубли после нормализации.** Если строить список из `base_lesson`
  без `teacher_base`, в кнопках окажутся «Кокошка И. П.» и «Кокошка
  И.П.» как два человека. Нормализовать перед показом.
