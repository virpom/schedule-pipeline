# План 069: обед привязан к паре 2 жёстко, а не к своей паре

**Приоритет:** низкий. Затрагивает 2 человека из 224, но баг настоящий
и тихий.

**Трудоёмкость:** S (~4 строки).

## Проблема

`bell.py:78`:

```python
# lunch (big break) — anchored to the para where lunch sits (2-я пара)
if user.bell_mode == BELL_FULL:
    lunch_lesson = next(
        (l for l in lessons if l.para <= 2 <= (getattr(l, "para_end", None) or l.para)),
        None,
    )
```

Двойка зашита в код. При этом в модели есть поле, которое говорит, к
какой паре привязан обед:

`infrastructure/database/models/bell_lunch.py:19`:

```python
para: Mapped[int] = mapped_column(Integer)   # к какой паре привязан обед
position: Mapped[str] = mapped_column(String(8))  # inside | after
```

Код его не читает. Если обед когда-нибудь переставят на 3-ю пару через
`/setbell`, `bell.py` продолжит искать 2-ю.

## Что ломается уже сейчас

Даже при `para=2` в БД есть случаи, когда пары 2 у группы нет вовсе.
Проверил на проде (колледж, даты от сегодня):

```

  ('ТЭф-25', '2026-10-29', '3,4,5')
```

Затронуто 9 групп:

Как это получается: у группы в этот день первые пары пустые (окно,
практика, поздний заход), занятия начинаются с 3-й. Условие
`l.para <= 2 <= para_end` для пары 3 даёт `3 <= 2` — ложь. Обед не
находится, уведомления «🍽 Обед» и «🍽 Обед закончился» не приходят.

## Масштаб

```
всего подписано:            224
с bell_mode != 'off':        14   (реальные получатели звонков)
  из них full:                7
  из них start_end:           8
```

Обед показывается только при `BELL_FULL`, то есть максимум 7 человекам.
Из них в затронутых группах — **2**.

Это немного. Но баг коварный: человек с `full` специально включил
подробный режим, чтобы знать про обед, и именно у него обед молча
пропадает. Он не поймёт, что сломалось, — просто не получит сообщение.

## Что сделать

Брать пару из самой записи об обеде, а не из литерала:

```python
if user.bell_mode == BELL_FULL:
    # Пара обеда берётся из bell_lunch: у разных потоков она может
    # отличаться, и жёсткая «2» ломается, когда первые пары пустые.
    lunch = lunches.get((dt, own_cg or "I_IV")) or lunches.get((dt, "I_IV"))
    if lunch:
        lunch_para = lunch.para
        lunch_lesson = next(
            (l for l in lessons
             if l.para <= lunch_para <= (getattr(l, "para_end", None) or l.para)),
            None,
        )
        if lunch_lesson:
            events.append((lunch.lunch_start, "lunch", "🍽 Обед"))
            events.append((lunch.lunch_end, "lunch_end", "🍽 Обед закончился"))
```

Обрати внимание на порядок: сейчас `lunch` вычисляется **внутри**
`if lunch_lesson`, то есть после того, как найдена пара. Надо наоборот —
сначала узнать пару обеда, потом искать занятие на ней.

## Проверено и признано НЕ проблемой

**30-секундный тик не теряет события.** `bell_loop` просыпается каждые
30 секунд, а `_tick` сравнивает события с текущей минутой
(`now_min = now.replace(second=0, microsecond=0)`). Если тик пришёлся
на 09:24:50, следующий будет 09:25:20 и увидит минуту 09:25. Потеря
возможна только если один тик займёт больше 60 секунд — тогда минута
пропускается навсегда.

Проверил, сколько это может длиться: реальных получателей звонков
**14**, а не 224 (фильтр `get_bell_subscribers` — `bell_mode != 'off'`).
Каждый требует одного запроса в своей сессии. 14 запросов по SQLite —
это единицы миллисекунд, до минуты далеко.

**`bell_notify` — мёртвая колонка.** В `migrations/versions/0001_baseline.py:33`
она есть (`server_default=0`), но в коде **не читается нигде**:

```
$ grep -rn "bell_notify" --include="*.py" . | grep -v .venv | grep -v tests
./migrations/versions/0001_baseline.py:8
./migrations/versions/0001_baseline.py:33
```

Фильтр получателей использует `bell_mode != "off"`. Это уже отмечено в
находке 50 как мёртвая колонка — отдельного плана не нужно.

## Риски

- **`own_cg` для учителя — `None`.** В коде выше `own_cg = None if
  is_teacher else bells_group(...)`. Для учителя нужен фолбэк на
  `_cg(lunch_lesson.group)`, но `lunch_lesson` ещё не найден — курица и
  яйцо. Проще: для учителя брать `I_IV` напрямую, как уже делается
  строкой ниже (`lunches.get((dt, "I_IV"))`).
- **`position="after"` означает, что обед после пары.** В текущем коде
  это учтено только при подавлении «Конец пары» (`lunch.position ==
  "after" and lunch.para == p`). При смене `para` надо проверить, что
  это условие продолжает работать.
