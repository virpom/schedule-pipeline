# План 171: пара на 6-й строке теряется — объединение на три строки и регулярка

**Приоритет:** средний. Одна пара у одной группы (`ТЭф-23`, среда), но
теряется **молча**: в базе её нет, студент её не увидит никогда. Та же
пара есть в файле — проверил, читается глазами.

**Трудоёмкость:** S (~10 строк + тест).

## Что происходит

Файл `Очная форма.xlsx`, лист «4 курс», колонка `C` (группа `ТЭф-23`),
строки 33–35:

```
строка 33:  B="5 пара"    C=" Психология общения\nЗенина С.В."
строка 34:  B=None        C="Иностранный язык в профессиональной деятельности\nГулиева Н.Г"
строка 35:  B=None        C="6-я пара с 18.05 до 19.40 - \n Выполнение работ по профессии ..."
```

`B33:B35` — **одно объединение на три строки** (не на две).

## Две дыры, одна потеря

### Дыра 1: цикл читает только строки с номером пары

`parse_ochoe` (`parsers/eios.py:277-279`):

```python
para_cell = sheet.cell(row, 2).value
if not (para_cell and "пара" in str(para_cell)):
    continue
```

У объединения `B33:B35` значение лежит только в `B33`. `B34` и `B35` —
`None`, поэтому строки 34 и 35 **пропускаются целиком**, хотя в `C35`
стоит настоящая пара.

Строка 34 не теряется случайно: её читают как `bottom` строки 33 и
получают нечётную половину пары 5. А строка 35 не читается никем.

### Дыра 2: регулярка не знает формата «N-я пара с … до …»

Даже если бы строка 35 дошла до `_strip_time_note`, префикс не снялся бы.
`_TIME_HEAD_RE` (`:59-62`):

```python
r"^\s*(?:\d+-я\s+пара\s*-\s*|с\s+\d+[.:]\d+\s+до\s*\.?[\d.:]+\s*-?\s*)"
```

Ветки две: `N-я пара -` (дефис сразу) **или** `с X до Y`. В источнике —
**оба сразу**: «`6-я пара с 18.05 до 19.40 -`». Проверил:

```
'6-я пара с 18.05 до 19.40 - \n Выполнение...'  match=False  note=None
'5-я пара - Психология'                          match=True   note='5-я пара'
'с 18.00 до 21.00 - Физика'                      match=True   note='с 18.00 до 21.00'
```

Тогда предмет остался бы с префиксом «6-я пара с 18.05 до 19.40 -» в
тексте, а `time_note` — пустым.

## Воспроизвёл

Разобрал живой файл (`parse_ochoe`, 52550 байт) и сравнил с базой:

```
ТЭф-23, среда, что отдал парсер:
  п3 EVEN  'Выполнение работ по профессии "Машинист-обходчик по кот'
  п4 EVEN  'Финансовая грамотность'
  п4 ODD   'Основы управления персоналом производственного подразде'
  п5 EVEN  'Психология общения'
  п5 ODD   'Иностранный язык в профессиональной деятельности'

п6 — нет вовсе
```

В `base_lesson` то же самое. Строки 35 в базе нет ни в каком виде:
искал `subject LIKE '%Выполнение работ по профессии%'` — у `ТЭф-23`
нашлась только пара 3 в среду, это другая пара (тоже «Выполнение
работ», но `Мордвин А.О.`).

## Масштаб — проверил

Искал по всем листам ячейки с шаблоном «N-я пара с … до …»:

```
'4 курс' C='ТЭф-23' строка 35
  '6-я пара с 18.05 до 19.40 - \n Выполнение работ по профессии "Машинист-обход...'
всего: 1
```

Один случай в файле. Но он показывает класс ошибки: **любая** пара,
попавшая в третью строку трёхстрочного объединения, пропадёт молча.
Сейчас объединений на 3 строки по группам немного (в «4 курс» — `D33:D35`,
`H33:H35`, `G33:G35`, все пустые), но формат от этого не защищён.

## Что сделать

**Обход объединений.** Читать значение объединения для любой строки
внутри него, а не только для верхней:

```python
merged_para = {}
for rng in sheet.merged_cells.ranges:
    if rng.min_col == 2 and rng.max_col == 2:
        value = sheet.cell(rng.min_row, 2).value
        for row in range(rng.min_row, rng.max_row + 1):
            merged_para[row] = value

para_cell = sheet.cell(row, 2).value or merged_para.get(row)
```

**Регулярка.** Разрешить оба хвоста сразу:

```python
r"^\s*(?:\d+-я\s+пара(?:\s+с\s+\d+[.:]\d+\s+до\s*\.?[\d.:]+)?\s*-\s*"
r"|с\s+\d+[.:]\d+\s+до\s*\.?[\d.:]+\s*-?\s*)"
```

Проверить на всех пяти вариантах, что были в тесте выше, плюс на
«`6-я пара с 18.05 до 19.40 -`».

**Номер пары.** После снятия префикса у строки 35 номер пары берётся из
`B` (там «5 пара» из объединения) — это **неверно**: текст говорит
«6-я пара». Стоит вытаскивать номер из префикса, когда он там есть:

```python
m = re.match(r"\s*(\d+)-я\s+пара", subject)
if m:
    para = int(m.group(1))
```

Иначе пара попадёт в п5 поверх «Иностранного языка» (нечётная
половина) и скроет его.

## Проверено и признал корректным

**Все шесть дней распознаются на всех четырёх листах.** Проверил
колонку `A` целиком:

```
'1 курс '  ПОНЕДЕЛЬНИК 5,  ВТОРНИК 15, СРЕДА 25, ЧЕТВЕРГ 35, ПЯТНИЦА 45, СУББОТА 55
'2 курс'   то же
'3 курс'   ПОНЕДЕЛЬНИК 5,  ВТОРНИК 15, СРЕДА 26, ЧЕТВЕРГ 36, ПЯТНИЦА 46, СУББОТА 56
'4 курс'   ПОНЕДЕЛЬНИК 5,  ВТОРНИК 15, СРЕДА 25, ЧЕТВЕРГ 36, ПЯТНИЦА 46, СУББОТА 56
```

Строки **нерегулярны**: на «3 курс» и «4 курс» перед средой и дальше
стоит лишняя пустая строка (26/36/46 вместо 25/35/45). Парсер это
переживает, потому что не полагается на арифметику: он идёт по строкам
и запоминает последний увиденный день. Но это же и объясняет, почему
объединение `B33:B35` попалось именно здесь — на листах с ровной
разметкой такой трёхстрочной клетки нет.

**Строка 34 не теряется.** Она читается как `bottom` строки 33 и даёт
нечётную половину пары 5 — «Иностранный язык», `Гулиева Н.Г`. Это
верно: в файле две пары на одну клетку, верх и низ.

**Заголовки дней в объединениях на 10 строк — не проблема.**
`A5:A14`, `A25:A34` и подобные содержат «ПОНЕДЕЛЬНИК», «СРЕДА». Цикл
читает их только в `min_row`, а этого достаточно: `day` запоминается до
следующей смены. Проверил — все шесть дней на всех листах
распознаются.

**Объединения `B23:B25` на «3 курс» безвредны.** Значение — `None`,
номер пары берётся из других строк.

**`merged_pairs` для пар чётности работает верно.** Он ловит только
`1x2` (`rng.max_row == rng.min_row + 1`), и это правильно: `1x2` —
разъединённая клетка «верх/низ», а не продолжение строки.

## Риски

- **Правка обхода объединений касается всех листов.** Прогнать
  `parse_ochoe` на живом файле и сверить число пар до/после: должно
  вырасти ровно на 1 (или больше, если появятся ещё трёхстрочные).
- **Номер пары из префикса** может разойтись с номером в колонке `B`,
  если файл противоречив. Тогда приоритет — за текстом ячейки: он
  описывает то, что реально написано.
- **План 158 считает `_TIME_HEAD_RE` мёртвой** и предлагает её удалить.
  После этой правки удалять её нельзя: она начнёт работать. Планы 158 и
  171 надо читать вместе — 158 верен в том, что `time_note` никуда не
  пишется, но не в том, что регулярка безвредна.
