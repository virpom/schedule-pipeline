# План 089: рассылка шлёт «Занятий нет» на даты за окном материализации

> **УСТАРЕЛ 27.10.2026.** Дефект закрыт переделкой рассылки по
> отпечаткам, а не этой правкой. Коммит `81161fe` (план
> [100](100-broadcast-all-dates-when-one-changed.md)) добавил
> `CollegeLessonRepo.digest_by_date()`, и `poll_once` теперь собирает
> даты **из `college_lesson`**, а не из `substitutions.get_dates()`:
>
> ```python
> for date, groups in after.items():          # after = digest_by_date()
>     was = before.get(date, {})
>     diff = {g for g, h in groups.items() if was.get(g) != h}
>     if diff:
>         changed[date] = diff
> ```
>
> Дат за окном материализации в `college_lesson` нет по построению —
> окно 14 дней, `MATERIALIZE_DAYS`. Значит и в рассылку они не попадут.
> `get_dates()` в `poll_once` больше не вызывается (проверил `grep`:
> остался только в тестах и в комментарии `poller.py:139`).
>
> Запасная ветка `for i in range(3)` тоже внутри окна — `today` плюс два
> дня. Остальное в плане описывает код, которого уже нет; читать как
> историю.

**Приоритет:** высокий. 1140 сообщений в день, когда обновился листок
замен, и почти все — неправда.

**Трудоёмкость:** S (~6 строк).

## Проблема

`poll_once` (`poller.py:130`) собирает даты для рассылки **из листка
замен**, не проверяя, попали ли они в `college_lesson`:

```python
dates = set(await repo.substitutions.get_dates(today))
if (result and result["ochoe"]) or vuz_changed:
    dates |= {today + datetime.timedelta(days=i) for i in range(3)}

for date in sorted(dates):
    changes.append((date, had_lessons == 0 and date == today))
```

`get_dates` отдаёт все даты замен начиная с сегодняшней — включая
далёкие. А материализация идёт только на 14 дней вперёд
(`MATERIALIZE_DAYS = 14`), поэтому на далёкую дату в `college_lesson`
**нет ни одной строки**.

Дальше `notify_new_schedule` честно спрашивает:

```python
lessons = await repo.college_lessons.get_for_group_date(user.group, date)
...
if lessons:
    text = format_day(...)
else:
    text = format_no_lessons(date, note)
```

Пусто → `empty_day` → **«Занятий нет 🙌»**.

## Что на проде прямо сейчас

Снял состояние (сегодня 26.10, окно 26.10–07.11, `max(date)` в
`college_lesson` = **07.11**):

```
дата замен     подписчиков получат «Занятий нет»
2026-11-09      228 из 228
2026-11-14      228 из 228
2026-11-18      228 из 228
2026-11-19      228 из 228
2026-12-10      228 из 228
```

Пять дат — **1140 сообщений**, и каждое неверно. Проверил, что там
на самом деле:

```
2026-11-09  6 замен  3 группы   ИП-25@vuz, ИС-26@vuz, ИЭ-26@vuz
2026-11-14  1 замена 1 группа   МН-25@vuz
2026-11-18  2 замены 2 группы   МН-26@vuz, ЭК-26-1@vuz
2026-11-19  1 замена 1 группа   ИП-25@vuz
2026-12-10  1 замена 1 группа   ЭК-24@vuz
```

Все — вуз, все `replace`. То есть у этих групп в те дни **есть пары**,
просто их ещё не материализовали.

## Почему это не «просто шум»

Сообщение приходит с префиксом «🔄 **Расписание изменилось**» — студент
читает: «в этот день занятий нет, и это только что изменилось». Для
даты через полтора месяца это выглядит как отмена. Кто-то не придёт.

Отдельно плохо, что даты далёкие: 10.12 — за 45 дней. Никакой
материализации там не будет ещё месяц, так что при каждом новом
листке замен это повторится.

## Что сделать

Не рассылать по датам, которых нет в материализованной таблице:

```python
async with session_pool() as db:
    repo = RequestsRepo(db)
    materialized = set(await repo.college_lessons.get_dates())   # все даты в таблице
dates &= materialized
```

Метод `get_dates_for_group` уже есть; нужен общий — либо просто
`select(distinct date)`.

**Почему это правильно, а не «костыль»:** `college_lesson` — то, что
видит студент. Если даты там нет, слать про неё нечего: текст будет
построен из ничего. Когда окно докатится, `materialize` создаст день,
но рассылка к тому времени уже не сработает — нужен второй механизм
(см. ниже).

**Второй механизм** — чтобы замена на 09.11 всё-таки дошла до
`ИП-25@vuz`. Сейчас она не доходит вообще: в день, когда окно
докатится до 09.11 (это 27.10), `poll_once` разошлёт только если
листок замен изменился **в этот день**. Иначе — тишина.

Вариант: при материализации нового дня сравнивать его с прошлым
состоянием и рассылать, если появились замены. Это уже за пределами
этой правки и ближе к [плану 055](055-new-schedule-flag-never-true.md)
(признак «новое»).

## Проверено и признано корректным

**`get_dates` сама по себе верна.** Она и должна отдавать все даты
замен — это её контракт (докстринг: «листок выдаётся сразу на несколько
дней вперёд»). Проблема в том, что вызывающий код не сверяет результат
с реально доступными данными.

**Окно в 14 дней — не дефект.** [План 068](068-broadcast-all-substitution-dates.md)
прав: «окно катится, и когда дата приблизится, замена применится».
Дефект не в окне, а в том, что рассылка про далёкие даты всё равно
уходит.

**План 068 это замечает, но не считает проблемой.** Строки 271–273:

> Замены на далёкие даты (`2026-11-14`, `2026-11-18`, `2026-11-19`,
> `2026-12-10`) не попадают в `college_lesson`, потому что
> материализация идёт на 14 дней вперёд. Это ожидаемо.

«Не попадают в `college_lesson`» — верно. Не замечено следствие: из
этого `notify_new_schedule` делает **«Занятий нет»**. План 068 про то,
**сколько** дат рассылается; этот — про то, **что** в них написано.

**Пустая дата без замен — не баг.** Если у группы правда нет пар,
«Занятий нет» — правильный ответ. Проверил: 31.10 (суббота) — 166 из
228 получают это сообщение, и это честно, суббота рабочая не у всех.

**`format_no_lessons` не различает причины.** Один и тот же текст для
«пар нет по расписанию», «дата за окном» и «группа исчезла из файла».
[План 029](029-not-published-unreachable.md) вводит
`format_not_published` для «ещё не выложено» — но здесь даже он не
подходит: расписание выложено, просто мы его не материализовали.

## Риски

- **Может скрыть настоящую проблему.** Если `materialize` сломается и
  таблица опустеет, фильтр уберёт все даты — рассылка замолчит
  целиком. Защита: если `materialized` пуст, не фильтровать (лучше
  шум, чем тишина). Или логировать, сколько дат отфильтровано.
- **Нужен новый метод в репозитории.** `get_dates()` без группы —
  одна строка `select(distinct date)`, но её надо добавить и покрыть
  тестом.
