# План 082: `materialize` смотрит только вперёд — прошлые дни остаются пустыми

**Приоритет:** средний. Студент вуза, открывший прошлый день, видит
«Занятий нет», хотя расписание есть.

**Трудоёмкость:** S (одна строка в `materialize`).

## Проблема

`materialize` (`sync_eios.py:401`) пересобирает дни **только вперёд**:

```python
today = datetime.date.today()
groups = await repo.base_lessons.get_groups()
written = 0

for offset in range(days):                       # 0..13
    date = today + datetime.timedelta(days=offset)
    ...
```

`MATERIALIZE_DAYS = 14`. Окно — `[сегодня, сегодня+13]`. Всё, что
раньше сегодняшнего дня, не пересобирается никогда.

## Что это даёт на проде

Разбивка `college_lesson` по датам — строки вуза против колледжа:

```
дата        вуз   колледж
2026-10-02    0     118
2026-10-03    0      60
2026-10-05    0      85
2026-10-06    0      89
2026-10-07    0     105
2026-10-08    0     110
2026-10-23    0     110      <- вуз НОЛЬ
2026-10-24  129      73      <- вуз появился
2026-10-26  139     132
2026-10-27  170     123
...
```

До 23.10 включительно строк вуза **ноль**. С 24.10 — есть.

При этом в `substitution` на 23.10 лежат **8 замен вуза**:

```
('ГП-26@vuz',    1, 'replace', 'Риторика для юристов (лек)')
('ЭЭ-26-1@vuz',  2, 'replace', 'История России (прак.)')
('ГП-26@vuz',    2, 'replace', 'Риторика для юристов (прак.)')
('ЭЭ-26-1@vuz',  3, 'replace', 'История России (лек)')
('АП-26@vuz',    3, 'replace', 'История России (лек)')
('АП-26@vuz',    4, 'replace', 'История России (прак.)')
('ТМ - 24оз@vuz', 7, 'replace', 'Переработка техногенных ресурсов')
('ТМ - 24оз@vuz', 8, 'replace', 'Переработка техногенных ресурсов')
```

И `base_lesson` вуза содержит пары на четверг. То есть расписание на
23.10 существует — в двух слоях. Но `college_lesson` пуст, а студент
читает именно его:

```python
async def _user_lessons(repo, user, date):
    ...
    return await repo.college_lessons.get_for_group_date(user.group, date)
```

Результат: `format_no_lessons(date)` — «Занятий нет 🙌».

## Почему так вышло

Материализация вуза появилась позже колледжа. Первый прогон с вузом
случился 24.10 — с этого дня строки и есть. Всё, что до него, никто
не пересобирал, и уже не пересоберёт: окно уехало вперёд.

## Что сделать

Дать окну заглядывать назад. Минимально — на столько же, сколько
вперёд:

```python
for offset in range(-days, days):
    date = today + datetime.timedelta(days=offset)
```

Но `materialize` вызывается на **каждом** опросе (раз в 10 минут), и
это утроит работу: было 14 дней, станет 28. Каждый день — это 129
групп × `get_day_slots` + `replace_date`.

Дешевле — отдельная разовая засыпка прошлого, один раз при старте:

```python
BACKFILL_DAYS = 14

async def backfill_past(repo: RequestsRepo, days: int = BACKFILL_DAYS) -> int:
    """Один раз дособрать дни, которых нет в college_lesson."""
    today = datetime.date.today()
    written = 0
    for offset in range(1, days + 1):
        date = today - datetime.timedelta(days=offset)
        if await repo.college_lessons.count_for_date(date):
            continue                    # уже есть — не трогаем
        written += await materialize_day(repo, date)
    return written
```

Вызвать из `main.py` после первого успешного `materialize`. Проверка
`count_for_date` не даст пересобирать то, что уже собрано.

**Код обещает обратное.** В `_hist_page` (`user.py:763`) стоит
комментарий:

```python
# У вуза история короче: college_lesson материализуется вперёд на
# 14 дней, а назад заполняется только по мере прошествия. Поэтому
# «Больше расписания нет» на первом заходе — норма, а не ошибка.
```

«Назад заполняется по мере прошествия» — **неверно**. Замер на проде,
даты строго меньше сегодняшней:

```
вуз:      2026-10-24                       (1 дата)
колледж:  2026-10-02 .. 2026-10-08, 10-23, 10-24   (8 дат)
```

Колледж набрал историю, потому что его материализовали раньше. Вуз
появился 24.10 — с этого дня и копится. 23.10 не появится никогда:
окно уехало.

То есть студент вуза, открывший «📜 История», увидит **одну** дату, а
через неделю — семь. Не потому, что расписания не было, а потому что
его не материализовали.

**Стоит ли вообще показывать прошлое?** `_hist_page` и кнопки
`hist:`/`histpage:` — готовый продукт, значит да. Если решено прошлое
не показывать, чинить надо экран, а не материализацию; но тогда 8
замен на 23.10 просто не нужны.

## Проверено и признано корректным

**`_merge_para_clash` сохраняет `action`.** Проверил напрямую: подал
`Slot(action='add')` — на выходе `action='add'`. Потерю `action` в
базе он не объясняет.

**`materialize_day` передаёт `action` в строку.** Проверил:
`"action": slot.action or ""` — поле пишется.

**Разница 24.10 против 26.10 — во времени материализации.** На проде:

```
2026-10-24  action=''     30 строк   <- материализовано до появления замен
2026-10-26  action='add'   5 строк   <- материализовано после
```

То есть `action` теряется не в коде, а в том, что строка записана
раньше, чем пришла замена. Это то же самое явление, что описано выше:
прошлые дни не пересобираются.

**`comment` нигде не выводится.** Проверил все обращения к `.comment`
(`grep -rn "\.comment"`) — пять штук, все либо присваивание, либо
копирование между `Slot`. `format_day` поле не читает. У `site`-замен
`comment` содержит весь текст ячейки («Химико – технолог –
Стрельникова Л.И., ауд. 201»), то есть дублирует `subject`+`teacher`+
`room`, и в `college_lesson` его вообще нет (в модели `CollegeLesson`
такого столбца не существует). Мёртвое поле — отдельного плана не
заслуживает.

**Правка базы тоже не доходит до прошлого.** `_save_base` (`editor.py:474`)
и `cb_del_base` (`:513`) вызывают `_rebuild(repo)` без даты — а это
`materialize`, то есть окно вперёд. Правка базы действует на **все**
недели, включая прошедшие, но пересобираются только 26.10–08.11.

Проверил соседние пути: `_save_sub` (`:618`), `cb_sub_cancel` (`:635`),
`cb_sub_reset` (`:726`) передают дату и вызывают `materialize_day(date)`
напрямую — окно не проверяется, прошлое обновляется. То есть
**замены чинятся, а база нет**.

Замер на проде: `base_lesson` для `ДП-26` пятница и `college_lesson`
за 23.10 совпадают — правок базы ещё не было (`schedule_edit` пуст),
дефект латентный.

**`cb_undo` не пересобирает вовсе** — это [план 004](004-undo-does-not-rebuild.md),
отдельный дефект: откат меняет слои, но `_rebuild` не вызывает. Проверил
программно все писатели в `editor.py` — он единственный без вызова.

**`get_groups()` отдаёт и вуз.** Проверил: `select distinct group from
base_lesson`, без фильтра. На проде 129 групп — 37 колледжа и 92 вуза.
Поэтому в `college_lesson` 1855 строк вуза. В прошлых раундах я
записывал весь слой как колледжный — это было неверно.

## Риски

- **Время прогона — замерил дважды.** На проде:

  ```
  только сборка (get_day_slots, 129 групп):  0.28 с/день, 236 слотов
  полная материализация (с записью):         0.38 с/день, 213 строк
  ```

  Засыпка 14 прошлых дней — **5.3 секунды**. Столько же занимают
  текущие 14 дней, которые уже делаются каждый опрос. Бот не заметит,
  в `main.py` делать можно.

  Замер делал на пустой дате 09.10.2026 и **откатил** (`ROLLED_BACK 0`)
  — следов в боевой базе не осталось.
- **История у преподавателя вуза не пуста, но и не полна.** Проверил:
  `get_dates_for_teacher` фильтрует `college_lesson` по фамилии, поэтому
  преподаватель видит и дни, где ведёт пары у вуза. У Лаговской Е.В.
  13 дат, но из них «прошлых» — только 24.10. Чинится той же засыпкой.
- **Поиск по предмету у вуза видит меньше.** `subject_answer`
  (`user.py:901`) читает `get_all_for_group`, то есть `college_lesson`.
  Замер на проде: у вуза **13 дат**, у колледжа **20**. Значит студент
  вуза ищет «Сопротивление материалов» в 13 днях из 20 и не находит то,
  что было раньше. Отдельного плана не заслуживает — это то же
  следствие, чинится засыпкой.
- **Перезапись ручных правок.** `materialize_day` берёт
  `source != SOURCE_SITE` и переносит их как есть, так что правки
  старосты не пропадут. Но на проде таких строк **ноль** — проверить
  не на чем.
- **`count_for_date` не существует.** В `college_lesson.py` есть
  `count_lessons()` без аргументов и `get_for_group_date`. Нужен новый
  метод или `len(await ...get_dates_for_group(...))` — при правке
  уточнить.
