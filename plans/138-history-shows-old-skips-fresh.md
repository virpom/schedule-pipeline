# План 138: «История» показывает старые дни и пропускает свежие

> **УСТАРЕЛ 27.10.2026.** Проверено на проде: ДП-26 — «27.10, 26.10,
> 24.10, 23.10, 22.10», «Раньше» отдаёт «21.10, 20.10, 19.10, 17.10,
> 16.10». Пропусков нет, свежие дни первыми. В архиве 13 дат.

**Приоритет:** средний. План 120 сказал «архив никто не читает».
Это верно, но неполно: **история работает — только показывает не то**.

**Трудоёмкость:** M (нужен новый метод репозитория + правка `_hist_page`).

## Что видит студент

Открыл «📜 История расписания» под `ДП-26`. Бот предложил:

```
24.10  23.10  08.10
07.10  05.10
⬅️ Раньше
```

Нажал «⬅️ Раньше» — получил:

```
03.10  02.10
```

**Пропущены 20, 21 и 22 октября** — три учебных дня на прошлой неделе.

## Что в архиве

```
day_snapshot:
  2026-10-20:  34 снимка
  2026-10-21:  95 снимков
  2026-10-22: 107 снимков
  2026-10-23:  95 снимков
  2026-10-24:  72 снимка
```

**236 снимков, 712 пар** за 20-22 октября лежат в архиве и не показываются.

## Почему так вышло

`_hist_page` (`user.py:765`) читает **не архив**, а `college_lesson`:

```python
dates = await repo.college_lessons.get_dates_for_group(user.group)
```

А `materialize` (`sync_eios.py:401`) пишет **только вперёд**:

```python
for offset in range(days):
    date = today + datetime.timedelta(days=offset)
```

Прошлое не материализуется вообще. Значит `college_lesson` содержит:

```
прошлые даты, попавшие туда раньше:  02, 03, 05, 06, 07, 08 окт
свежие прошлые даты:                 НЕТ (20, 21, 22 окт отсутствуют)
будущие:                             26.10 .. 07.11
```

**02-08 октября попали в таблицу раньше** — когда окно материализации
было другим или шло назад. С тех пор там и лежат. А 20-22 октября
никогда не материализовались, потому что окно уже сдвинулось.

## Откуда в архиве 20-22 октября

`snapshot_past_days` (`notify_edits.py:61`) собирает их **не из
`college_lesson`**, а из слоёв:

```python
slots = await get_day_slots(repo, group, date)
```

`get_day_slots` читает `base_lesson` + `substitution` — источник истины.
Поэтому архив знает про 20-22 октября, а `college_lesson` нет.

Снимки созданы 23.10 в 21:26 — то есть в тот день, когда эти даты были
«вчера», «позавчера», «три дня назад» (дефолт `days_back=3`).

## Проверил, что данные в архиве верные

Взял `ДП-26` на 21.10:

```
архив: 4 пары
  п1 Организация документооборота и документирование...  Харькова Д.А.
  п2 История России                                     Куранова Е.И.
  п3 Физическая культура                                Рамазанов Т.М.
  п4 Основы делопроизводства                            Молчанова Н.А.
```

А бот на эту дату говорит:

```
📅 Среда, 21 октября

Занятий нет по постоянному расписанию 📋

⚠️ Сайт колледжа не отвечает с 26.10 15:48...
```

**Четыре пары были — бот говорит, что не было.** Архив хранит правду,
но его никто не спрашивает.

## Почему это хуже, чем «архив не читается»

План 120 говорил: архив пишется впустую. На самом деле **история
работает, но врёт**: показывает давние дни, где данные могли устареть,
и молчит про свежие, где данные точные.

Студент, который хочет посмотреть «что было вчера», получает
«Занятий нет» — и поверит.

## Что сделать

**1. Добавить чтение архива.** В `SnapshotRepo` сейчас только `save` и
`exists`. Нужен метод списка дат:

```python
async def get_dates(self, group: str) -> list[datetime.date]:
    result = await self.session.execute(
        select(DaySnapshot.date)
        .where(DaySnapshot.group == group)
        .order_by(DaySnapshot.date.desc())
    )
    return list(result.scalars().all())
```

**2. Слить два источника в `_hist_page`:**

```python
from_lessons = await repo.college_lessons.get_dates_for_group(user.group)
from_archive = await repo.snapshots.get_dates(user.group)
dates = set(from_lessons) | set(from_archive)
```

**3. Отдавать приоритет архиву при показе дня.** Если дата есть в
снимке — рисовать снимок, а не `college_lesson`: снимок зафиксирован
на момент дня, а таблица могла быть перезаписана позже.

## Что проверил и признал корректным

**Неделя рисуется правильно.** Проверил `_week_text` на `ДП-26`:
расписание, преподаватели, звонки и обед на месте, порядок пар верный.
Дефекта нет.

**Снимки создаются по расписанию.** Проверил время:

```
2026-10-20: 2026-10-23 21:26:04 .. 21:26:06
2026-10-21: 2026-10-23 21:26:02 .. 2026-10-24 11:53:08
2026-10-22: 2026-10-23 21:25:59 .. 2026-10-24 11:53:05
2026-10-23: 2026-10-24 00:21:47 .. 11:53:02
2026-10-24: 2026-10-25 00:10:08 .. 00:10:13
```

Работает как задумано: каждый день досоздаёт пропущенное за три дня
назад.

**`replace_date` не удаляет прошлое.** Проверил: единственный
`delete(CollegeLesson)` в проекте — по одной дате
(`college_lesson.py:42`). Никакого `purge` нет. Значит 20-22 октября
не удаляли — их просто никогда не материализовали.

**Материализация идёт только вперёд — это осознанно.** Комментарий в
`poller.py:113` объясняет: окно должно сдвигаться, иначе через две
недели расписание «кончится». Назад писать не нужно, для прошлого есть
архив. Логика верная, не хватает чтения.

## Риски

- **Снимок не содержит `changed`/`action`.** Проверил формат `payload`:
  `{para, subject, teacher, room}` — только четыре поля. Значит по
  архиву нельзя показать, была ли пара заменена или отменена. Для
  «истории» это приемлемо (что было — то было), но надо решить
  осознанно.
- **Слияние дат может показать день, где в архиве пусто** (снимок не
  создался из-за `if not slots: continue`). Тогда «Занятий нет» —
  честно.
