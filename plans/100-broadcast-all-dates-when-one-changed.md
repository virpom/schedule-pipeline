# План 100: рассылка шлёт 15 дат, когда изменился один день

> **СДЕЛАНО 26.10.2026** (коммит `81161fe`). Добавлен
> `CollegeLessonRepo.digest_by_date()`: отпечаток содержимого каждой
> даты. `poll_once` снимает его до и после материализации и рассылает
> только по датам, где отпечаток изменился. Тест —
> `test_digest_by_date_detects_only_changed_date` (мутация проверена:
> при подмене отпечатка на константу тест падает).
>
> Побочный эффект: `get_dates()` больше не нужен рассылке — отпечаток
> ловит и замены, и базовое расписание. Даты без замен тоже
> уведомляются, если там что-то поменялось (раньше выпадали).
>
> Замер на проде: 3927 строк, чтение 9.5 мс, два раза за цикл — 19 мс.

**Приоритет:** высокий. Это ровно то, что произошло 26.10 в 10:40:
студент получил 15 сообщений «Расписание изменилось», хотя изменилась
одна строка в файле.

**Трудоёмкость:** M (~20 строк).

## Что произошло

Живой инцидент на проде. Пользователь получил подряд:

```
10:40  🔄 Расписание изменилось · Четверг, 29 октября · 3 пары
10:41  🔄 Расписание изменилось · Понедельник, 26 октября · Занятий нет 🙌
10:42  🔄 Расписание изменилось · Вторник, 27 октября · 4 пары
       🔄 Расписание изменилось · Среда, 28 октября · 4 пары
```

Он написал: «хотя вроде ничего не изменилось».

## Разбор

### Что реально изменилось

`last_sync_ok = 2026-10-26T10:40:21`. В этот момент хэш файла очного
расписания не совпал с сохранённым:

```
eios_hash_ochoe   f57d998d1c7ff736d8a7...
```

`_sync_ochoe` (`sync_eios.py:286`) переписал `base_lesson` — сейчас там
**2659** строк. Разница с прошлым состоянием — одна строка.

### Как это превратилось в 15 дат

`poll_once` (`poller.py:124`):

```python
college_changed = result is not None and (result["ochoe"] or result["zameny"])
if not college_changed and not vuz_changed:
    return changes

dates = set(await repo.substitutions.get_dates(today))

if (result and result["ochoe"]) or vuz_changed:
    dates |= {today + datetime.timedelta(days=i) for i in range(3)}
```

Две причины широкого охвата:

1. **`dates` — это ВСЕ даты замен начиная с сегодня.** Проверил
   `substitutions.get_dates(today)` — на проде это 15 дат:
   ```
   10-26, 10-27, 10-29, 10-30, 10-31,
   11-02, 11-03, 11-05, 11-06, 11-07,
   11-09, 11-14, 11-18, 11-19, 12-10
   ```
   Даже если изменилась одна строка базового расписания, рассылка идёт
   по всем ним.

2. **`dates |= {today, today+1, today+2}`** добавляет три дня, не
   проверяя, изменилось ли в них что-нибудь.

### Почему «ничего не изменилось» — правда

Проверил `ДП-26` на даты из сообщений — они совпадают с тем, что
пришло:

```
27.10: Деловая культура / Систематизация / Архивное дело / БЖД
28.10: Организация документооборота / История России / Физкультура / Основы делопроизводства
29.10: Деловая культура / Систематизация / Архивное дело
26.10: 0 пар
```

А `26.10 — Занятий нет` — **честно**: у `ДП-26` в `base_lesson` нет ни
одной пары на понедельник (`weekday=1` → 0 строк). Понедельник у них
пустой по учебному плану.

То есть сообщения не врали по содержанию, но **все были не нужны**:
изменение касалось не этих дней.

## Что сделать

Сравнивать не «файл изменился», а **что именно изменилось в
материализованном слое**.

`materialize` уже пересобирает `college_lesson` каждый цикл. Дешевле
всего — запомнить снимок и сравнить:

```python
async def poll_once(...):
    ...
    # до материализации
    before = await repo.college_lessons.snapshot_digest()   # {(date, group): hash}

    await sync_eios.materialize(repo)

    # после
    after = await repo.college_lessons.snapshot_digest()
    changed_dates = {d for (d, g), h in after.items()
                     if before.get((d, g)) != h}
```

Тогда рассылка идёт только по реально изменившимся датам, и
`result["ochoe"]` перестаёт быть триггером для всех подряд.

**Более дешёвый вариант** (если снимок дорог): сверять хэш **на дату**.
`college_lesson` уже материализован — можно считать
`sha256` от отсортированных строк за дату и хранить в `setting`
(как уже делается для файлов). 14 дней × 129 групп — но хэш по дате,
а не по группе, это 14 записей.

**Совсем дешёвый** (минимальная правка): убрать `dates |=
{today, today+1, today+2}` для случая, когда изменились **только
замены** (`result["zameny"]`), и оставить его только при
`result["ochoe"]`. Это сократит шум вдвое, но не уберёт главную
причину — `get_dates` всё равно вернёт 15 дат.

## Что это не починит

**Изменившаяся строка может быть у группы, которой нет среди
получателей.** В этом случае после правки не будет отправлено вообще
ничего — и это правильно: кому нужно, те увидят при следующем заходе.

**`had_lessons == 0 and date == today`** (`poller.py:145`) — флаг
«новое расписание». Он ставится один раз за всё время жизни бота
(первый запуск). Проверять не надо.

## Проверено и признано корректным

**Данные в базе верные.** После инцидента проверил:
`base_lesson` 2659, `college_lesson` 3927 (все `source='site'`),
`substitution` 247. Материализация прошла, расписание на месте.

**Рассылка не дублирует сообщения.** `notify_new_schedule` идёт по
`sorted(changes)`, каждому подписчику — по одному сообщению на дату.
Дублей в рамках одного цикла нет.

**Ночное окно не при чём.** `_in_night` для 10:40 возвращает `False`
(`night_start=23:00`, `night_end=07:00`) — проверено ранее на 12
краевых случаях.

**`get_dates` возвращает все даты намеренно.** Docstring
`substitution.py:58` говорит, что это сделано для рассылки: «листок
выдаётся сразу на несколько дней». Проблема не в нём, а в том, что
`poll_once` не сужает список по факту изменения.

## Риски

- **Снимок на каждый цикл — это 129 × 14 запросов.** Дорого. Лучше
  хэш по дате, но и он требует чтения всех строк за день.
- **Пропустить изменение.** Если хэш считается по материализованному
  слою, а слой пересобирается из тех же слоёв, хэш изменится только
  при реальном изменении данных — ложных пропусков быть не должно. Но
  если `materialize` начнёт писать `created_at`/`updated_at`, хэш
  будет меняться каждый цикл и рассылка вернётся к прежнему шуму.
