# План 050: тревога админу теряется, если отправка не удалась

**Приоритет:** средний. Ломается ровно тогда, когда нужна больше
всего — при недоставке.

**Трудоёмкость:** S (~8 строк).

## Проблема

`alerts.py:36` — сначала коммит, потом отправка:

```python
async def alert(bot, repo, config, kind, text):
    key = ALERT_KEY.format(kind=kind)
    digest = hashlib.sha256(text.encode()).hexdigest()
    if await repo.settings.get(key) == digest:
        return  # об этом уже сообщили, не спамим

    await repo.settings.set(key, digest)      # <- КОММИТ
    await _send(bot, config, f"⚠️ ...")       # <- ОТПРАВКА
```

`settings.set` внутри делает `commit()` (`repo/setting.py:37`). То есть
хеш записывается в базу **до** того, как сообщение ушло.

А `_send` глотает ошибку:

```python
async def _send(bot, config, text):
    for admin_id in config.tg_bot.admin_ids:
        try:
            await bot.send_message(admin_id, text)
        except TelegramAPIError as e:
            log.warning("не удалось отправить тревогу %s: %s", admin_id, e)
```

## Что происходит

1. Админ заблокировал бота (или сменил аккаунт, или у Telegram сбой).
2. `alert()` записывает `digest` в `setting`.
3. `_send()` падает, пишет `log.warning` и **возвращает управление
   нормально** — исключения нет.
4. Следующий цикл: текст тревоги тот же → `digest` совпадает →
   `return` на второй строке.
5. **Тревога не дойдёт никогда**, а система считает, что доложила.

Это тихая потеря на самом важном пути: админ не узнает, что структура
сайта сломалась, пока студенты не начнут жаловаться.

## То же в `clear`

```python
await repo.settings.set(key, "")          # <- коммит «сброшено»
await _send(bot, config, f"✅ Восстановилось")
```

Если отправка упала, админ не узнает о восстановлении. Но здесь
последствие мягче: следующий `alert` сработает заново, потому что ключ
пуст.

## Что сделать

Сначала отправить, потом записывать — и только если доставка удалась
хотя бы одному админу:

```python
async def _send(bot, config, text) -> bool:
    """True, если доставлено хотя бы одному админу."""
    delivered = False
    for admin_id in config.tg_bot.admin_ids:
        try:
            await bot.send_message(admin_id, text)
            delivered = True
        except TelegramAPIError as e:
            log.warning("не удалось отправить тревогу %s: %s", admin_id, e)
    return delivered


async def alert(bot, repo, config, kind, text):
    key = ALERT_KEY.format(kind=kind)
    digest = hashlib.sha256(text.encode()).hexdigest()
    if await repo.settings.get(key) == digest:
        return

    if await _send(bot, config, f"⚠️ <b>Проблема с расписанием</b>\n\n{text}"):
        # Запоминаем только доставленное: иначе неотправленная тревога
        # считалась бы сообщённой и больше не повторилась.
        await repo.settings.set(key, digest)
    log.warning("тревога админу (%s): %s", kind, text)
```

То же для `clear`, но с обратной логикой — очищать только при успехе:

```python
if await _send(bot, config, f"✅ <b>Восстановилось</b>\n\n{text}"):
    await repo.settings.set(key, "")
```

**Побочный эффект, который надо принять:** если админ заблокировал
бота, тревога будет пытаться отправиться каждый цикл (раз в 5 минут).
Это спам в лог, но не в Telegram — сообщение не уходит. Зато когда
админ разблокирует, тревога дойдёт. Это лучше тихой потери.

## Проверено и признано корректным

**Порядок `except` в `_send` правильный** — ловится `TelegramAPIError`,
базовый класс для всех ошибок Telegram, так что и `Forbidden`, и
`BadRequest` попадут сюда.

**Тесты покрывают дедупликацию, но не сбой отправки.** Прочитал
`test_alerts.py`: есть проверки «два одинаковых текста → одно
сообщение», «разные тексты → два», «разные kind → два», «два админа →
два сообщения», «длинный текст → хеш 64 символа». **Нет теста «отправка
упала → тревога повторится»**.

**Хеш, а не текст — правильно.** В `setting.value` 128 символов,
sha256 hex — ровно 64. Тест это проверяет.

**`clear` не отправляет, если тревоги не было** — проверка
`if not await repo.settings.get(key): return`. Разумно: не спамить
«восстановилось» без предшествующей проблемы.

**Механизм работал.** Проверил `setting` на проде — ключ
`alert_structure` есть, значение пустое:

```
('alert_structure', '', 0)
```

Пустое значение означает, что тревога когда-то поднималась
(`digest` записывался), а потом была снята через `clear`. То есть путь
«тревога → восстановление» прошёл целиком, и код в этой части рабочий.
Проблема только в случае **сбоя отправки**, которого пока не случалось.

## Побочно: мёртвый ключ `site_down`

В `setting` на проде лежит:

```
('site_down', '0')
```

Код его **не читает и не пишет** — проверил `grep` по всему проекту,
упоминание осталось только в докстроке `source_state.py:3`:

> Раньше здесь был один флаг ``site_down``, и он врал в двух местах

То есть флаг заменили на `last_sync_ok`, а строку в базе не убрали.
Безвредно, но при чтении `/stats` или отладке можно решить, что он
ещё что-то значит. Удалить вместе с `bell_notify` (план 047).

## Риски

- **При заблокированном боте лог будет расти** — одна строка на админа
  раз в 5 минут. За сутки 288 строк. Приемлемо, но стоит понизить до
  `log.debug` после первой неудачи или считать попытки.
- **`alert` может упасть между отправкой и записью.** Если `settings.set`
  бросит исключение после успешной отправки, тревога придёт дважды.
  Дубликат лучше потери — принимаю.
- **Правка меняет поведение при частичной доставке.** Если админов
  двое и одному дошло, `digest` запишется, и второму повтор не придёт.
  Это верно: факт тревоги зафиксирован.
