# План 135: `Slot` теряет `para_end` — спаренные пары схлопываются

> **УСТАРЕЛ 27.10.2026.** `Slot` имеет поле `para_end`, и оно
> заполняется. Проверено на проде: ПРф-25 на 28.10 отдаёт слот
> `para=3, para_end=4`, экран рисует «3–4)». В `college_lesson` таких
> строк 133, и все — **на будущие даты**, а не прошлые, как сказано в
> плане.

**Приоритет:** низкий. Сейчас в проде 27 таких строк, все — прошлые
даты. Но код `format_day` **умеет** их рисовать, а `Slot` не даёт.

**Трудоёмкость:** S (~5 строк).

## Проблема

В `college_lesson` есть колонка `para_end`
(`models/college_lesson.py:28`). Смысл: одна пара может занимать
**два номера подряд** — например, «п5-6 Техническая механика» вместо
двух отдельных пар.

`format_day` это учитывает (`common/schedule.py:234`):

```python
para_end = getattr(lesson, "para_end", None) or lesson.para
for p in range(lesson.para, para_end + 1):
    bs = bell.get((dt, cg, p)) or bell.get((dt, "I_IV", p))
    ...
```

То есть для строки `para=5, para_end=6` рисуются **две** строки
расписания — с разным временем звонков.

**А `Slot` этого поля не имеет:**

```python
class Slot:
    __slots__ = ("para", "subject", "teacher", "room", "changed", "action",
                 "comment", "group")
```

`__slots__` без `para_end` → `getattr(lesson, "para_end", None)` вернёт
`None` → диапазон схлопнется в одну пару.

## Проверил на живых данных

`ТЭф-25`, 02.10.2026 — в таблице есть `п5-6 Техническая механика`:

```
college_lesson:  п3-3 Иностранный язык
                 п4-4 Химико тех. процессы
                 п5-6 Техническая механика

get_day_slots:   п3 Теоретические основы теплотехники
                 п4 Химико-технологические процессы на тепло
                 п5 Техническая механика
```

Слой отдаёт **п5** вместо **п5-6**. Второй номер пары потерян.

## Почему сейчас не видно

Проверил распределение:

```
college_lesson: 3927 строк
  с para_end != para:  27
  из них будущих:       0
```

Все 27 — **прошлые даты** (02.10, 03.10 и т. д.). На будущее
материализация ставит `para_end = slot.para` (`sync_eios.py:388`),
то есть всегда одиночную пару.

Причина: парсер колледжа сейчас не порождает спаренных пар. В
`parsers/eios.py` нет разбора «п5-6» как диапазона. Старые строки —
следы более ранней версии парсера или ручных правок.

**У вуза этого поля нет вообще.** Проверил `vuz.Lesson`:

```
поля Lesson: ['date', 'group', 'para', 'parity', 'room',
              'subject', 'teacher', 'weekday', 'weeks']
```

Ни `para_end`, ни намёка. Значит VUZ-расписание спаренных пар не
содержит, и дефект его не касается.

## Достижимость в будущем

Три пути, которыми спаренные пары появятся снова:

1. **Парсер начнёт разбирать «п5-6»** из листка замен или xlsx
2. **Староста вручную** поставит пару на два номера — редактор сейчас
   такого не умеет, но поле в схеме есть
3. **`_merge_para_clash`** (`sync_eios.py:315`) склеивает пары при
   конфликте — проверил, `para_end` там не ставится

Пока ни один не активен. Но поле в схеме, рендер в `format_day` и
поддержка в `bell.py` (`:51`, `:63`, `:73`) — всё готово. Не хватает
только передачи через `Slot`.

## Что сделать

Добавить поле в `Slot`:

```python
__slots__ = ("para", "para_end", "subject", "teacher", "room", "changed",
             "action", "comment", "group")

def __init__(self, para: int, subject: str, teacher: str = "", room: str = "",
             changed: bool = False, action: str = "", comment: str = "",
             group: str = "", para_end: int = 0):
    ...
    self.para_end = para_end or para
```

И заполнять его в `get_day_slots` из `base_lesson` — но там его нет.
Значит правильнее: `get_day_slots` не может знать `para_end`, потому
что он собирает из `base_lesson`, где колонки нет.

**Вывод: правильное место — не `Slot`, а путь `college_lesson` →
`format_day`.** А он уже работает: `_hist_page` (`user.py:765`) и
рассылка читают `college_lesson` напрямую и получают настоящий
`para_end`. Ломается только путь через слой.

Значит вопрос не «добавить поле», а **«нужен ли `para_end` в слое
вообще»**. Если парсер его не порождает — нет. Если начнёт —
понадобится колонка в `base_lesson` и `substitution`, а их нет.

**Минимальное действие:** либо добавить `para_end` в `base_lesson`
(миграция), либо признать, что спаренные пары в слое не поддерживаются,
и убрать `para_end` из `format_day`, чтобы не создавать иллюзию.

## Что проверил и признал корректным

**`comment` не теряется — проверил все 74.** `Slot.comment` заполняется
из `substitution.comment`, но ни `format_day`, ни `notify_edits` его
не рендерят. Сначала решил, что это потеря. Проверил: `comment` — это
исходная строка листка замен вида
`«Метрология – Куранова Е.И., ауд. 223»`, и она **полностью
дублирует** уже разобранные поля:

```
всего замен с comment: 74
расхождений с subject/teacher/room: 0
```

Ничего уникального в `comment` нет. Рендерить его не нужно.

**VUZ-данные в `college_lesson` целы.** Заметил, что 1855 из 3927 строк
помечены `source='site'`, хотя относятся к группам `@vuz`. Проверил,
к чему это ведёт: `materialize_day` (`sync_eios.py:392`) ставит
`SOURCE_SITE` всем группам без разбора, а сохранение ручных правок
(`:364`, `:427`) фильтрует по `source != SOURCE_SITE`. Раз VUZ-строки
тоже `site`, они попадают в пересборку — но собираются из того же
`get_day_slots`, поэтому результат тот же. Проверил живьём:

```
АП-23оз@vuz 2026-10-27: слой=2, college_lesson=2, совпадает=True
```

Избыточно, но не ломает. Помечать VUZ-строки отдельным `source` стоит
ради ясности, но это не дефект.

**`bell.py` поддерживает `para_end`** — проверил `:51`, `:63`, `:73`.
Напоминания о звонках на спаренные пары работают, если такие появятся.

## Риски

- **Добавление `para_end` в `Slot` без источника данных** создаст поле,
  которое всегда равно `para`. Это хуже, чем отсутствие поля: читатель
  будет думать, что диапазоны поддержаны.
- **Удаление `para_end` из `format_day`** сломает историю: `_hist_page`
  читает `college_lesson` напрямую, и там 27 старых строк с диапазоном
  отрисовались бы верно. Их немного, но они настоящие.
