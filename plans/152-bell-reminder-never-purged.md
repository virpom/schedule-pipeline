# План 152: `bell_reminder` не чистится — 60% строк мёртвые

> **СДЕЛАНО 27.10.2026** (коммит `6321b89`).
>
> `delete_before` в репозитории, вызов в `_tick` при смене даты.
> Строго `<`, не `<=` — иначе перезапуск в течение дня дал бы
> повторные звонки.
>
> На проде перед правкой было 456 строк за 06–27.10, то есть больше
> половины мёртвых.

**Приоритет:** низкий. Работает, запросы не деградируют (индекс есть).
Но таблица растёт линейно и никогда не освобождается.

**Трудоёмкость:** S (~10 строк).

## Проблема

`BellReminderRepo` (`repo/bell_reminder.py`) содержит **ровно два
метода**:

```python
async def is_sent(self, user_id, date, event_key) -> bool: ...
async def mark_sent(self, user_id, date, event_key) -> None: ...
```

Ни очистки, ни удаления по дате, ни ограничения по возрасту. Запись
появляется один раз на `(user_id, date, event_key)` и остаётся навсегда.

## Данные на проде

```
bell_reminder: 295 строк
  2026-10-06:   7   <- прошлое
  2026-10-07:  29   <- прошлое
  2026-10-08:  72   <- прошлое
  2026-10-24:  68   <- прошлое
  2026-10-26: 119   <- сегодня
```

**176 из 295 — прошлые (60%).** Они не нужны ни для чего: `is_sent`
проверяет только сегодняшнюю дату, а вчерашние события повториться не
могут.

## Рост

Считаю по факту: 295 строк за три недели работы, из них 119 за один
день. При такой нагрузке:

```
~120 строк/день
~44 000 строк/год
~220 000 строк/5 лет
```

Сейчас база 2.1 MB. Через год прибавится несколько мегабайт — не
катастрофа, но и пользы ноль.

## Почему это не срочно

**Запросы не деградируют.** Проверил индексы:

```
ix_bell_reminder_date     ON bell_reminder (date)
ix_bell_reminder_user_id  ON bell_reminder (user_id)
sqlite_autoindex_bell_reminder_1  UNIQUE (user_id, date, event_key)
```

`is_sent` фильтрует по всем трём полям уникального индекса — попадание
точное.

**Замер:** `is_sent` = **0.62 мс**. `_tick` звонков на 16 подписчиках
делает ~160 вызовов → **99 мс** на тик при лимите 30 с. Запас 300×.

То есть даже с 220 000 строк время не изменится: индекс растёт
логарифмически.

## Что сделать

Удалять строки старше суток — в `_tick` звонков или отдельным шагом в
поллере (он и так ходит раз в 5 минут):

```python
async def delete_before(self, date: datetime.date) -> int:
    result = await self.session.execute(
        delete(BellReminder).where(BellReminder.date < date)
    )
    await self.session.commit()
    return result.rowcount
```

и вызывать раз в сутки, например при смене даты в `_tick`.

**Важно:** удалять только `date < today`, не `<=`. Иначе при
перезапуске в течение дня человек получит повторные звонки.

## Что проверил и признал корректным

**`on_conflict_do_nothing` работает.** Проверил: дублей
`(user_id, date, event_key)` в базе **0**, уникальный индекс держит.

**`is_sent` корректно фильтрует.** Проверил запрос: все три поля из
уникального индекса, `limit(1)` — читает не больше одной строки.

**План 048 рост уже отмечал**, но как наблюдение, а не как проблему
(«растёт и читается нормально»). Отдельного плана на очистку не было.

**Данные не теряются при перезапуске.** `mark_sent` коммитит сразу,
поэтому после рестарта бот не шлёт повторно — проверено планом 109.

## Риски

- **Удаление при смене даты** — если бот перезапустится ночью, очистка
  может не сработать до первого тика. Не критично: старые строки
  просто полежат ещё день.
- **Часовой пояс.** `date` в `bell_reminder` — локальная дата
  (`TZ=Asia/Krasnoyarsk`). Сравнивать надо с `datetime.date.today()`,
  а не с UTC, иначе удалится сегодняшнее.
