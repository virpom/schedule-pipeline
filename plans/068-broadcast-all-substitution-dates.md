# План 068: рассылка уходит по всем датам замен, а не по изменившимся

> **СДЕЛАНО 26.10.2026** (коммит `81161fe`). Закрыт вместе с планом 100.
> `poll_once` снимает `digest_by_date()` до и после материализации и
> рассылает только по датам, у которых отпечаток изменился.
>
> Выбран вариант **лучше предложенного здесь**: в разделе «Что сделать»
> предлагалось вернуть `zameny_dates` из `sync_once` и предупреждалось,
> что «разница множеств не поймает изменение существующей даты». Отпечаток
> ловит и появление, и правку — и для замен, и для базового расписания.
>
> `get_dates()` рассылке больше не нужен (метод остался — его использует
> тест и он безвреден).
>
> Замер: 3927 строк, 9.5 мс на чтение, 19 мс за цикл.

**Приоритет:** высокий. Каждый новый листок замен шлёт полное расписание
на две недели вперёд всем подписчикам.

**Трудоёмкость:** S (~10 строк).

## Проблема

`poller.py:53` — `poll_once` решает, по каким датам рассылать:

```python
async with session_pool() as db:
    repo = RequestsRepo(db)
    dates = set(await repo.substitutions.get_dates(today))

if (result and result["ochoe"]) or vuz_changed:
    dates |= {today + datetime.timedelta(days=i) for i in range(3)}

for date in sorted(dates):
    changes.append((date, had_lessons == 0 and date == today))
```

`get_dates` возвращает **все** даты, на которые есть замены:

```python
async def get_dates(self, since: datetime.date) -> list[datetime.date]:
    """Даты, на которые есть замены, начиная с указанной.

    Нужно для рассылки: листок замен выдаётся сразу на несколько дней
    вперёд (например, на субботу и понедельник), и уведомлять надо про
    каждую из этих дат, а не про фиксированное окно «сегодня + 2 дня».
    """
```

Комментарий объясняет, зачем это было сделано — и это верно для
**первого** листка. Но метод не знает, какие замены пришли **в этом
синке**, а какие лежат с прошлой недели.

### Откуда взялось

Проверил историю — это **намеренный фикс**, а не недосмотр. Коммит
`318819f` «fix(poller): уведомления про замены на все даты из листка»:

> Критический баг: рассылка брала фиксированное окно «сегодня + 2 дня».
> Листок замен выдаётся сразу на несколько дат (например, суббота и
> понедельник), и замена на понедельник, пришедшая в пятницу, в окно не
> попадала — студент о ней не узнавал.

Задача была настоящая, и фикс её решает. Побочный эффект — старые
будущие даты тоже попадают в выборку — остался незамеченным.

### Почему тесты это не поймали

К фиксу добавлены два теста. Первый проверяет, что суббота и
понедельник обе попадают в рассылку. Второй — что прошедшие даты **не**
попадают:

```python
def test_substitution_dates_skip_past(tmp_path):
    """Прошедшие даты не попадают в рассылку."""
    past = today - dt.timedelta(days=5)
    future = today + dt.timedelta(days=2)
    ...
    assert past not in dates
    assert future in dates
```

Прошедшие отфильтрованы, будущие старые — нет. Теста на «замена
двухнедельной давности, ещё не наступившая» не существует. Это ровно
тот случай, который и создаёт спам.

## Что происходит на проде

Измерил прямо сейчас (26.10.2026):

```

Значит один проход с обновлённым листком порождает:

```

При этом новый листок был **только на 26.10** — остальные 14 дат

Из 15 будущих дат листок в конкретный день обычно трогает 1–3.

при любом обновлении файла, независимо от того, что в нём изменилось.

## Почему это не проявилось в отписках

Проверил: подписано 224, отписано 7. Всего 3% — эффекта почти нет.

Причина: листки приходят редко, а рассылка идёт **только когда файл
реально изменился**:

```python
college_changed = result is not None and (result["ochoe"] or result["zameny"])
if not college_changed and not vuz_changed:
    return changes
```

То есть 3360 сообщений уходит не каждый час, а раз в несколько дней.
Но когда уходит — это стена.

## Второе последствие: поллер стоит 3 минуты

Рассылка синхронная и с паузами. `broadcaster.py:75`:

```python
delay = 1.0 / max(rate, 0.1)
sent = 0
for user_id, text, photo in items:
    ...
    await asyncio.sleep(delay)
```

При `notify_rate = 20` (значение по умолчанию из
`repo/setting.py:10`) пауза 50 мс. На 3360 сообщений:

```
3360 × 0.05 = 168 секунд
```

И всё это время `poller_loop` **не опрашивает сайт**:

```python
changes = await poll_once(bot, session_pool, config)
if changes:
    await notify_new_schedule(...)   # 168 секунд
last_poll = time.monotonic()
```

`poll_interval = 300`, так что цикл занимает 168 из 300 секунд — больше
половины. Если кто-то снизит `notify_rate` до 5 (разумно для фото),
рассылка займёт 672 секунды, и синхронизация встанет на 11 минут.

Телеграм-бот при этом работает (`dp.start_polling` и `bell_loop` —
отдельные задачи), так что люди не заметят. Но расписание перестанет
обновляться на это время.

## Что сделать

Брать только даты, которые **появились или изменились в этом проходе**.
`sync_once` уже знает, что обновилось, — надо прокинуть это наружу.

Минимальный вариант: сравнить набор дат до и после синхронизации.

```python
# в poll_once, до sync_eios.sync_once
async with session_pool() as db:
    repo = RequestsRepo(db)
    dates_before = set(await repo.substitutions.get_dates(today))

result = await sync_eios.sync_once(session, repo, config)

# после
async with session_pool() as db:
    repo = RequestsRepo(db)
    dates_after = set(await repo.substitutions.get_dates(today))

# Рассылаем только новые даты: старые уже разосланы, когда появились.
dates = dates_after - dates_before
```

Но этого мало: если листок на существующую дату **изменился** (было
2 замены, стало 5), дата не попадёт в разницу, и люди не узнают.
Нужен признак «на эту дату замены менялись».

Лучше — вернуть из `sync_once` список затронутых дат. Функция уже
разбирает замены и знает их даты:

```python
subs = await asyncio.to_thread(eios.parse_substitutions, data)
...
count = await replace_substitutions(repo, subs)
changed["zameny"] = True
changed["zameny_dates"] = sorted({s.date for s in subs})   # <- добавить
```

Тогда в `poll_once`:

```python
dates = set(result.get("zameny_dates") or [])
```

Окно «сегодня + 3» при смене базового расписания оставить как есть —
там логика верная.

## Что уже работает и трогать не надо

- **Значок замены виден.** `format_day` рисует `SUB_MARK` у изменённых
  пар и зачёркивает отменённые:

  ```python
  mark = f" {SUB_MARK}" if getattr(lesson, "changed", False) else ""
  ```

  Так что человек, получивший сообщение, поймёт, что именно поменялось.

- **Рассылка не идёт без изменений.** Проверка `if not college_changed
  and not vuz_changed: return` стоит до формирования списка — при
  неизменном файле сообщений нет.

- **Материализация идёт всегда**, даже без изменений (окно дат должно
  сдвигаться). Это правильно и к рассылке не относится.

## Проверено и признано НЕ проблемой

Пока разбирал рассылку, проверил три подозрения — все оказались
корректными.

**Отмена пары, которой нет в базовом расписании.** На проде нашёлся
ровно один такой случай:

```
ДОУ-24, 26.10, пара 1: action='cancel'
base_lesson ДОУ-24 пн: пары 2, 3, 4 (первой нет)
```

`get_day_slots` в `schedule_layer.py` обрабатывает отмену только внутри
цикла по базовым парам, а второй цикл берёт лишь `add`/`replace`:

```python
for para, sub in sorted(sub_by_para.items()):
    if sub.action in ("add", "replace") and para not in used:
```

То есть отмена пары 1 молча пропускается. **Но результат верный:**
отменять нечего — показывать нечего. Студент видит зачёркнутыми пары
2, 3, 4, и это полная картина дня. Листок замен — дельта, а не полный
день, поэтому «отменить пару, которой нет» — нормальный способ сказать
«в этот день пар нет».

**57 замен против 56 `changed=1`** на 26.10 — то же самое расхождение,
объясняется одним случаем выше.

**Замены на далёкие даты** (`2026-11-14`, `2026-11-18`, `2026-11-19`,
`2026-12-10`) не попадают в `college_lesson`, потому что материализация
идёт на 14 дней вперёд (`MATERIALIZE_DAYS = 14`). Это ожидаемо: окно
катится, и когда дата приблизится, замена применится.

## Риски

- **Правка существующей даты.** Если ограничиться разницей множеств,
  изменение листка на уже известную дату не разошлётся. Поэтому
  правильный вариант — `zameny_dates` из `sync_once`, а не разница.
- **Ручные замены.** `replace_substitutions` их не трогает (фильтр по
  `source != SOURCE_SITE`). Значит даты с ручными заменами в
  `zameny_dates` не попадут — и не должны: староста уведомляет сам
  через `notify_group_about_edit`.
- **Первый запуск после деплоя.** Если `dates_before` пуст, разница
  даст все даты — это правильно, первый раз надо разослать всё.
- **Рассылка блокирует поллер.** Даже после исправления стоит подумать
  о фоне: сейчас `notify_new_schedule` ждётся в цикле. При 224
  подписчиках и 3 датах это 34 секунды — терпимо. Но при росте числа
  пользователей или снижении `notify_rate` синхронизация начнёт
  отставать. Вынести в `asyncio.create_task` — отдельная задача, не
  часть этого плана.
