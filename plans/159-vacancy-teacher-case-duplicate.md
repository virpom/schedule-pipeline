# План 159: «Вакансия» и «вакансия» — два разных преподавателя

> **СДЕЛАНО 28.10.2026.** План описывал состояние ДО коммита ecefae0 (план 097): дубля в списке нет. Реальный дефект — в карточке пары печаталось «вакансия» со строчной. Правка в clean_teacher. Коммит e6ef26c.

**Приоритет:** низкий. Ничего не ломает, но в списке преподавателей
две строки вместо одной, и они дают разные наборы пар.

**Трудоёмкость:** S (~3 строки).

## Что нашёл

В проде, `college_lesson`:

```
'Вакансия' : 54 пары
'вакансия' :  8 пар
```

В `base_lesson` то же самое:

```
'Вакансия' : 25
'вакансия' :  4
```

Два разных значения там, где по смыслу одно: «преподаватель не
назначен».

## Откуда берётся

`parsers/eios.py:55-58` — регулярка распознавания преподавателя:

```python
_TEACHER_RE = re.compile(
    rf"^(?:{_NAME}(?:\s*[–-]\s*{_NAME})?\s+[А-ЯЁ]\.\s*[А-ЯЁ]?\.*"
    rf"|{_NAME}\s+{_NAME}"
    rf"|[Вв]акансия)$"
)
```

Последняя ветка `[Вв]акансия` покрывает **оба написания** — и
«Вакансия», и «вакансия». То есть регулярка работает правильно:
обе строки распознаются как преподаватель.

Проблема в том, что дальше значение **не нормализуется**.
`clean_teacher:178-196` приводит к единому виду только ФИО с
инициалами:

```python
m = re.match(r"^(.+?)\s+([А-ЯЁ])\.?\s*([А-ЯЁ])?\.*$", name)
if m:
    ...
return name          # <- вакансия уходит как есть
```

Строка «вакансия» не подходит под шаблон ФИО и возвращается
дословно.

## Что видит студент

**1. В карточке пары** — `format_day` (`common/schedule.py:264`):

```python
m = " · ".join(x for x in (lesson.teacher, lesson.room) if x)
```

Для 8 пар в `college_lesson` вторая строка будет «вакансия» со
строчной буквы. Остальные 54 покажут «Вакансия». Выглядит как
опечатка в расписании.

**2. В поиске по преподавателю** — `_teacher_letter_kb`
(`user.py:311-320`):

```python
picked = [n for n in names if n[:1].upper() == letter.upper()]
```

`"В".upper() == "В"` и `"в".upper() == "В"` — обе строки попадут под
одну букву. Проверил, как это выглядит в реальном списке из 234
уникальных преподавателей:

```
[31]  'Вакансия'
[233] 'вакансия'
```

**На разных концах списка.** Первая — почти в начале, вторая —
последняя. Студент, ищущий по букве «В», видит две записи, и не может
понять, чем они отличаются.

**3. Наборы пар разные.** Выбор «Вакансия» покажет 54 пары, выбор
«вакансия» — 8. Это не дубликат, а **разные данные**.

## Почему LIKE не спасает

`get_for_teacher_date` (`college_lesson.py:166`) фильтрует через
`LIKE`:

```sql
teacher LIKE '%Вакансия%'   -> 54
teacher LIKE '%вакансия%'   ->  8
teacher LIKE '%ВАНСИЯ%'     ->  0
```

`LIKE` в SQLite регистрозависим для кириллицы (приводит регистр только
для ASCII). Значит исправить на уровне запроса нельзя — надо
нормализовать при записи.

## Что сделать

**Нормализовать в `clean_teacher`:**

```python
def clean_teacher(name: str) -> str:
    name = re.sub(r"\s+", " ", (name or "")).strip()
    if not name:
        return ""
    if name.lower() == "вакансия":
        return "Вакансия"
    ...
```

Это чинит новые данные. Старые 8 строк в `college_lesson` и 4 в
`base_lesson` останутся, пока не пройдёт следующая синхронизация:
`replace_base_lessons` перезаписывает `source='site'` целиком, а
`college_lesson` материализуется заново.

**Проверить, что перезапись действительно произойдёт.** `base_lesson`
с `source='site'` удаляется и вставляется заново при каждом изменении
хэша файла (`sync_eios.py:78`). `college_lesson` пересобирается
`materialize_day` на 14 дней вперёд. Значит 4 строки в `base_lesson`
исчезнут при следующем обновлении файла, а 8 в `college_lesson` — при
следующей материализации этих дат.

**Если нужно починить немедленно** — разовая миграция:

```sql
UPDATE base_lesson   SET teacher='Вакансия' WHERE teacher='вакансия';
UPDATE college_lesson SET teacher='Вакансия' WHERE teacher='вакансия';
```

## Проверено и признал корректным

**Регулярка распознаёт оба варианта.** `[Вв]акансия` намеренно
покрывает оба написания — это не баг парсера, а следствие того, что
источник пишет по-разному.

**`ВАКАНСИЯ` заглавными не распознаётся** (`[Вв]` не покрывает `В`
заглавную в начале при остальных заглавных — на самом деле покрывает,
но `_TEACHER_RE` требует ровно «акансия» строчными после). Проверил:
`_TEACHER_RE.match("ВАКАНСИЯ")` → `False`. В живом файле такого
написания нет, поэтому не дефект.

**Ячеек с последней строкой без инициалов, но похожей на ФИО** — 0.
Проверил все 4 листа живого файла: ложных срабатываний `_TEACHER_RE`
нет.

**25 + 4 = 29 в `base_lesson` и 54 + 8 = 62 в `college_lesson`** —
числа согласуются: материализация размножает базовые пары на даты.

## Риски

- **Нормализация в `clean_teacher`** затронет только разбор колледжа.
  Вуз (`parsers/vuz.py`) вакансий не содержит — там преподаватель либо
  есть, либо пустая строка.
- **Разовая SQL-правка** должна идти после остановки синхронизации,
  иначе следующий прогон вернёт старое значение из файла. Впрочем,
  после правки `clean_teacher` он вернёт уже нормализованное.
