# План 093: отмена пары, которой нет в базе, исчезает молча

> **ПОДТВЕРЖДЕНО НА ЖИВЫХ ДАННЫХ 27.10.2026.** Заголовок раньше
> утверждал «на проде не случалось (0 из 22 отмен)» — это уже не так.
> Проверил заново: отмен 22, из них **1 без базы** —
> `ДОУ-24`, 26.10.2026, пара 1.
>
> Что было в листке замен:
> ```
> п1 cancel comment='НЕТ ПАРЫ'
> п2 cancel comment='НЕТ ПАРЫ'
> п3 cancel comment='НЕТ ПАРЫ'
> п4 cancel comment='НЕТ ПАРЫ'
> ```
> В базе `ДОУ-24` по понедельникам есть только п2, п3, п4 — пары 1
> там нет вовсе.
>
> В `college_lesson` на 26.10 попало три строки с `action='cancel'`
> (п2, п3, п4). Пары 1 нет.
>
> Воспроизвёл экран студента (`format_day`, живая БД):
> ```
> 📅 Понедельник, 26 октября
>
> 09:00–09:20  Разговоры о важном 🇷🇺
> 2) 11:10–11:55 / 12:00–12:45  Организация и нормативно-правовые...  ❌ отменено
> 3) 13:15–14:00 / 14:05–14:50  Методика и практика архивоведения      ❌ отменено
> 4) 15:00–15:45 / 15:50–16:35  Информационные технологии...           ❌ отменено
> ```
> Нумерация начинается с «2)». Студент видит дыру и не знает, была ли
> там пара и отменили её или её никогда не было. Это ровно тот дефект,
> который план описывает, — только он уже случился.

**Приоритет:** низкий по частоте (1 случай из 247 замен), но случай
живой, а не гипотетический. Дальше будет повторяться: вуз/колледж
ставит «НЕТ ПАРЫ» и на те слоты, где пары не было.

**Трудоёмкость:** S (~6 строк).

## Проблема

`get_day_slots` (`schedule_layer.py:70`) обрабатывает отмену только для
пар, которые **есть в базовом расписании**:

```python
for lesson in base:
    sub = sub_by_para.get(lesson.para)
    used.add(lesson.para)
    if sub and sub.action == SUB_CANCEL:
        slots.append(Slot(lesson.para, lesson.subject, lesson.teacher,
                          lesson.room, changed=True, action=SUB_CANCEL,
                          group=group))
        continue
```

А «добавки» — отдельным циклом, где `cancel` в список **не входит**:

```python
for para, sub in sorted(sub_by_para.items()):
    if sub.action in ("add", "replace") and para not in used:
        slots.append(Slot(para, sub.subject, ...))
```

Значит `substitution` с `action='cancel'` на пару, которой нет в
`base_lesson`, **не создаёт слот вообще** — ни отменённого, ни какого.

## Как сюда попасть

Путь открыт через редактор:

1. Староста открывает день, пара 3 в базе **отсутствует**.
   `cb_sub_slot`: `base_slot=None`, `has_sub=False`.
   `sub_actions_kb` показывает только «➕ Добавить пару».
2. Жмёт «➕ Добавить», вводит предмет → `substitutions.set(..., "add", ...)`.
   `get_day_slots` создаёт слот (второй цикл ловит `add`).
3. Возвращается на экран пары 3: `has_sub=True` → появляется
   «❌ Отменить пару».
4. Жмёт отмену → `substitutions.set(..., SUB_CANCEL, ...)`.
   `get_day_slots`: первого цикла нет (базы нет), второй цикл `cancel`
   не ловит → **слота нет**.

Студент видит «Занятий нет 🙌» — ровно противоположное тому, что
староста пытался сообщить.

## На проде

```
отмен без базовой пары: 0
всего отмен: 22, у всех база есть
```

Не срабатывало. Но механизм готов, а «поставить пару на пустое
место» — штатный сценарий для вуза (перенос на субботу, разовая
консультация). Проверил, сколько замен стоит на парах, которых нет в
`base_lesson`:

```
add      2
replace  17
-----------
        19
```

Все доходят до студента — второй цикл `get_day_slots` их ловит. То
есть шаг 2 делается регулярно, а шаг 4 пока не делали ни разу.

То есть шаг 2 делается регулярно. Шаг 4 пока не делали ни разу.

## Что сделать

Дать отмене тот же путь, что и добавке — показывать её как слот:

```python
for para, sub in sorted(sub_by_para.items()):
    if para in used:
        continue
    if sub.action in ("add", "replace"):
        slots.append(Slot(para, sub.subject, sub.teacher, sub.room,
                          changed=True, action=sub.action, comment=sub.comment,
                          group=group))
    elif sub.action == SUB_CANCEL:
        # отменять нечего — пары и так нет; показывать нечего
        pass
```

**Но это ничего не меняет.** Если пары нет, «отменить» её бессмысленно:
показывать нечего. Правильнее — **не предлагать** отмену там, где
отменять нечего, то есть в `sub_actions_kb`:

```python
if has_sub and (base_slot or <замена не cancel-и-уже-невидима>):
    rows.append(... "❌ Отменить пару" ...)
```

Точнее: кнопку «❌ Отменить» показывать, только если есть что отменять —
базовая пара **или** замена `add`/`replace`:

```python
cancellable = base_slot is not None or (sub and sub.action in ("add", "replace"))
```

Это честнее: отмена без базы и без замены — операция ни над чем.

## Проверено и признано корректным

**Замена на пару без базы работает.** Второй цикл `get_day_slots`
создаёт слот для `add`/`replace`, даже если пары нет в `base_lesson` —
комментарий объясняет: «У вуза такие часты: перенос на субботу, разовая
консультация. Раньше учитывался только `action='add'`, и такая замена
молча пропадала». Проверил на проде: 12 таких замен, все доходят до
студента.

**Отмена без базы и без замены недоступна.** Если `base_slot=None` и
`has_sub=False`, кнопки «❌ Отменить» нет — проверил
`sub_actions_kb`. Защита есть, просто неполная.

**`cb_sub_cancel` сам по себе не проверяет базу.** Он просто пишет
`cancel` в `substitution` — и это правильно: слой замен не обязан
знать про базовое расписание. Проблема в том, что читатель
(`get_day_slots`) такие записи игнорирует.

**Пара 6–8 — отдельный дефект.** `sub_slots_kb` перебирает
`range(1, 6)`, так что до пар 6–8 редактор вообще не добирается — это
[план 042](042-vuz-editor-para-range.md), не дублирую.

## Риски

- **Скрыть кнопку — не починить данные.** Если в БД уже есть `cancel`
  без базы, он останется невидимым. На проде таких нет, но стоит
  добавить проверку при чтении: логировать, если встретился
  `cancel` без слота.
- **Правка `sub_actions_kb` меняет UX.** Староста, привыкший, что
  «Отменить» есть всегда при наличии замены, не найдёт кнопку. Но
  кнопка, которая молча ничего не делает, хуже.
