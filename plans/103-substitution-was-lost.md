# План 103: при замене теряется, что было раньше

> **СДЕЛАНО 28.10.2026** (коммиты `f982257`, `e4ebf1b`). `comment` теперь хранит «было» из листка замен, `format_day` печатает строку только когда «было» действительно отличается: на проде таких 2 из 29, остальные 27 перенесли ту же пару на другую дату.

**Приоритет:** средний. Студент видит новую пару, но не знает, что она
заменила. Для «перенесли предмет» это не важно, для «сменился
преподаватель» — важно.

**Трудоёмкость:** M (~20 строк + миграция).

## Проблема

Листок замен устроен как «было → стало». Парсер читает обе колонки:

```python
group, para_text, was, now = cells[0], cells[1], cells[2], cells[3]
...
result.append(Substitution(
    ...,
    was=was,
    raw_now=now,
))
```

`raw_now` сохраняется в `Substitution.comment`. **`was` не сохраняется
никуда** — в модели `infrastructure/database/models/substitution.py`
поля `was` нет:

```python
date, group, para, action, subject, teacher, room, comment, source, ...
```

## Что теряется

Проверил на реальном листке с прода. Колонка «было» содержит фамилию
**прежнего преподавателя**:

```
ТЭк-26, пара 4
  БЫЛО:  «Обществознание – Кекеева К.А.»
  СТАЛО: «Биология – Утева О.В., ауд. 202»
```

Распределение значений «было» (топ):

```
35  'НЕТ'                                    <- новая пара (add)
 3  'Иностранный язык – Суворова Э.В.'
 3  'ИГ – Кузьмина С.М.'
 2  'Трудовое право – Никифоров А.Н.'
 2  'Общая энергетика – Городиский В.В.'
...
```

Для `add` (`было = НЕТ`) терять нечего. Для `replace` — теряется
предмет и преподаватель, которые стояли до замены.

## Что видит студент сейчас

Собрал `Slot` с заменой и прогнал через `format_day`:

```
📅 Понедельник, 26 октября

4) 15:00–15:20  Биология 🔄
Утева О.В. · ауд. 202
```

Студент видит новую пару со значком 🔄. Он **не видит**, что раньше
здесь была «Обществознание / Кекеева К.А.».

При этом `comment` доходит до `Slot` — `schedule_layer.py:83` передаёт
его, `Slot.comment` хранит, — но **`format_day` его не выводит**.
Проверил `common/schedule.py` поиском по `comment` — совпадений нет.

То есть в базе лежит текст «Биология – Утева О.В., ауд. 202», который
никогда не показывается. Мёртвый груз.

## Когда это больно

**Сменился преподаватель.** Студент знает, что «ИГ – Кузьмина С.М.»
была в понедельник. Приходит «ИГ – Иванова Н.А. 🔄» — непонятно, это
та же пара с другим человеком или её вообще убрали.

**Перенесли на другую пару.** В листке стоит «2-3 пара: ИГ – Кузьмина».
Пара переехала, а студент видит две пары вместо одной.

**Отменили, но в базе её не было.** `cancel` с `was='НЕТ'` — заменять
нечего, но и показать нечего.

## Что сделать

**Шаг 1 — сохранять `was`.** Добавить колонку и миграцию:

```python
was: Mapped[str] = mapped_column(String(256), default="")
```

```python
op.add_column("substitution", sa.Column("was", sa.String(256),
                                        nullable=False, server_default=""))
```

Писать при `replace_substitutions`:

```python
was=(sub.was or "")[:256],
```

**Шаг 2 — показывать.** В `format_day` для замены добавлять строку,
если `was` непусто и не `НЕТ`:

```python
if getattr(lesson, "action", "") == SUB_REPLACE and getattr(lesson, "was", ""):
    was = lesson.was
    if was.upper().strip() != "НЕТ":
        lines.append(f"   <i>было: {was}</i>")
```

**Экранирования нет — и это отдельный вопрос.** Проверил
`common/schedule.py`: `html.escape` не импортирован, ни одного вызова.
Данные подставляются в HTML-текст как есть. Сейчас это безопасно —
проверил все пять текстовых колонок в проде:

```
college_lesson.subject   0 строк с < > &
college_lesson.teacher   0
base_lesson.subject      0
substitution.subject     0
substitution.comment     0
```

Символов разметки нет ни в одном поле. Но источник — xlsx и docx от
внешней организации, и если однажды в названии предмета появится `<`,
Telegram ответит `BadRequest: can't parse entities`, и день не
отрисуется целиком. Для новой строки «было» риск тот же, поэтому
экранировать стоит сразу — `from html import escape`, и в `format_day`
пропустить через него `subject`, `teacher`, `room`, `comment`.
Это выходит за рамки плана, но связано с ним.

**Или проще — в `comment`.** Если не хочется миграции, можно писать
`comment=f"{was} → {now}"` и выводить `comment` целиком. Но тогда
теряется разделение «что было» / «что стало» и ломается поиск.

## Проверено и признано корректным

**`parity` из заголовка тоже теряется — но он не нужен.** Парсер
читает «нечетная неделя» из заголовка (`eios.py:392`) и кладёт в
`Substitution.parity`, которого нет в модели. Сверил на реальном
листке:

```
2026-10-24  из файла=EVEN  вычислено=EVEN  OK
2026-10-26  из файла=ODD   вычислено=ODD   OK
```

Совпадает, потому что замена привязана к **дате**, а чётность из даты
выводится однозначно: `week_parity(date, PARITY_OFFSET)`. Поле
избыточно, терять нечего.

**`raw_now` сохраняется и доходит до `Slot`.** Проверил цепочку:
`parse_substitutions` → `replace_substitutions(comment=...)` →
`get_day_slots(comment=sub.comment)` → `Slot.comment`. Обрыв только на
выводе.

**`comment` заполнен у 96 замен из 247.** Остальные 151 — замены вуза
(`sync_vuz`), они кладут своё. Не регресс.

## Риски

- **Миграция на живой базе.** 247 строк, `server_default=""` — безопасно.
- **Студент не должен видеть лишнего.** «Было: Обществознание – Кекеева
  К.А.» удлиняет каждую строку дня. На дне из 7 пар это +7 строк. У
  `format_day` уже есть проблема длины (1633 символа у `ГИ-24@vuz` при
  лимите 4096), так что запас есть, но стоит показывать только при
  `replace`, не при `cancel`.
- **Преподаватель «было» может быть уволен.** Показывать фамилию
  бывшего сотрудника — нормально для расписания, но стоит подумать,
  не лучше ли только предмет.
