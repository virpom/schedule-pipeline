# План 106: опечатка «06.11.20226» превращается в замену на 2022 год

> **СДЕЛАНО 28.10.2026** (коммит `e6379ff`). `DATE_RE` ограничен
> четырьмя цифрами с `(?![0-9])`. На фикстуре было две замены
> 2022 года, стало ноль.

**Приоритет:** низкий по последствиям, но дефект настоящий: парсер
молча создаёт запись с датой на четыре года в прошлом, и она лежит в
базе навсегда.

**Трудоёмкость:** S (~3 строки + тест).

## Что в источнике

В файле вуза `1-ochnoe.xls`, лист «ФЭЭиУ 1 курс», ячейка `(60, 3)`:

```
ч.  Основы корпоративной культуры и деловое общение (лек)
    Самойлова Л.П.  06.11.20226. - перенос на 18.11.2026
```

Методист напечатал `06.11.2022` и приписал `6.` — то есть хотел
`06.11.2026`. Опечатка в одном символе.

## Что делает парсер

`parsers/vuz.py:70`:

```python
DATE_RE = re.compile(r"(\d{1,2})\.(\d{1,2})(?:\.(\d{2,4}))?")
```

`\d{2,4}` — **жадный**: он забирает максимум цифр. На строке
`06.11.20226.` получается:

```
совпадение: '06.11.2022'   день=06 месяц=11 год=2022
```

Хвостовая `6` остаётся за совпадением и теряется. `parse_date`
(`vuz.py:249`) берёт **первое** совпадение:

```python
for m in DATE_RE.finditer(text):
    ...
    return datetime.date(y, month, day)
```

Итог — дата `2022-11-06` вместо `2026-11-06`.

## Что это даёт в базе

Проверил прод 26.10.2026:

```
substitution: 247 записей
  min(date) = 2022-11-06   <- аномалия
  max(date) = 2026-12-10
  дат вне 2026 года: 1 (две записи)
```

Две записи, обе `action='replace'`, обе на пару 3:

```
2022-11-06  ЭК-26-1@vuz  п3  «Основы корпоративной культуры…»  Самойлова Л.П.
2022-11-06  МН-26@vuz     п3  «Основы корпоративной культуры…»  Самойлова Л.П.
```

**В `college_lesson` они не попали** — проверил, `date='2022-11-06'` даёт
0 строк. Окно материализации 14 дней, 2022 год в него не входит.
То есть студенты ничего не видят, данные просто лежат мусором.

**Но при этом теряется настоящая замена.** В той же ячейке написано
«перенос на 18.11.2026» — это второе совпадение `18.11.2026`, и оно
**не разбирается вообще**: `parse_date` возвращает первое и выходит из
цикла. Значит перенос пары на 18.11 студенты не увидят.

## Что сделать

Не давать году уходить в прошлое. Дата замены не может быть раньше
начала учебного года, который парсер уже знает из шапки (`_year`,
`vuz.py:419`).

```python
def parse_date(text: str, year: int) -> datetime.date | None:
    for m in DATE_RE.finditer(text):
        day, month = int(m.group(1)), int(m.group(2))
        y = int(m.group(3)) if m.group(3) else year
        if y < 100:
            y += 2000
        # Опечатка вида «06.11.20226»: жадный \d{2,4} съедает «2022».
        # Дата замены не бывает раньше учебного года из шапки.
        if y < year:
            y = year
        try:
            return datetime.date(y, month, day)
        except ValueError:
            continue
    return None
```

Три строки. **Проверил на живом коде:**

```
без фикса: 2022-11-06
с фиксом:  2026-11-06

обычные даты не сломались:
  '18.11.2026'  -> 2026-11-18
  '09.11'       -> 2026-11-09
  '09.11.26'    -> 2026-11-09
  '30.10.2026'  -> 2026-10-30
```

**Второе — не терять «перенос на 18.11.2026».** Это отдельный дефект:
ячейка содержит две даты, а парсер читает одну. `MOVE_RE` ловит слово
«перенос», но `parse_date` уже вернул первое совпадение. Стоит вернуть
все даты и создать по замене на каждую — но это меняет сигнатуру
`parse_date`, поэтому отдельным шагом.

## Проверено и признано корректным

**`parse_date` правильно разбирает обычные даты.** Проверил на
`18.11.2026` из той же ячейки — вернул бы `2026-11-18`. Проблема
только в опечатке с лишней цифрой.

**Год по умолчанию берётся из шапки, а не из `today()`.** `_year`
(`vuz.py:409`) ищет «2026-2027» в первых 10 строках и возвращает 2026.
Только если шапки нет — падает на `datetime.date.today().year`. Это
правильно: разбор файла не должен зависеть от даты запуска.

**`anchor_fit` такую дату не ломает.** Он считает попадания только по
заменам, у которых группа есть в расписании. Для `2022-11-06`
`vuz_week` даёт `-199`, попадания нет — одна неудача из сотни, порог
`anchor_looks_off` (меньше половины) не срабатывает.

**`college_lesson` чист.** Проверил: `date='2022-11-06'` — 0 строк.
Окно 14 дней от 26.10 не достаёт до 2022.

**У вуза своя нумерация недель — не путать.** `vuz_week`
(`sync_vuz.py:65`) считает от якоря `2026-08-31` и для дат до якоря даёт
0 или отрицательное. Это не дефект сам по себе (якорь первый день
семестра), но защита от прошлогодних дат полезна и здесь.

## Риски

- **Подъём года может исказить настоящую прошлогоднюю дату.** Если в
  файле осмысленно стоит `06.11.2025` (например, для сравнения), парсер
  сделает из неё 2026. Но расписание на 2026/2027 не содержит дат
  прошлых лет — проверено на всех восьми файлах: «2022» встречается
  ровно один раз, и это опечатка.
- **Опечатка может быть и в месяце.** `06.13.2026` даст `ValueError` и
  уйдёт в `continue` — это уже обработано, дата просто пропадёт.
