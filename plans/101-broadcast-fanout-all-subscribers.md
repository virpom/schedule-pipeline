# План 101: изменение у одной группы уходит всем 228 подписчикам

**Приоритет:** высокий. Продолжение плана 068/100. Тот фикс сократил
рассылку в 15 раз (с дат), но не тронул второй множитель — получателей.

**Трудоёмкость:** M (~25 строк).

## Проблема

`notify_new_schedule` (`poller.py:147`) рассылает по **всем**
подписчикам независимо от того, чья группа изменилась:

```python
for date, is_new in sorted(changes, key=lambda x: x[0]):
    for user in subscribers:                    # <- ВСЕ 228
        if user.role == "teacher" and user.teacher_name:
            lessons = await repo.college_lessons.get_for_teacher_date(...)
        else:
            lessons = await repo.college_lessons.get_for_group_date(user.group, date)
        ...
        items.append((user.id, prefix + text, photo))
```

`prefix` — «🔄 Расписание изменилось». Он один на всех: и для группы,
где правда поменялось, и для 227 групп, где ничего не трогали.

## Сколько это сообщений

Проверил на проде: **228 подписчиков в 31 группе**.

```
сценарий A: изменилась одна группа (ДП-26) на один день
  1 дата × 228 = 228 сообщений
  полезных: 12 (подписчики ДП-26)
  мусорных: 216 (94.7%)

сценарий B: изменился весь день (10–20 групп)
  1 дата × 228 = 228 сообщений
  полезных: ~150
  мусорных: ~78 (34%)
```

Топ групп по подписчикам: `СМк-25` 26, `ЮР-25Б` 19, `ТЭк-26` 19,
`ЭОф-24` 17, `ЭОк-26` 15.

**До фикса `81161fe`** было 15 дат × 228 = **3420** сообщений.
Стало 228. Прогресс в 15 раз, но 94.7% всё ещё мусор в обычном
сценарии.

## Почему это хуже, чем «лишние сообщения»

**Человек отвыкает читать.** 216 сообщений в месяц «расписание
изменилось» про дни, где у него ничего не менялось, — это обучение
игнорировать уведомления. Когда придёт настоящее (его пару
перенесли), он его пропустит.

**Лимит Telegram.** 228 сообщений при `notify_rate=20` — это 11.4
секунды. Не критично, но каждый раз.

**Поллер стоит.** `broadcast_schedule` синхронный:

```python
for user_id, text, photo in items:
    await send_message(...)
    await asyncio.sleep(1.0 / rate)
```

При `poll_interval=300` рассылка на 228 сообщений занимает 11 секунд —
нормально. Но если когда-нибудь `notify_rate` снизят до 5 (разумно для
фото), это 46 секунд.

## Что сделать

`poll_once` уже знает изменившиеся даты. Нужно знать ещё и группы.
`digest_by_date` считает отпечаток **по дате** — расширить до
**пары (дата, группа)**:

```python
async def digest_by_date(self) -> dict[datetime.date, str]:
    ...
```

в

```python
async def digest_by_slot(self) -> dict[tuple[datetime.date, str], str]:
    """Отпечаток по каждой паре (дата, группа)."""
    result = await self.session.execute(
        select(CollegeLesson).order_by(
            CollegeLesson.date, CollegeLesson.group, CollegeLesson.para)
    )
    buckets: dict[tuple, list] = {}
    for row in result.scalars().all():
        buckets.setdefault((row.date, row.group), []).append(
            (row.para, row.subject, row.teacher, row.room,
             row.changed, row.action))
    return {
        key: hashlib.sha256(repr(rows).encode()).hexdigest()
        for key, rows in buckets.items()
    }
```

В `poll_once` вернуть не просто даты, а `(date, groups)`:

```python
changes.append((date, is_new, changed_groups))
```

`notify_new_schedule`:

```python
for date, is_new, groups in sorted(changes, key=lambda x: x[0]):
    for user in subscribers:
        # Студенту — только если его группа затронута.
        if user.role != "teacher" and user.group not in groups:
            continue
        ...
```

### Преподаватели — отдельное правило

Их пара может быть в любой группе, а `teacher_name` не связан с
`group`. Правило «затронута ли группа» к ним не применимо.

Проверил на проде — преподавателей среди подписчиков **трое**:

```
6602662332  teacher_name=None            <- тот самый «выбрал роль, не выбрал себя»
1039429314  Молчанова Н.А.
1037099659  Боровик И.А.
```

У двух есть пары: `Молчанова Н.А.` — по 1 в день, `Боровик И.А.` — 2–3.

Считать затронутость по `teacher` в изменившихся слотах:

```python
changed_teachers = {
    row.teacher
    for (d, g) in changed_pairs
    for row in after[(d, g)]
    if row.teacher
}
if user.role == "teacher" and not any(
        teacher_matches(t, user.teacher_name) for t in changed_teachers):
    continue
```

**Проверил главный риск: пару у преподавателя убрали — он в `after`
останется?** Да. `get_day_slots` при отмене **не выкидывает** слот, а
помечает его:

```python
if sub and sub.action == SUB_CANCEL:
    result.append(Slot(lesson.para, lesson.subject, lesson.teacher,
                       lesson.room, changed=True, action=SUB_CANCEL, group=group))
    continue
```

`teacher` берётся из базовой пары, поэтому отменённая строка остаётся в
`college_lesson` с фамилией. Измерил на проде: **19 отменённых пар, у
всех 19 `teacher` заполнен**:

```
ДОУ-24  26.10  пара 2  Горпинченко Е.В.  cancel
ПРк-25  26.10  пара 1  Кузьмина С.М.     cancel
ПСО-23  26.10  пара 1  Киреева П.А.      cancel
...
```

Значит преподаватель увидит и «пару добавили», и «пару отменили».

**Второе исключение — `replace` с пустым `teacher`.** При замене
`get_day_slots` берёт фамилию из замены, а не из базовой пары:

```python
if sub and sub.action in ("replace", "add"):
    slots.append(Slot(lesson.para, sub.subject, sub.teacher, sub.room, ...))
```

Если в листке замены фамилию не указали, пара теряет владельца.
Измерил: **1 такой `replace` из 190**, и он безобиден:

```
2026-10-16  ИП-24@vuz  пара 2  replace
«с 10.00-12.00 Защита результатов производственной практики»  teacher=''
```

Это дата в прошлом (вне окна 14 дней) и мероприятие без
преподавателя. В `college_lesson` таких строк **0**.

**Третье исключение — пара удалена из базового расписания совсем**
(не отменена, а убрана из файла). Тогда строка исчезает из `after`, и
её владелец уведомления не получит. На проде таких случаев в текущем
окне нет; риск признаю, но он редок и не хуже текущего поведения
(сейчас уведомление получают все, включая тех, у кого ничего не
менялось).

## Обратная совместимость

**Сигнатура `changes` меняется** — `list[tuple[date, bool]]` →
`list[tuple[date, bool, set[str]]]`. Проверил все использования:

```
poller.py:252       poller_loop         -> notify_new_schedule(changes)
admin.py:643        cb_notify_confirm   -> notify_new_schedule(..., [(latest, True)], ...)
test_poller_vuz.py  форму changes не проверяет
```

**Второй потребитель — админская рассылка, и его надо не сломать.**
`cb_notify_confirm` (`admin.py:633`) запускает рассылку вручную из
панели:

```python
latest = await repo.college_lessons.get_latest_date()
_spawn(notify_new_schedule(cb.message.bot, session_pool, [(latest, True)],
                           rate, config.photos_path))
```

Здесь `changed_groups` **неизвестен** — админ шлёт «всё расписание»,
а не «что изменилось». Если фильтр «только затронутые группы» применить
наивно, `groups` будет пустым, и **админская рассылка не уйдёт никому**,
при этом ответит «Рассылка запущена».

Поэтому:

```python
# changes: list[tuple[date, is_new, groups | None]]
# groups is None -> слать всем (ручная рассылка, первый запуск)
for date, is_new, groups in sorted(changes, key=lambda x: x[0]):
    for user in subscribers:
        if groups is not None and user.role != "teacher" \
                and user.group not in groups:
            continue
```

`admin.py:643` тогда правится на `[(latest, True, None)]` — одна строка,
и поведение сохраняется.

## Что это не починит

**Первый запуск.** `had_lessons == 0 and date == today` — флаг «новое
расписание». Тогда `changed_groups` пуст (сравнивать не с чем), и
условие «группа затронута» отсечёт всех. Нужно: если `before` пуст —
слать всем (как сейчас).

**Чат группы** (`for chat in chats`) — у него свой `group`, фильтровать
по нему.

План реализован в тот же день, когда сработал второй раз. Что

  уходит всем — там неизвестно, что менялось.

## Удалить уже отправленное нельзя

Проверил все восемь таблиц прода на колонку с `message_id`:

```
users            -
chats            -
bell_reminder    -
day_snapshot     -
schedule_edit    -
college_lesson   -
substitution     -
setting          -
```

**Нигде не хранится.** `broadcast_schedule` отправляет сообщение и
выбрасывает ответ Telegram, в котором приходит `message_id`. Без него
удалить нельзя: метод `deleteMessage` требует `chat_id` **и**
`message_id`, а узнать id уже отправленного сообщения задним числом
через Bot API невозможно.

Что можно сделать сейчас — руками в клиенте Telegram: открыть чат с
ботом и удалить сообщения. У кого-то их 14 подряд.

Что стоит сделать на будущее — сохранять `message_id` при рассылке,
чтобы следующие ошибочные пачки можно было отозвать. Это отдельный
план, но он требует колонки в БД и обработки «сообщение старше 48
часов» (Bot API не даёт удалять старше).

## Риски

- **Пропустить уведомление.** Если человек сменил группу между циклами,
  его старая группа в `before`, новая — в `after`, и он получит
  уведомление про новую (правильно) и не получит про старую (тоже
  правильно).
- **Замены на будущее.** Дата 12-10 может быть в `after`, но не в
  `before` (окно материализации 14 дней). Тогда `changed_groups` — все
  группы этой даты, и рассылка уйдёт всем в этих группах. Это
  правильное поведение: дата только что появилась.
