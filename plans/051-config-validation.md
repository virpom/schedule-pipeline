# План 051: конфиг не проверяется при старте — три тихих отказа

> **СДЕЛАНО 27.10.2026** (коммит `9df8ea4`). Отметка стояла в
> `plans/README.md`, но не в файле плана.

**Приоритет:** низкий. На проде всё в порядке, но каждый из трёх
сценариев даёт отказ без единой ошибки в логе.

**Трудоёмкость:** S (~15 строк).

## Отказ 1: пустой `ADMINS` — бот без управления

`config.py:33`:

```python
def _ids(name: str) -> list[int]:
    return [int(x) for x in (os.environ.get(name) or "").replace(",", " ").split()]
```

Проверил все варианты:

```
ADMINS=''         -> []          <- тихо
ADMINS='123'      -> [123]
ADMINS='123,456'  -> [123, 456]
ADMINS='  '       -> []          <- тихо
ADMINS='123,abc'  -> ValueError  <- хотя бы падает
```

При пустом значении получается пустой список, и дальше:

- `_is_admin` (`admin.py:60`) — `user.id in []` всегда `False`:
  **никто не может открыть `/stats`, `/broadcast`, `/setpoll`**;
- `alerts._send` — `for admin_id in []` не выполняется ни разу:
  **тревоги уходят в никуда, без записи в лог**.

Бот при этом работает, студенты получают расписание, и **никто не
узнает, что админ-функции мертвы**.

## Отказ 2: отсутствие `BOT_TOKEN` — голый traceback

`config.py:56`:

```python
token=os.environ["BOT_TOKEN"],
```

Проверил:

```
KeyError: 'BOT_TOKEN'
```

В докере это выглядит как оборванный старт с `KeyError` в конце
стектрейса. Понятного «не задан токен бота» нет. Мелочь, но при
развёртывании на новом сервере время на диагностику уходит зря.

## Отказ 3: три мёртвых ключа в `.env`

На проде `.env` содержит (проверил имена, значения не выводил):

```
BOT_TOKEN, ADMINS, SQLITE_PATH, SCHEDULE_URL,
BASE_URL, POLL_INTERVAL, NOTIFY_RATE
```

А `load_config` читает только:

```python
BOT_TOKEN, ADMINS, SQLITE_PATH, SCHEDULE_URL, PHOTOS_PATH
```

| ключ в `.env` | читается? | что реально работает |
|---|---|---|
| `POLL_INTERVAL` | **нет** | `DEFAULTS["poll_interval"]="300"`, меняется `/setpoll` |
| `NOTIFY_RATE` | **нет** | `DEFAULTS["notify_rate"]="20"`, меняется `/setrate` |
| `BASE_URL` | **нет** | захардкожен в `parsers/vuz.py:39` |

Последствия: админ правит `.env`, перезапускает контейнер, **ничего не
меняется**. Причём `BASE_URL` — самый неприятный: если вуз сменит
домен, правка `.env` не поможет, нужен коммит и деплой.

Комментарий в самом `.env` это косвенно признаёт:

```
# --- Опрос сайта (стартовое значение; дальше живёт в БД, команда /setpoll) ---
POLL_INTERVAL=...
```

«Стартовое значение» — но оно нигде не читается, даже как стартовое.

## Что сделать

**Часть 1 — проверка на старте.** Одна функция в `config.py`:

```python
def _require(name: str) -> str:
    value = (os.environ.get(name) or "").strip()
    if not value:
        raise SystemExit(f"Не задана переменная окружения {name}. "
                         f"Проверь .env или --env-file.")
    return value
```

И в `load_config`:

```python
token=_require("BOT_TOKEN"),
admin_ids=_ids("ADMINS"),
```

Плюс отдельная проверка:

```python
if not admin_ids:
    raise SystemExit("ADMINS пуст: некому слать тревоги и некому управлять ботом.")
```

`SystemExit` вместо `KeyError` — потому что `main.py:71` ловит
`(KeyboardInterrupt, SystemExit)` и печатает «Bot is stopped!» вместо
стектрейса.

**Часть 2 — убрать мёртвые ключи или начать их читать.** Два варианта:

*Вариант А (проще):* удалить `POLL_INTERVAL`, `NOTIFY_RATE`,
`BASE_URL` из `.env` и из `.env.example`, чтобы не вводить в
заблуждение.

*Вариант Б (если настраиваемость нужна):* сделать их стартовыми
значениями:

```python
@dataclass
class Config:
    ...
    poll_interval: int
    notify_rate: float
    vuz_base_url: str
```

и при первом запуске (когда в `setting` пусто) писать их в базу.
Тогда комментарий в `.env` станет правдой.

Рекомендую **А**: `/setpoll` и `/setrate` уже есть, дублировать
настройку через файл — лишний источник расхождений. А `BASE_URL`
лучше не выносить в конфиг, а оставить в коде: он меняется раз в
несколько лет вместе с парсером.

## Проверено и признано корректным

**`_read_env` не перетирает уже заданные переменные** — использует
`os.environ.setdefault`. Правильно: в докере значения приходят через
`--env-file`, и файла внутри может не быть.

**Отсутствие `.env` не ошибка** — `except FileNotFoundError: pass`.
Так и задумано.

**Формат `.env` на проде чистый.** Проверил: нет строк с `export `,
нет inline-комментариев после значений. Значит парсер справляется.

**Но парсер хрупкий к форматам.** Прогнал крайние случаи:

```
export FOO=bar        -> None                     <- строка пропущена целиком
FOO=bar  # коммент    -> 'bar  # комментарий'     <- комментарий попал в значение
FOO="bar baz"         -> 'bar baz'                <- кавычки сняты, верно
FOO=                  -> ''                       <- пустая строка, не None
FOO = bar             -> 'bar'                    <- пробелы обрезаны, верно
FOO                   -> None                     <- без '=' пропущена, верно
```

Два дефекта: `export` не поддерживается (стандартная запись в
shell-совместимых `.env`), а inline-комментарий становится частью
значения. На проде не проявляется, но если кто-то отредактирует `.env`
привычным способом — получит загадочно неверный `SQLITE_PATH`.

Чинится двумя строками:

```python
line = line.removeprefix("export ").strip()
value = value.split(" #", 1)[0].strip().strip("\"'")
```

**`_int` и `_float` не используются вовсе** — проверил, ни одного
вызова. Мёртвый код вместе с `POLL_INTERVAL`/`NOTIFY_RATE`.

## Риски

- **`SystemExit` при пустом `ADMINS` сломает сценарий «бот без
  админов».** Сейчас такой режим технически возможен: студенты
  работают, тревоги не шлются. Если это кому-то нужно — проверку
  сделать предупреждением в лог, а не отказом.
- **Удаление ключей из `.env`** — правка файла с секретом. Делать
  аккуратно, не пересоздавая файл целиком, иначе токен потеряется.
- **Правка `_read_env` может сломать разбор значений с `#` внутри.**
  Например, пароль `p#ss` превратится в `p`. Резать только по `" #"`
  (пробел перед решёткой) — так и предложено.
