# План 119: анаграмма группы считается точным совпадением

> **СДЕЛАНО 28.10.2026** (коммит `2f9b945`). Признак — позиции цифр:
> «26ДП» перепутан по порядку, «ПД26» — другая группа.

**Приоритет:** низкий. На реальных данных коллизий нет, но критерий
неверный, а исход хуже, чем «не нашли».

**Трудоёмкость:** S (~2 строки).

## Проблема

`match_group` (`eios.py:577`) ищет группу по «грязному» имени из
листка замен. Третий шаг — нечёткая похожесть, и первое условие в ней:

```python
for other_key, original in by_key.items():
    if sorted(key) == sorted(other_key):
        score = 1.0                      # <- «точное совпадение»
    elif key in other_key or other_key in key:
        score = 0.9
    else:
        score = _similarity(key, other_key)
        if score < 0.75:
            continue
    candidates.append((score, original))
```

`sorted()` по строке — это **перестановка символов**, а не совпадение.
Номера групп отличаются цифрами, и цифры при сортировке теряют
позицию:

```
ДОУ-25  ->  normalize  ДОУ25  ->  sorted  ['2','5','Д','О','У']
ДОУ-52  ->  normalize  ДОУ52  ->  sorted  ['2','5','Д','О','У']
                                                   ^^^^^ одинаково
```

**`ДОУ-52` и `ДОУ-25` — анаграммы.** Первое условие даёт `score = 1.0`,
это максимальный балл, и группа находится «точно».

## Что это даёт

Проверил на живом коде:

```python
known = ['ДОУ-25', 'ЭОК-26', 'ЮР-25А']
match_group('ДОУ-52', known)  ->  'ДОУ-25'    # НЕВЕРНО
match_group('ДОУ-5',  known)  ->  'ДОУ-25'    # неверно, но хотя бы логично
match_group('ДОУ-2',  known)  ->  'ДОУ-25'    # неверно
```

Если в листке замен опечатка `ДОУ-52` вместо `ДОУ-25`, замена уйдёт
**второкурсникам вместо третьекурсников**.

## Почему это хуже, чем «не нашли»

`_resolve_groups` (`sync_eios.py:205`) при `None` **выбрасывает**
замену и пишет в лог:

```python
if name is None:
    if sub.group not in warned:
        log.warning("группа из листка замен не найдена: %r", sub.group)
    continue
```

Два исхода:

| Исход | Что происходит |
|---|---|
| `None` | Замена выброшена, в логе предупреждение. Студент видит базовое расписание. **Потеря заметная и безопасная** |
| Ложное совпадение | Замена записана **чужой группе**. Лога нет. Студент видит не свою замену. **Тихая порча данных** |

Второе хуже: никто не узнает, что что-то пошло не так.

## На реальных данных не воспроизводится

Проверил обе таблицы групп:

```
base_lesson:  129 групп, коллизий sorted(normalize) -> 0
vuz_group:     92 группы, коллизий -> 0
```

Ни одной пары-анаграммы. Дефект не сработал ни разу.

## Что сделать

Заменить критерий на сравнение с учётом позиций цифр. Достаточно
потребовать совпадения **цифровой части** отдельно:

```python
if sorted(key) == sorted(other_key) and re.sub(r"\D", "", key) == re.sub(r"\D", "", other_key):
    score = 1.0
```

Тогда `ДОУ25`/`ДОУ52` дадут разные цифровые части (`25` ≠ `52`) и
провалятся в `_similarity`, где наберут 0.80 — ниже порога 0.75? Нет,
выше. Значит всё равно попадут в кандидаты.

**Надёжнее — убрать первое условие вовсе.** Оно и так дублирует
`_similarity`: для настоящих опечаток `SequenceMatcher` даст высокий
балл, а цифры он учитывает позиционно.

**Проверил, что это не сломает реальные опечатки.** Единственная
подтверждённая опечатка в коде — `ЭОФ26 → ЭО-26ФП` — уже покрыта
таблицей `KNOWN_TYPOS` (`eios.py:558`), которая проверяется **до**
нечёткого поиска:

```python
KNOWN_TYPOS: dict[str, str] = {
    "ЭОФ26": "ЭО-26ФП",
}
```

Так что удаление `sorted()`-ветки на неё не влияет.

Замерил похожесть для случаев из комментария:

```
ЭОК26 vs ЭО26ФП  ->  0.73   (ниже порога 0.75)
ЭОФ26 vs ЭО26ФП  ->  0.73   (ниже порога — потому и нужна таблица)
ДОУ25 vs ДОУ52   ->  0.80   (выше порога — пройдёт как кандидат)
```

Первые два без `KNOWN_TYPOS` не распознались бы и сейчас — значит
эвристика на них не рассчитывает. Третье останется кандидатом с 0.80,
но **перестанет быть «точным»** и попадёт под проверку
неоднозначности.

```python
for other_key, original in by_key.items():
    if key in other_key or other_key in key:
        score = 0.9
    else:
        score = _similarity(key, other_key)
        if score < 0.75:
            continue
    candidates.append((score, original))
```

## Проверено и признано корректным

**Защита от неоднозначности работает.** После сбора кандидатов:

```python
if len(candidates) > 1 and abs(candidates[0][0] - candidates[1][0]) < 0.05:
    return None
```

Если два кандидата равны — не угадываем. Проверил: `match_group('ЮР-25В', known)`
возвращает `None`, потому что `ЮР-25А` и `ЮР-25Б` одинаково похожи.

**`KNOWN_TYPOS` — правильный подход.** Подтверждённые опечатки
чинятся таблицей, а не эвристикой. Это надёжнее любого сходства.

**`normalize_group` корректен.** Убирает пробелы и дефисы, приводит к
верхнему регистру — ровно то, что нужно для `ДОУ - 25` / `ДОУ-25`.

**`_similarity` использует `SequenceMatcher`** — позиционно-чувствительный,
в отличие от `sorted()`. Правильный инструмент.

## Риски

- **Удаление первого условия может ухудшить распознавание реальных
  опечаток.** Если в листке переставлены буквы (`ЭОК-26` вместо
  `ЭКО-26`), `sorted()` давал 1.0, а `SequenceMatcher` даст ~0.67 — ниже
  порога. Такие случаи надо вносить в `KNOWN_TYPOS`, а не ловить
  эвристикой.
- **Сегодня дефект не срабатывает.** Ценность правки — в том, что
  критерий неверен по смыслу, и при появлении группы-анаграммы бот
  начнёт тихо портить данные.
