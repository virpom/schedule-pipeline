# План 056: спаренные пары существуют только в старых данных

> **СДЕЛАНО 27.10.2026** (коммит `692aa75`), вариант Б.
>
> План предлагал вариант А (только почистить старые строки) или Б
> (провести `para_end` через цепочку). Выбрал Б: спаренность в
> источнике реальна — 23 случая из 704, проверено на живом файле.
> Вариант А оставил бы студента с двумя занятиями вместо одного.
>
> `Slot.para_end`, `_join_paired` в `get_day_slots`, честный
> `para_end` в `materialize`/`materialize_day`.
>
> Замены и отмены не склеиваются — у них своя семантика.

**Приоритет:** низкий. 27 строк из 3927 (0.7%), все на датах 18–24 дня
назад. На поведение не влияют, но показывают, что механизм `para_end`
не работает.

**Трудоёмкость:** S (~5 строк + чистка).

## Как обнаружено

Проверил распределение `para_end` в `college_lesson` на проде:

```
para_end != para: 27
para_end = para:  3900
```

Значит спаренные пары (2 пары подряд, одна запись) в базе есть.
Посмотрел примеры:

```
('2026-10-02', 'ТЭф-25', 5, 6, 'Техническая механика')
('2026-10-03', 'ДП-26', 1, 2, 'Организация документооборота')
('2026-10-03', 'ДП-26', 3, 4, 'БЖД')
```

Проверил источник — все 27 строк `source='site'`:

```
('site', 27)
```

А `source != 'site'` (ручные правки) — **0 строк**.

## Противоречие

`materialize_day` (`sync_eios.py:388`) для сайтовых строк пишет:

```python
"para_end": slot.para,
```

То есть **`para_end` всегда равен `para`** — спаренность теряется. А
`_merge_para_clash` (`sync_eios.py:315`) склеивает пары с одинаковым
номером и создаёт `Slot` без поля `para_end` вообще:

```python
seen[slot.para] = Slot(
    para=slot.para,
    subject=f"{prev.subject} / {slot.subject}"[:256],
    ...
)
```

`Slot` в `schedule_layer.py:17` объявлен с `__slots__ = ("para",
"subject", "teacher", "room", "changed", "action", "comment", "group")`
— `para_end` там нет.

Значит **ни один текущий код не может записать `para_end != para`**.
Откуда же 27 строк?

## Ответ: это старые данные

Проверил даты:

```
2026-10-02  (-24 дн)  2 строк
2026-10-03  (-23 дн)  9 строк
2026-10-05  (-21 дн)  1 строк
2026-10-06  (-20 дн)  4 строк
2026-10-07  (-19 дн)  2 строк
2026-10-08  (-18 дн)  9 строк
```

Все — в прошлом, 18–24 дня назад. Материализация идёт по окну
`MATERIALIZE_DAYS = 14` вперёд от сегодня, а `replace_date(date)`
перезаписывает только те даты, которые материализуются. Прошлые даты
не трогаются никогда.

То есть это остатки **старого парсера**, который писал `para_end`
по-настоящему. Современный код так не умеет.

## Последствия

**Для студентов — никаких.** `get_day_slots` и `format_day` читают
`para`, `para_end` используется только в `bell.py`:

```python
para_end = getattr(l, "para_end", None) or l.para
...
for p in range(l.para, para_end + 1):
```

Для 27 старых строк цикл пройдёт 2 итерации вместо 1 — то есть звонок
на 6-ю пару сработает для пары 5–6. Логика верная. Но эти даты в
прошлом, напоминаний на них уже не будет.

**Для отладки — мешает.** `para_end != para` выглядит как работающий
механизм, хотя его нет. Если кто-то решит, что спаренные пары
поддерживаются, и начнёт на них опираться — получит пустоту на новых
данных.

## Что сделать

**Вариант А (минимум):** ничего не чинить, только убрать мёртвые
строки и не создавать иллюзию.

```sql
DELETE FROM college_lesson
WHERE date < date('now', '-30 days');
```

Это заодно почистит все старые даты, которых накопилось **879 строк**
из 3927 (22% таблицы):

```
10-02..10-08: 567 строк (6 дней по 60–118)
10-23, 10-24: 312 строк
```

При окне материализации 14 дней вперёд эти даты не перезаписываются
никогда — они остаются навсегда, если не удалить вручную.

**Вариант Б (если спаренные пары нужны):** провести `para_end` через
всю цепочку:

1. добавить `para_end` в `Slot` (`schedule_layer.py:17`);
2. пробрасывать его в `get_day_slots` из `base_lesson` — но в
   `base_lesson` колонки `para_end` нет (проверил `pragma table_info`:
   `id, group, week_parity, weekday, para, subject, teacher, room,
   source, updated_by, updated_at, weeks`), значит нужна миграция;
3. `materialize_day` писать `slot.para_end`, а не `slot.para`;
4. `_merge_para_clash` сохранять `para_end` при склейке.

Это M-работа с миграцией. Судя по тому, что 27 строк появились давно и
никто не жаловался — **вариант А достаточно**.

## Проверено и признано корректным

**`_merge_para_clash` работает как задумано.** Комментарий в коде
объясняет: «У вуза бывает, что на одну пару приходятся два предмета:
физкультура идёт потоком все недели, а иностранный язык — по
подгруппам». Склейка через « / » — разумный компромисс при уникальном
ключе `(дата, группа, пара)`. В коде есть пометка о пределе:

```
ponytail: склейка теряет структуру (какой предмет чей). Если вуз
начнёт делить группы по подгруппам всерьёз — нужна колонка subgroup.
```

Честно задокументировано.

**Ручные правки сохраняют `para_end`** — ветка для `source != 'site'`
пишет `r.para_end`. Но редактор такого поля не выставляет (в
`_save_base` нет `para_end`), так что и там оно всегда равно `para`.

**`bell.py` использует `para_end` с защитой** —
`getattr(l, "para_end", None) or l.para`. Для `None` подставит `para`,
цикл не сломается.

**Замыкание `_cg` внутри цикла безопасно.** Написал проверку:

```python
for user in subscribers:
    is_teacher = ...
    own_cg = ...
    def _cg(group): ...      # объявлена внутри цикла
    cg = _cg(l.group)        # вызывается сразу, до следующей итерации
```

Late binding не срабатывает: переменные уже установлены, вызов
происходит в том же проходе. Функция пересоздаётся на каждого
подписчика (14 раз за тик, ~40 000 в сутки) — неэффективно, но
незаметно. Выносить наружу не обязательно.

## Риски

- **`DELETE FROM college_lesson WHERE date < ...`** удалит историю.
  `day_snapshot` её дублирует частично (403 строки на 20–24 октября),
  но не полностью. Если история нужна — сначала выгрузить.
- **Вариант Б требует миграции** `base_lesson.para_end` и правки
  парсера. Не начинать без явного запроса.
- **Правка не влияет на студентов** — все 27 строк в прошлом.
