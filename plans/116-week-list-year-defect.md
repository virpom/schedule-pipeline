# План 116: год в списке недель ломает разбор (не воспроизводится сейчас)

**Приоритет:** низкий. **На реальных файлах дефект не воспроизводится.**
Записан как защита на будущее: цена при срабатывании — пара исчезает
навсегда.

**Трудоёмкость:** S (~2 строки).

## Проблема

`parse_week_list` (`vuz.py:151`) обещает защиту от годов:

```python
m = re.match(r"^(\d+)\s*[-–]\s*(\d+)$", chunk)
if m:
    a, b = int(m.group(1)), int(m.group(2))
    if a <= b and b - a < 40:      # защита от «2026-2027»
        numbers.extend(range(a, b + 1))
    continue
```

Комментарий говорит «защита от 2026-2027», но условие `b - a < 40`
**пропускает** эту пару: `2027 - 2026 = 1`, что меньше 40. Проверил:

```
parse_week_list('2026-2027')  ->  (2026, 2027)
```

Защита сработала бы для `2026-2067` (`41`), но не для года учебного
года, который как раз и пишут.

## Второй путь, который тоже открыт

Регулярка `WEEK_LIST_RE` (`vuz.py:68`) захватывает `[\d\s,;\-–]+` —
цифры, пробелы, запятые, точки с запятой и тире. Год, приписанный
после списка недель, попадает в захват:

```
'№н. 5-13 2026'  ->  захват '5-13 2026'  ->  weeks ()
```

`parse_week_list` не разбирает `"5-13 2026"`: `re.split(r"[,;]")` даёт
один кусок, `^\d+$` не совпадает, `^(\d+)-(\d+)$` тоже (там пробел и
третье число). Возвращается пустой кортеж.

## Цена при срабатывании

Два разных исхода, оба плохие:

**`weeks = (2026, 2027)`** — `_parse_chunk` ставит `parity = PARITY_ANY`,
и `materialize` сверяет недели с `vuz_week(date, anchor)`. Номер недели
семестра никогда не будет 2026 или 2027. **Пара не покажется ни в один
день семестра.**

**`weeks = ()`** — `_parse_chunk` падает в ветку чётности
(`PARITY_ODD`/`PARITY_EVEN` по строке). Пара будет видна, но **через
неделю** вместо своих настоящих недель.

## Что проверил — дефект не воспроизводится

Скачал оба реальных файла вуза с сайта и прогнал по всем ячейкам:

```
full (644096 байт, 11 листов):  ячеек с «№» = 602, подозрительных = 0
part (317952 байт, 11 листов):  ячеек с «№» = 437, подозрительных = 0
```

**1039 ячеек, ни одного сбоя.** Формат `«№н. 5-13 2026»` в файле не
встречается: год стоит либо в шапке листа, либо не стоит вовсе.

## Что сделать

Две независимые правки, обе по строке.

**1. Отсечь годы в `parse_week_list`:**

```python
if a <= b and 1 <= a and b <= 60:      # недели бывают только 1..60
    numbers.extend(range(a, b + 1))
```

Это и есть настоящая защита. `b - a < 40` её не даёт: разница между
годами равна единице.

**2. Не давать регулярке захватывать год.** Либо сузить
`WEEK_LIST_RE`, либо отбрасывать числа больше 60 при разборе — второе
уже почти есть в ветке `^\d+$`:

```python
elif 1 <= n <= 60:
    numbers.append(n)
```

Но в диапазонной ветке проверки нет вовсе.

**Достаточно первой правки.** Если `a` и `b` вне 1..60 — диапазон
отбрасывается целиком, `weeks` остаётся пустым, и пара пойдёт по
чётности (мягкий исход) вместо «исчезнет навсегда».

## Проверено и признано корректным

**`parse_week_list` верно разбирает всё, что реально встречается:**

```
'5-13'          -> (5,6,7,8,9,10,11,12,13)
'5,7,9'         -> (5,7,9)
'5,7,9-13'      -> (5,7,9,10,11,12,13)
'5-13,15'       -> (5,6,7,8,9,10,11,12,13,15)
'6,8,10,1218'   -> (6,8,10,12,18)     <- опечатка в файле, обработана
'1-18'          -> все 18
''              -> ()
'0'             -> ()
```

**Опечатка `«6,8,10,1218»` обрабатывается специально** и с объяснением
в комментарии: число больше 60 при чётной длине разбивается на пары.
Это редко, но реально.

**`split_by_weeks` работает верно.** Проверил логику: делит ячейку
только если частей больше одной **и** в каждой есть свой список недель.
Иначе возвращает текст целиком — правильно, иначе «Страхование;
Юрченко» развалилось бы на два урока.

## Риски

- **Правка изменит поведение на граничных неделях.** Если в каком-то
  файле есть неделя 61+ (например, нумерация продолжается через лето),
  она перестанет разбираться. Но `vuz_week` считает недели от якоря и
  тоже не выйдет за разумные пределы, так что совпадения не было бы и
  раньше.
- **Дефект не воспроизводится, чинить не срочно.** Ценность правки —
  в том, что комментарий в коде сейчас обещает защиту, которой нет.
  Это вводит в заблуждение следующего, кто будет читать.
