# План 156: сломанный лист вуза блокирует вторую форму обучения

**Приоритет:** средний. Срабатывает только при изменении структуры
файла, но последствие тихое: одна форма перестаёт обновляться, а
`/stats` показывает сбой, не объясняя, что вторая форма тоже стоит.

**Трудоёмкость:** S (~4 строки).

## Что происходит

`parsers/vuz.py:784-790` — цикл по листам книги:

```python
for name in book.sheet_names():
    try:
        parsed = parse_sheet(book, name)
    except VuzParseError:
        raise                                        # <- :788
    except Exception as exc:
        raise VuzParseError(f"Лист «{name}» не разобрался: {exc}") from exc
```

**Один плохой лист валит весь файл.** `raise` выходит из `parse()`
целиком, хотя остальные листы могли разобраться.

## Что происходит дальше

`tgbot/services/sync_vuz.py:344-352` — цикл по формам:

```python
for form, url in FILES.items():        # {"full": ..., "part": ...}
    ...
    try:
        parsed = await asyncio.to_thread(vuz.parse, data, form)
    except vuz.VuzParseError as exc:
        log.error("файл вуза %s не разобрался: %s", form, exc)
        result["failed"].append(form)
        raise                          # <- :352 рвёт цикл по формам
```

`FILES` (`:39`) — словарь из двух форм:

```python
FILES = {
    "full": f"{vuz.BASE_URL}/1-ochnoe.xls",
    "part": f"{vuz.BASE_URL}/2-ochno-zaochnoe.xls",
}
```

**Если `full` не разобрался — `part` вообще не обрабатывается.**
Порядок словаря фиксирован: `full` первая.

## Почему это хуже, чем просто «сбой»

**Данные не портятся.** Проверил: `replace_vuz_lessons` вызывается
**после** `parse` (`sync_vuz.py:355`), а `raise` на `:352` до него не
доходит. Старые строки `full` целы.

**Но `part` тоже не обновится.** Даже если его файл скачался
нормально и структура у него в порядке — до него не дошла очередь.

Форма `part` — очно-заочная. В `vuz_group` она есть, у неё свои
группы и свои студенты. Они увидят устаревшее расписание, и **никто об
этом не узнает**: `result["failed"]` содержит только `["full"]`,
`mark_ok_vuz` не вызывается, `is_stale_vuz` сработает через 30 минут —
но скажет «синхронизация вуза не проходила», не уточняя, что
пострадала одна форма из двух.

## Проверил, что план 016 это не покрывает

План 016 знает про `raise` на `:349` и правильно требует тревогу
админу. Но он разбирает **только последствие «админ не узнает»**.
Про то, что `raise` обрывает цикл и вторая форма не обработается, там
ни слова — `grep "цикл\|for form\|part"` по плану 016 даёт только
строку про `anchor_off`.

## Что сделать

**Вариант 1 — не рвать цикл (минимальный):**

```python
    except vuz.VuzParseError as exc:
        log.error("файл вуза %s не разобрался: %s", form, exc)
        result["failed"].append(form)
        continue                       # вместо raise
```

Тогда `part` обработается, а `full` останется на старых данных.
`result["failed"]` честно перечислит, что сломалось.

**Вариант 2 — спасать остальные листы внутри `parse`:**

```python
    for name in book.sheet_names():
        try:
            parsed = parse_sheet(book, name)
        except VuzParseError as exc:
            log.error("лист %r не разобрался: %s", name, exc)
            continue
        except Exception as exc:
            log.error("лист %r упал: %s", name, exc)
            continue
```

Тогда один битый лист не убивает файл целиком — но результат будет
неполным без всякого признака, что часть данных потеряна. **Это
опаснее варианта 1**: неполное расписание выглядит как полное.

**Рекомендую вариант 1.** Он сохраняет строгую проверку целостности
(файл либо разобран целиком, либо не принят), но перестаёт наказывать
вторую форму за грехи первой.

## Проверено и признано корректным

**Данные при сбое не теряются.** `replace_vuz_lessons` вызывается
после `parse`; `raise` до него не доходит. Проверил порядок в
`sync_once:344-360`.

**`_download` обрабатывается мягко** (`:334-338`) — `continue`, не
`raise`. Сетевой сбой одной формы не мешает другой. Это правильный
образец, и `parse`-ветка от него отличается без причины.

**`parse_sheet` бросает `VuzParseError` осмысленно.** `:617`:
`raise VuzParseError(f"Лист «{sheet_name}»: не найдено ни одной группы")`.
Сама по себе проверка верная — лист без групп действительно подозрителен.

**`anchor_off` собирается отдельно** и не рвёт цикл (`:369-373`) —
тоже правильный образец.

## Риски

- **`continue` вместо `raise`** меняет контракт `sync_once`: раньше
  исключение гарантировало, что вызывающий узнает о сбое структуры.
  После правки сбой виден только в `result["failed"]`. Нужно убедиться,
  что `poller.py:89` его читает — читает: `logging.warning("частичный
  сбой вуза: %s", vuz_result["failed"])`.
- **Порядок `FILES`** — словарь, порядок вставки сохраняется в Python
  3.7+. Если поменять местами, симптом переедет на другую форму, но не
  исчезнет.
