# 174. «Следующая пара» в звонке об окончании

**Статус:** сделано 17.11.2026
**Повод:** просьба из чата владельца. Студент одногруппника сказал:
после звонка об окончании непонятно, что дальше — какая пара, во
сколько, сколько ждать. Владелец сначала оценил как «сомнительную
фичу» (кнопка-дубль звонков), потом согласился в другой форме: не
отдельный экран, а строка в существующем звонке.

## Как выглядит

Было:

```
🔔 Конец пары
```

Стало:

```
🔔 Конец пары
следующая пара 12:50
Основы безопасности и защиты Родины
Костылева В.В.
```

Со значком замены, если пара пришла из листка:

```
🔔 Конец пары
следующая пара 14:35
Иностранный язык 🔄
Пупкова В.В. · ауд. 406
```

Если до пары меньше трёх часов — добавляется обратный отсчёт:

```
следующая пара 10:45 · через 10 мин
```

## Почему так, а не кнопкой

Первая формулировка была «кнопка, показывающая текущую и следующую
пару». От неё отказались: кнопка требует, чтобы студент сам нажал,
а в момент окончания пары он уже идёт. Строка в звонке приходит сама
и отвечает ровно на вопрос «что дальше и когда», без второго действия.

## Где живёт

`tgbot/services/bell.py`:

| Функция | Что делает |
|---|---|
| `_with_next` | дописывает строку к тексту события |
| `_next_para` | первая неотменённая пара с номером больше текущего |
| `_lesson_line` | предмет + значок + преподаватель + аудитория |
| `_lesson_mark` | 🔄 замена / ➕ добавление |

Вызов — в `_tick`, после сборки `events`:

```python
events = [(t, key, _with_next(text, key, lessons, bell, dt, _cg, user))
          for t, key, text in events]
```

## Правила

1. **Только к «Конец пары»** (ключи `e:N`). Начало пары, перемена,
   обед — без изменений. Проверяется по префиксу ключа, а не по
   тексту: текст локализуемый, ключ нет.
2. **Отменённые пары пропускаются.** Иначе студент шёл бы на
   отменённую — ровно та ошибка, что чинилась 10.11.2026, когда звонки
   приходили на отменённые пары ДП-26.
3. **Время: `time_note` сильнее сетки звонков.** Вечерняя пара
   («с 18.00 до 21.00») показывается как есть, а не как 18:50 по сетке.
4. **«через N мин» только до 3 часов.** Иначе звонок в 09:00 про пару
   в 18:05 показал бы «через 545 мин» — шум, а не польза.
5. **После последней пары строки нет.** Писать «занятий больше нет»
   после каждого последнего звонка — лишний шум, и так очевидно.
6. **Лишних запросов в базу нет.** `lessons` уже в руках `_tick`,
   когда он собирает звонки. Фича — чистая функция над этими данными.

## Защита от поломки

Вызов обёрнут в `try/except` с `logging.exception`. Фича косметическая:
если в ней что-то сломается, звонки должны уйти как раньше, а не
пропасть. Это отличается от данных расписания, где лучше не отправить,
чем отправить неверное.

## Проверка

`tests/test_bell_next_lesson.py` — 8 тестов: дописывание, отсутствие
строки после последней пары, пропуск отменённой, только «Конец пары»,
приоритет `time_note`, отсутствие отсчёта на дальнем горизонте,
преподаватель, пустой день.

Дополнительно прогнано на живых данных прода (17.11.2026) для
`ДП-26`, `ТЭ-26ФП`, `ЮР-25А`: строка собирается, края ведут себя как
задумано (после последней пары, на начале пары, на обеде — текста не
добавляется).

## Что не сделано

- **Кнопка «сейчас / следующая»** — от неё отказались осознанно (см.
  выше). Если студенты попросят отдельный экран, это другой разговор.
- **Звонок до начала пары** не расширялся: там уже есть название
  предмета и кабинет, добавлять «через сколько» не нужно.
- **Вузовские пары** проходят те же правила; отдельных проверок на
  них не делал — сетка вуза (`VUZ_GROUP`) уже была покрыта раньше.

## Хвост, не относящийся к фиче

`tests/test_day_states_uncovered.py` падает 4 тестами на чистом дереве
(проверено `git stash`): у него жёсткая дата `D = 2026-11-09`, а
`stale_when` считается от текущего времени, поэтому «сайт лежит 120
минут» перестало быть правдой, когда день уехал в прошлое. Тест мой,
от 09.11.2026, и его надо перевести на относительную дату
(`datetime.date.today()`), а не чинить. Не трогал в этой задаче.
