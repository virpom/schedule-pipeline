# План 141: «Откатить» не пересобирает расписание

**Приоритет:** средний. Староста откатывает правку, видит
«↩️ Возвращено», а студенты ещё до пяти минут видят отменённое.

**Трудоёмкость:** S (~6 строк).

## Проблема

Каждая правка старосты заканчивается пересборкой `college_lesson` —
иначе студент не увидит изменения, ведь читает он готовую таблицу, а
не слои. Проверил все вызовы `_rebuild`:

```
editor.py:474  _save_base   -> _rebuild(repo)        окно целиком
editor.py:513  _save_sub    -> _rebuild(repo, date)  один день
editor.py:618  ...          -> _rebuild(repo, date)
editor.py:635  ...          -> _rebuild(repo, date)
editor.py:726  ...          -> _rebuild(repo, date)
editor.py:875  определение
```

**`cb_undo` (`:829`) в списке нет.** Он меняет `base_lesson` или
`substitution`, удаляет запись из журнала — и на этом всё:

```python
    await repo.edit_log.delete(last.id)
    await cb.answer(msg, show_alert=True)
    await cb_log(cb, repo)
```

## Что происходит

```
1. Староста правит пару
   -> _save_base -> base_lesson меняется -> _rebuild -> college_lesson
   -> студент видит правку

2. Староста жмёт «↩️ Откатить»
   -> cb_undo -> base_lesson меняется обратно
   -> college_lesson НЕ трогается
   -> студент продолжает видеть отменённую правку

3. Поллер (каждые 300 с) зовёт materialize ВСЕГДА
   -> college_lesson пересобирается -> правка наконец исчезает
```

Задержка — до 5 минут. Проверил `poller.py:113`: `materialize`
вызывается безусловно, комментарий это подчёркивает:

```python
# Материализуем ВСЕГДА, даже при сбое сайта и даже если файлы не
# менялись: окно дат должно сдвигаться вперёд каждый день...
```

То есть **данные не теряются** — только задерживаются. Это делает
дефект неприятным, но не разрушительным.

## Почему это заметно

Староста нажимает «Откатить» и ждёт немедленного результата — он же
только что видел, как правка применилась мгновенно. А откат «не
работает» пять минут.

Хуже: если староста после отката откроет предпросмотр (`_preview_for_user`
читает `college_lesson`), он увидит **свою отменённую правку** и решит,
что откат не сработал. Нажмёт ещё раз — получит «Нечего откатывать»
(запись уже удалена из журнала). Выглядит как поломка.

## Что сделать

Добавить пересборку в конец `cb_undo`, по той же логике, что в
`_save_base`/`_save_sub`:

```python
    await repo.edit_log.delete(last.id)
    # Пересобрать так же, как при самой правке: база повторяется каждую
    # неделю — окно целиком; замена живёт на одной дате — только она.
    if last.layer == "base":
        await _rebuild(repo)
    else:
        await _rebuild(repo, last.date)
    await cb.answer(msg, show_alert=True)
    await cb_log(cb, repo)
```

`last.layer` уже есть в `ScheduleEdit` (`log()` его пишет), `last.date`
тоже — для замены заполняется.

**Порядок важен:** `_rebuild` до `cb.answer`, иначе пользователь
получит ответ раньше, чем данные обновятся, и следующий экран покажет
старое.

## Что проверил и признал корректным

**`_rebuild` не падает молча.** Оборачивает всё в `try/except` с
`logging.exception` (`:884`) — если материализация сломается, староста
не получит трейсбек, но ошибка попадёт в лог.

**`_save_base` и `_save_sub` пересобирают правильно.** База — окно
целиком (правка повторяется каждую неделю), замена — один день. Логика
верная, откат должен её повторить.

**`no_lessons` — мёртвая таблица.** Заметил отдельно: `NoLessonsRepo`
имеет `replace_date`, но **никто его не вызывает** — grep по всему
проекту даёт только чтение (`user.py:673`, `poller.py:192`, `:216`).
Данные от 07-08 октября лежат с тех пор, как их залили руками:

```
2026-10-07  ПРк-25   «Занятий нет. Смотреть расписание на 08.10.2026»
2026-10-07  ЭК-25    то же
2026-10-07  ЮР-25А   то же
2026-10-08  ПРф-25   то же
```

Это не дефект — механизм ручных пометок, работает как задумано. Но
писать в него можно только через SQL, что стоит знать.

## Риски

- **`materialize` занимает 5.9–6.4 с** (замерено ранее). При откате
  базовой пары староста будет ждать шесть секунд. Telegram не отвалится
  (таймаут callback ~15 с), но ощутимо. Если станет проблемой —
  вынести в `asyncio.create_task`, как сделано в админке через `_spawn`.
- **`last.date` может быть `None`** у базовой правки — поэтому ветка
  `if last.layer == "base"` обязательна, а не `if last.date`.
