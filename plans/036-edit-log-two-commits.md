# План 036: правка и журнал пишутся двумя коммитами

> **СДЕЛАНО 27.10.2026** (коммит `36fa196`). Отметка стояла в
> `plans/README.md`, но не в файле плана.

**Приоритет:** низкий. Срабатывает только при сбое между двумя
записями, но тогда правка теряется из истории навсегда.

**Трудоёмкость:** S (~10 строк).

## Проблема

`tgbot/handlers/editor.py:463`:

```python
await repo.base_lessons.upsert(group, parity, weekday, para, subject, teacher, room,
                               source="manual", updated_by=event.from_user.id)   # commit #1
await repo.edit_log.log(
    group, "base", "edit" if old_slot else "add", user_id=event.from_user.id,
    ...
)                                                                              # commit #2
await _rebuild(repo)
```

Каждый метод репозитория коммитит сам (`base_lesson.py:90`,
`schedule_edit.py:28`). Значит между правкой и записью в журнал есть
окно, где **одно уже зафиксировано, а другого нет**.

Тот же паттерн в пяти местах:

| Строка | Что пишется | Журнал |
|---|---|---|
| `editor.py:463` | `base_lessons.upsert` | `edit_log.log` |
| `editor.py:508` | `base_lessons.delete_slot` | `edit_log.log` |
| `editor.py:614` | `substitutions.set` (отмена) | `edit_log.log` |
| `editor.py:632` | `substitutions.delete` | `edit_log.log` |
| `editor.py:724` | `substitutions.set` | `edit_log.log` |

## Что сломается

Если второй коммит не пройдёт (`disk I/O error`, `database is locked`
при `busy_timeout`, обрыв питания):

```
1. upsert -> commit -> правка в базе ЕСТЬ
2. edit_log.log -> ошибка
3. исключение улетает в aiogram
4. староста видит ошибку в логе, но правка применилась
5. undo её не покажет: журнал пуст
6. отменить нечем, и никто не знает, что отменять
```

То есть студенты увидят правку, а староста не сможет её снять и не
поймёт почему. Это хуже, чем «правка не применилась» — там хотя бы
всё согласовано.

## Что проверил и признал корректным

- **Репозитории всегда коммитят сами.** Это осознанный выбор: 13
  файлов, 26 вызовов `commit()`. Иначе изменения молча терялись бы
  при `session.close()` в middleware. Трогать это не надо.
- **Middleware коммитит `get_or_create_user` отдельно.** Это правильно:
  регистрация пользователя не должна откатываться из-за ошибки
  в бизнес-логике.
- **`_rebuild` после правки — верное решение.** План 009 про
  проглатывание исключений в нём остаётся в силе, но сам вызов нужен.
- **`cb_undo` без `_rebuild`** — это план 004, отдельная проблема.
- **Админские действия не логируются вовсе** (`set_group`,
  `set_role`, `set_editor`). Это не про атомарность, а про отсутствие
  аудита — отдельная тема, в план 022 (мёртвый код) не входит.

## Что сделать

Сделать пару «правка + журнал» одной транзакцией. Простейший способ,
не переписывая репозитории — отдельный метод-обёртка:

```python
async def apply_edit(repo, *, mutate, log_kwargs) -> None:
    """Правка и запись в журнал — в одной транзакции.

    Репозитории коммитят сами, поэтому на время операции отключаем
    автокоммит и фиксируем оба изменения одним вызовом.
    """
    await mutate()                          # без commit
    await repo.edit_log.add_no_commit(**log_kwargs)
    await repo.session.commit()
```

Для этого в `BaseLessonRepo` и `SubstitutionRepo` нужны варианты
методов без `commit()`, а в `ScheduleEditRepo` — `add_no_commit`.
Это ~6 строк на каждый и по одной замене в пяти местах `editor.py`.

**Альтернатива проще:** не разделять. Сначала журнал, потом правка:

```python
await repo.edit_log.log(...)          # commit #1: намерение
await repo.base_lessons.upsert(...)   # commit #2: действие
```

Тогда при сбое останется «в журнале запись есть, правки нет» — undo
попытается откатить несуществующее и получит no-op. Это безопаснее,
чем обратный порядок: потерянной истории не будет, а лишняя запись
безвредна.

## Как проверить

```python
async def test_edit_and_log_same_transaction(repo):
    """Сбой записи в журнал не оставляет правку в базе."""
```

Проверить практически сложно (нужен смоделированный сбой). Достаточно
теста, что после успешной правки в журнале ровно одна запись, а
`old_value` содержит прежний предмет.

## Риски

- **`session.commit()` внутри репозитория — общая конвенция проекта.**
  Вводить «no_commit»-варианты значит нарушить её в двух файлах из
  тринадцати. Проще переставить порядок (журнал → правка), чем
  ломать конвенцию.
- **Порядок «журнал → правка» имеет свой минус:** undo увидит запись,
  которой соответствует уже откаченная правка, и удалит её. Но это
  no-op — вреда нет.
- **`_rebuild` остаётся третьим шагом.** Он идемпотентен и
  пересобирает из базы, так что его падение безопасно (студент увидит
  изменения после следующего опроса). Не надо включать его в
  транзакцию.
