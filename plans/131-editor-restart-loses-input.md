# План 131: рестарт посреди ввода молча съедает работу старосты

> **СДЕЛАНО 27.10.2026** (коммит `38f286c`).
>
> Закрыт только сценарий 2. `_save_base` и `_save_sub` теперь
> отвечают «Права редактора отозваны. Правка не сохранена» с кнопкой
> возврата и чистят состояние, вместо голого `return`.
>
> Сценарий 1 (рестарт) и `KeyError` в `_save_base` — править не нужно,
> как и доказано в плане: `MemoryStorage` чистит состояние и данные
> одной записью, поэтому обработчики шагов без состояния не
> вызываются. Для рестарта оставлено как есть — Redis не заводим.

**Приоритет:** низкий по факту (правок ещё не было ни одной), но
высокий по последствиям, когда редактор начнут использовать.

**Трудоёмкость:** S (~10 строк).

## Проблема

FSM-хранилище — **в памяти** (`main.py:48`):

```python
dp = Dispatcher(storage=MemoryStorage())
```

Любой рестарт контейнера стирает все состояния и все накопленные
данные диалога. А рестартов много: каждый деплой, каждое падение,
пересоздание контейнера.

Диалог старосты — трёхшаговый. Он вводит:

```
1. предмет   -> state=teacher
2. фамилию   -> state=room
3. кабинет   -> _save_base
```

## Что происходит при рестарте между шагами

1. Староста нажал «🗓 Базовое расписание» → «1 пара» →
   `set_state(EditorState.subject)`, в `data` лежат `weekday`, `parity`,
   `para`
2. Бот перезапустился — `MemoryStorage` пуст
3. Староста пишет «Математика»
4. `on_subject` привязан к `EditorState.subject` — состояния нет,
   обработчик **не вызывается**
5. Текст проваливается в `any_text` (`user.py:1022`):

```python
@user_router.message(F.text, ~F.text.startswith("/"))
async def any_text(message: Message, repo: RequestsRepo, user: User):
    """Не молчим на непонятный текст — показываем меню и нижние кнопки."""
    text, kb = await _render_menu(repo, user)
    await message.answer(text, reply_markup=kb)
    await message.answer("Кнопки внизу — быстрый доступ 👇", reply_markup=BOTTOM_KB)
```

**Человек получает меню и не понимает, почему его ввод пропал.**
Ни «ввод прерван», ни «начни заново». Просто меню.

## Второй сценарий: молчаливый отказ при отзыве прав

`_save_base` (`editor.py:439`) и `_save_sub` (`:703`) начинаются с:

```python
async def _save_base(event, repo, state, via_cb):
    data = await state.get_data()
    group = await editor_group(repo, event.from_user.id)
    if not group:
        return                          # <- ни сообщения, ни alert
```

Если права отозвали **пока староста вводил поля**, он проходит три
шага и на последнем не получает ничего. Ни ошибки, ни подтверждения.

Тот же `return` сработает, если староста нажал «✏️ Редактор» на одном
устройстве, а права отозвали с другого.

## Третий сценарий: `KeyError` — проверил, недостижим

В `_save_base`:

```python
weekday = data["weekday"]      # без .get()
parity = data["parity"]
para = data["para"]
```

Если `data` пуст, будет `KeyError`. Проверил достижимость:

- `state.clear()` в `cb_back` (`:279`) чистит **и состояние, и данные**
  одновременно — следующий текст уйдёт в `any_text`, не в `on_subject`
- Рестарт чистит и то, и другое — та же история
- aiogram хранит состояние и данные в одной записи storage

**Вывод: `data` без `state` не бывает.** `KeyError` недостижим, править
не нужно.

## Что проверил и признал защищённым

**Все 33 callback-обработчика админки проверяют права.** Проверил
программно: разобрал `admin.py`, у каждого
`@admin_router.callback_query(...)` взял тело до следующего декоратора
и поискал `_is_admin_cb`. **Ноль без проверки.**

**Четыре message-обработчика админки без явной проверки** —
`m_group_broadcast`, `m_broadcast`, `m_setting`, `upload_photo` —
привязаны к FSM-состояниям. Проверил все сеттеры этих состояний:

```
:503  broadcast_cmd        -> if not _is_admin(message, config)
:580  cb_broadcast         -> if not _is_admin_cb(cb, config)
:590  cb_broadcast_teachers-> if not _is_admin_cb(cb, config)
:599  cb_broadcast_group   -> if not _is_admin_cb(cb, config)
:957  cb_setting           -> if not _is_admin_cb(cb, config)
:1031 cb_photo_day         -> if not _is_admin_cb(cb, config)
```

Войти в состояние может только админ. Защита двухступенчатая и
достаточная.

**Состояния не пересекаются между роутерами.** `AdminState` и
`EditorState` — разные `StatesGroup`, имена не совпадают.

**Все шаги редактора, кроме последнего, защищены на входе.** Проверил
расстояние до ближайшей проверки `if not group:` перед каждым
`set_state(EditorState...)`:

```
:390  subject  -> 1 проверка выше   (первый шаг, защищён)
:655  subject  -> 1 проверка выше   (первый шаг замен, защищён)
:418, :429, :682, :693, :944, :954  -> 0
```

Ноль — это `on_teacher`/`on_room`, которые вызываются **только** после
`on_subject`. Попасть в них напрямую нельзя: состояние ставит бот, а
не пользователь. Внешней записи в FSM нет — проверил, `set_state` —
обычная запись в storage, но вызвать её можно только из обработчика.

**Запись защищена на уровне сохранения.** Даже если бы кто-то дошёл до
`_save_base` без прав, `editor_group()` вернёт `None` и данные не
запишутся.

## Что сделать

**1. Сказать человеку, что ввод прерван.** В `any_text` добавить
проверку, не был ли пользователь в диалоге — но состояния уже нет,
значит нужен флаг. Проще: добавить в `_save_base`/`_save_sub` ответ
вместо молчаливого `return`:

```python
if not group:
    await event.answer("Права редактора отозваны. Правка не сохранена.")
    await state.clear()
    return
```

Это закрывает второй сценарий полностью.

**2. Для рестарта — либо `RedisStorage`, либо явное сообщение.** Если
ставить Redis — новая зависимость и сервис, чего проект избегает.
Дешевле: `on_subject`/`on_teacher`/`on_room` начинать с проверки, что
`data` содержит нужные ключи, и отвечать «Ввод прерван, начни заново» —
но они и так не вызовутся без состояния.

Значит для рестарта честнее оставить как есть и **задокументировать**:
«незавершённый ввод теряется при перезапуске». Или перейти на
`RedisStorage`, если редактор станет массовым.

## Риски

- **Сейчас правок ноль.** Проверил: `base_lesson source='manual'` — 0,
  `substitution source='manual'` — 0, `schedule_edit` — 0 строк.
  Редактор ни разу не использовался по назначению. Значит все три
  сценария латентны.
- **Правка `_save_base`/`_save_sub` может сломать обычный поток**, если
  перепутать `event.answer` (Message) и `event.message.answer`
  (CallbackQuery). Функции принимают и то, и другое через `via_cb`.
