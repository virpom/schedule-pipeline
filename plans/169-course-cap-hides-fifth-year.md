# План 169: студент 5–6 курса вуза видит «4 курс»

**Приоритет:** низкий. Сейчас в затронутых группах **0** пользователей
бота, но механизм сломан: любой пятикурсник при подключении увидит
неверную подпись.

**Трудоёмкость:** S (одна строка).

## Что происходит

`course_from_group` (`common/schedule.py:107-113`):

```python
def course_from_group(group: str) -> int:
    m = re.search(r"(\d{2})", group)
    if not m:
        return 1
    admission = 2000 + int(m.group(1))
    now = datetime.datetime.now()
    acad_start = now.year if now.month >= 9 else now.year - 1
    return max(1, min(acad_start - admission + 1, 4))
```

`min(..., 4)` — потолок в **4 курса**. Для колледжа это верно: там
программы до 4 лет. Но в вузе есть 5 и 6 курс, и они схлопываются в 4.

Меню (`user.py:199-204`):

```python
if is_vuz(user.group):
    label = "Группа · вуз"
    course = course_from_group(user.group)   # <- потолок 4
else:
    course = user.course
if course:
    ident = f"{ident} · {course} курс"
```

## Что видит студент

Сейчас (`acad_start = 2026`):

```
ГИ-22@vuz   -> "ГИ-22 · 4 курс"     реально 5
ГИ-21@vuz   -> "ГИ-21 · 4 курс"     реально 6
```

## Масштаб — проверил на проде

Сверил `vuz_group.course` (истина из файла) с `course_from_group` по
всем 92 группам: **10 расхождений**.

```
курс 5 (8 групп):  ГИ-22, ГИ - 22оз, МД-22, МН - 22оз,
                   МЦ-22оз, ПС-22оз, ФК-22оз, ЭП-22оз
курс 6 (2 группы): ГИ-21, ГИ - 21оз
```

Пользователей бота в этих десяти группах — **ноль**. Всего
пользователей вуза на проде **3** (`ИС-25@vuz`, `АП-26@vuz`,
`АП-25оз@vuz`), все на младших курсах.

## Почему план 147 этого не заметил

`plans/147-week-no-merge.md:115-118` утверждает:

> **`course_from_group` работает верно.** Проверил распределение по
> всем 129 группам: курс 1 — 38, курс 2 — 30, курс 3 — 28, курс 4 —
> 33. Аномалий нет, все имена содержат год приёма в первых двух цифрах.

Проверка смотрела на **распределение результата функции**, а `min(...,
4)` по построению даёт только 1..4 — распределение «без аномалий»
получается автоматически, что бы ни было в данных. Сравнивать надо
было с `vuz_group.course`, а не с самой функцией.

## Что сделать

Убрать потолок — он нужен только колледжу, а для него есть
`user.course` из базы:

```python
return max(1, acad_start - admission + 1)
```

Проверил, что это безопасно:

- **Колледж не затронут.** `user.py:203` для него берёт `user.course`
  из БД, а не из имени группы.
- **Звонки не затронуты.** `bells_group` (`common/schedule.py:132-145`)
  при непустой группе сразу возвращает `course_group_from_group(group)`,
  а тот для вуза отдаёт `VUZ_GROUP` без всякой арифметики.
  `course_group_from_course` вызывается только когда группа пустая.
- **`course_group_from_group` для колледжа** использует
  `course in (1, 4)` — при курсе 5–6 вернёт `II_III`. Но колледж
  до 5 курса не доходит, а вуз в эту ветку не попадает.

Второй вариант — не трогать `course_from_group`, а в меню брать курс из
`vuz_group`. Но это лишний запрос к БД ради подписи; потолок проще.

## Проверено и признал корректным

**Звонки вуза не зависят от курса.** `course_group_from_group`
(`:115-124`) первым делом проверяет `is_vuz(group)` и возвращает
`VUZ_GROUP`. Арифметика курса до неё не доходит.

**`user.course` для колледжа хранится в БД** — `user.py:203` берёт
`user.course`, а не вычисляет из имени. Потолок ему не мешает.

**Поиск преподавателя не затронут** — `course_from_group` там не
вызывается.

**`course_from_group("ЭК-23@vuz") == course_from_group("ЭК-23")`** —
суффикс `@vuz` не мешает `re.search`, это уже проверено в
`tests/test_vuz_foundation.py:41-42`.

**Остальные 82 группы совпадают** с `vuz_group.course` — расхождение
ровно на курсах выше четвёртого.

## Риски

- **Курс теперь может быть 7+** для старых групп. Проверил: самая
  старая — `ГИ-21` (курс 6). Через год станет 7 — но это правда, а не
  ошибка: группа действительно на 7 курсе.
- **Тест:** `tests/test_vuz_foundation.py` проверяет только совпадение
  с/без суффикса. Стоит добавить случай `course_from_group("ГИ-21@vuz")
  == 6` — сейчас он вернул бы 4.
