# План 086: «Откатить» снимает чужую правку

> **СДЕЛАНО 27.10.2026** (коммит `9538590`).
>
> Выбран вариант А — «каждый откатывает своё». Плюс попутная мелочь
> из плана: в журнале теперь помечено «👤 другой», иначе непонятно,
> почему откатывать нечего.

**Приоритет:** средний. Портит данные молча: староста нажимает
«Откатить» и убирает то, чего не делал.

**Трудоёмкость:** S (одна строка).

## Проблема

`cb_undo` (`editor.py:835`) берёт последнюю правку **группы**, не
спрашивая, кто её сделал:

```python
last = await repo.edit_log.get_last(group)
```

`get_last` (`schedule_edit.py`) умеет фильтровать по автору — параметр
есть:

```python
async def get_last(self, group: str, user_id: int | None = None) -> ScheduleEdit | None:
    query = select(ScheduleEdit).where(ScheduleEdit.group == group)
    if user_id is not None:
        query = query.where(ScheduleEdit.user_id == user_id)
    ...
```

Но `user_id` не передаётся, значит `None`, значит фильтра нет.

## Что произойдёт

```
староста А: правит пару 3 (суббота, чётная) → строка в журнале
староста Б: той же группы, ничего не делал
староста Б: жмёт «↩️ Откатить»
           → откатывается правка А
           → Б видит «↩️ Возвращено: <предмет>»
```

Б не поймёт, что откатил чужое: сообщение выглядит как успешный откат
своего. И проверить нечем — журнал показывает записи группы, без
автора.

## Что на проде

```
schedule_editor: 2 строки, обе group = 'ДП-26'
```

**Два старосты на одну группу уже есть.** То есть сценарий не
гипотетический — он готов сработать на первом же откате.

`schedule_edit` — 0 строк, поэтому пока не срабатывал: правок не было.

## Что сделать

Передать автора:

```python
last = await repo.edit_log.get_last(group, cb.from_user.id)
```

Тогда каждый староста откатывает только своё. Если своей правки нет —
`get_last` вернёт `None`, и сработает существующая ветка «Нечего
откатывать».

## Но подумать шире

Есть два разумных поведения, и выбор продуктовый:

**Вариант А — «каждый откатывает своё»** (одна строка выше). Просто,
предсказуемо, но староста Б не может убрать ошибку А, если та ушла.

**Вариант Б — «откат общий, но видно автора»**. Тогда надо не менять
`get_last`, а добавить в журнал колонку автора:

```python
for e in entries:
    who = f" · {e.user_id}" if e.user_id else ""
```

Сейчас `cb_log` (`editor.py:799`) автора не печатает вовсе, хотя поле
`user_id` в модели есть и заполняется.

Я бы взял **А**: кнопка «Откатить» без указания, что именно
откатывается, — плохой инструмент для коллективной правки. А увидеть
чужое можно в журнале, если добавить туда автора (это отдельная
мелочь, плана не заслуживает).

## Проверено и признано корректным

**`edit_log.delete` после отката — замысел, не баг.** Проверил
docstring:

```
Убрать запись из журнала после отката.
Без этого повторное нажатие «Откатить» откатывало ту же самую правку
снова: журнал не двигался, и кнопка выглядела сломанной.
```

То есть журнал — **стек отмены**, а не аудит. Так и задумано. Если
понадобится настоящий аудит, это отдельная таблица, а не правка этой.

**`get_recent` показывает записи всей группы** — это правильно:
журнал общий, старосты видят, что менялось.

**`delete` коммитит сам** — значит после отката запись исчезает
атомарно с самой отменой? Нет: отмена правки и `edit_log.delete` —
две разные транзакции. Это [план 036](036-edit-log-two-commits.md), не
дублирую.

**Правка и журнал пишутся разными коммитами** — тоже план 036.

## Риски

- **`cb.from_user.id` может не совпасть с `user_id` в журнале.** При
  записи используется `cb.from_user.id` (`editor.py:468` и рядом) — то
  же значение. Совпадёт.
- **Старые записи без `user_id`.** В модели `user_id` nullable. На
  проде журнал пуст, так что легаси-строк нет. Если появятся — фильтр
  их скроет, и «Откатить» скажет «Нечего откатывать». Приемлемо.
