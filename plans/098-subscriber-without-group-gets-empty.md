# План 098: подписчик без группы получает «Занятий нет» на каждую дату

**Приоритет:** средний. Пять человек на проде получают ложные
уведомления о каждом изменении расписания — и никогда не получают
настоящего.

**Трудоёмкость:** S (~6 строк).

## Проблема

`notify_new_schedule` (`poller.py:147`) рассылает по `get_subscribed()`
без проверки, есть ли у человека группа или фамилия:

```python
if user.role == "teacher" and user.teacher_name:
    lessons = await repo.college_lessons.get_for_teacher_date(user.teacher_name, date)
    note = None
else:
    lessons = await repo.college_lessons.get_for_group_date(user.group, date)
    note = await repo.no_lessons.get_note(date, user.group) if not lessons else None
```

Ветка `else` — запасная. В неё попадают **все**, кто не «преподаватель с
фамилией»: и студенты с группой, и любой пользователь без группы.

`get_for_group_date(None, date)` (`college_lesson.py:45`) выполняет

```sql
SELECT ... WHERE "group" IS NULL AND date = ?
```

— то есть пустой результат. Дальше:

```python
if lessons:
    text = format_day(...)
else:
    text = format_no_lessons(date, note)
```

и человек получает:

```
📅 Вторник, 27 октября

Занятий нет 🙌
```

## Кто попадает

На проде **5 подписчиков из 228** без группы или фамилии:

```
6602662332  teacher  группа=None  фамилия=None
6231955455  student  группа=None
6692409439  student  группа=None
1588628434  student  группа=None
7749685971  student  группа=None
```

Первый — тот самый `role='teacher'` без фамилии (см. ниже). Остальные
четыре — студенты, которые подписались, но группу не выбрали.

## Сколько сообщений

Список дат для рассылки (`poller.py:132-139`) — это все даты замен
плюс три дня вперёд. На проде сейчас это 15 дат:

```
10-26, 10-27, 10-29, 10-30, 10-31,
11-02, 11-03, 11-05, 11-06, 11-07,
11-09, 11-14, 11-18, 11-19, 12-10
```

Значит **каждый** такой подписчик получает 15 сообщений «Занятий нет» за
один цикл опроса — и так при каждом изменении расписания.

## Как сюда попадают

`cb_role_teacher` (`user.py:442`) меняет роль **до** выбора фамилии:

```python
async def cb_role_teacher(cb, repo, user):
    await repo.users.set_role(user.id, "teacher")
    await cb.message.edit_text("👨‍🏫 Где ты преподаёшь?", reply_markup=TEACHER_UNIT_KB)
```

Если человек нажал «Я преподаватель» и закрыл чат — остаётся
`role='teacher'`, `teacher_name=None`. Так и появился `6602662332`
(создан 05.10, `subscribed=1`).

У студентов то же самое, но механизм другой: `subscribed` по
умолчанию **`0`**, а не `1`.

Проверил, потому что нашёл расхождение:

```
модель   infrastructure/database/models/user.py:26
         subscribed: server_default=text("1")
миграция migrations/versions/0001_baseline.py:28
         sa.Column("subscribed", ..., server_default=sa.text("0"))
схема в проде
         subscribed BOOLEAN DEFAULT 0 NOT NULL
```

**Модель врёт, работает миграция.** `DEFAULT 0` — потому что SQLite
берёт значение из `CREATE TABLE`, а модель описывает схему только для
`create_all`, который в этом проекте не используется (есть alembic).

Значит четыре студента без группы включили подписку **вручную**, а не
получили её по умолчанию. Тем важнее фильтр: человек сам нажал
«Подписка», но не выбрал группу — и получает «Занятий нет» на каждую
дату.

Расхождение `1` против `0` стоит поправить отдельно: если кто-то
однажды пересоздаст базу через `metadata.create_all()`, все получат
подписку по умолчанию, и рассылка пойдёт всем 231 пользователю.

## Что уже сделано правильно

Главное меню обрабатывает это корректно — проверил на живом коде:

```
menu_text:
  🎓 Расписание ПТК
  Фамилия не выбрана.
  Найди себя в списке 👇

menu_kb:
  [🎯 Найти себя -> pick_teacher]     <- первой строкой
  [📅 Сегодня] [📅 Завтра]
  ...
```

`_has_identity` возвращает `False`, и кнопка выбора ставится в начало.
Все девять обработчиков, которым нужна идентичность (`cb_today`,
`cb_tomorrow`, `cb_week`, `cb_hist`, `cb_hist_page`, `cb_hist_date`,
`cb_sub`, `cb_bell_mode`, `cb_find`), вызывают `_require_identity` и
отвечают «Сначала выбери группу или фамилию 🎯».

**Единственное место без проверки — рассылка.** Она не спрашивает, а
шлёт.

## Что сделать

Пропускать подписчиков без идентичности:

```python
for user in subscribers:
    if user.role == "teacher" and not (user.teacher_name or "").strip():
        continue
    if user.role != "teacher" and not (user.group or "").strip():
        continue
    ...
```

**Или** — лучше — не подписывать тех, у кого нет идентичности:
`cb_sub` уже проверяет `_require_identity`, так что включить подписку
без группы нельзя. Но `subscribed=1` стоит по умолчанию с момента
создания пользователя, до всякого выбора. Значит фильтр нужен именно
в рассылке.

## Проверено и признано корректным

**Меню не ломается.** `menu_text` для `role='teacher'` без фамилии
явно пишет «Фамилия не выбрана», `menu_kb` ставит «🎯 Найти себя»
первой строкой. Для студента без группы — «Группа не выбрана» и
«🎯 Выбрать группу».

**Пустой `teacher_name` не ломает выборку преподавателя.**
`get_for_teacher_date` начинается с `if not (teacher_name or "").strip():
return []` — пустая строка не превращается в `LIKE '%%'`. Проверено.

**`cb_role_switch` чистит всё.** `set_group(None)`,
`set_teacher_name(None)`, `set_course(None)`, `set_unit("college")` —
после переключения роли человек возвращается в чистое состояние.

## Риски

- **Пропустить подписчика — не то же, что отписать.** `subscribed`
  остаётся `1`, человек появится в меню как подписанный, но сообщений
  не получит. Честнее либо слать «выбери группу», либо ставить
  `subscribed=0` при отсутствии идентичности.
- **Пять человек — не повод не чинить.** Сейчас их пять, но каждый
  новый пользователь начинает с `subscribed=1` и без группы. Дефект
  будет воспроизводиться с каждым, кто нажмёт «Подписка» в первые
  секунды после `/start`.
