# План 160: поиск человека по русскому имени не работает

> **СДЕЛАНО 28.10.2026.** План про поиск человека админом, не про поиск преподавателя. SQLite lower() понимает только латиницу — поиск по русскому имени не находил. Фильтр перенесён в Python casefold. Коммит 3515769.

**Приоритет:** средний. Админ не может выдать права редактора, введя
имя человека — а именно так он и будет искать. Обходной путь есть
(@ник или id), но он требует, чтобы админ их знал.

**Трудоёмкость:** S (~5 строк).

## Что происходит

`/admin` → «Редакторы» → «Добавить» → FSM `set_editor` принимает текст
(`admin.py:1178`) и ищет:

```python
found = await repo.users.search(query, limit=8)     # :1183
if not found:
    await message.answer(f"🔍 По запросу <code>{query}</code> никто не найден.")
```

`UserRepo.search` (`user.py:153-172`):

```python
clean = q.lstrip("@").lower()
result = await self.session.execute(
    select(User)
    .where(
        (func.lower(User.username) == clean)
        | (func.lower(User.username).like(f"%{clean}%"))
        | (func.lower(User.full_name).like(f"%{clean}%"))
    )
    ...
)
```

## Почему не находит

`func.lower()` транслируется в SQLite `lower()`, а он **понижает
регистр только для ASCII**. Кириллица остаётся как была:

```sql
SELECT lower('ЦАТУРЯН'), lower('Цатурян'), upper('цатурян');
-- 'ЦАТУРЯН'  'Цатурян'  'цатурян'
```

То есть `lower()` не меняет ни один кириллический символ.

Дальше сравнение идёт в `LIKE`, который в SQLite тоже регистрозависим
для не-ASCII. Итог для пользователя `full_name = 'Цатурян Владислав'`:

```
clean   = "цатурян"
pattern = "%цатурян%"
lower('Цатурян Владислав') = 'Цатурян Владислав'   -- не изменилось
'Цатурян Владислав' LIKE '%цатурян%'               -- НЕТ совпадения
```

## Проверил на проде

Взял реальных пользователей с заглавной кириллицей в `full_name` и
поискал по их фамилии в нижнем регистре — ровно как это делает
`search`:

```
ищем 'найс'    (от 'Найс')    -> 0 найдено
ищем 'димчик'  (от 'Димчик')  -> 0 найдено
ищем 'руфат'   (от 'Руфат')   -> 0 найдено
ищем 'вито'    (от 'Вито')    -> 0 найдено
```

При этом пользователи существуют. Поиск по id и по @нику (ASCII)
работает — `lower()` там отрабатывает корректно.

**Затронуто 86 пользователей из 246** — у них в `full_name` есть
кириллица. Не у всех она с заглавной, поэтому находится не ноль, а
подмножество: те, кто записал имя строчными (например
`'сандорская'`), совпадают случайно.

## Второй дефект: `%` и `_` не экранируются

`clean` подставляется в шаблон без escape:

```python
.like(f"%{clean}%")
```

Запрос `%` даёт шаблон `%%%`, который матчит **всех**. `limit=8`
вернёт 8 произвольных пользователей, и админ увидит список чужих
людей под своим запросом — с возможностью выдать права не тому.

То же с `_` (любой один символ).

## Что сделать

**1. Понижать регистр в Python, а не в SQL.** Сравнивать через
`lower()` бессмысленно для кириллицы — надо тянуть кандидатов и
фильтровать, либо хранить нормализованную копию. Для 246 строк хватит
простого варианта:

```python
async def search(self, query: str, limit: int = 8) -> list[User]:
    q = query.strip()
    if not q:
        return []
    if q.isdigit():
        user = await self.get(int(q))
        return [user] if user else []

    clean = q.lstrip("@").lower()
    rows = await self.get_all()
    found = [
        u for u in rows
        if clean in (u.username or "").lower()
        or clean in (u.full_name or "").lower()
    ]
    found.sort(key=lambda u: u.last_seen or datetime.datetime.min, reverse=True)
    return found[:limit]
```

`str.lower()` в Python понижает кириллицу корректно.

**2. Экранировать `%` и `_`,** если остаётся SQL-вариант:

```python
safe = clean.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")
... .like(f"%{safe}%", escape="\\")
```

## Почему это не срочно

**Обходной путь работает.** По @нику и по id поиск находит всегда —
это ASCII, `lower()` там отрабатывает. Сейчас в `schedule_editor` две
записи, обе `ДП-26`, выданы вручную. То есть дефект ещё никому не
помешал — но помешает в первый же раз, когда админ попробует найти
старосту по имени.

**Запрос «%» безобиден на практике:** админ не набирает `%` случайно.
Но это единственная защита — случайность.

## Проверено и признал корректным

**`q.isdigit()` → `get(int(q))`** — ветка верная, id ищется точно.

**Точное совпадение по @нику** (`func.lower(User.username) == clean`)
работает для ASCII-ников. Все 246 пользователей имеют ASCII-username
(проверил: `username glob '*[А-Яа-яЁё]*'` → 0).

**Сортировка `last_seen.desc().nullslast()`** — верная, свежие сверху.

**`limit=8`** — разумно для выбора кнопками.

## Риски

- **`get_all()` на каждый поиск** — 246 строк, это дёшево. Если
  пользователей станет десятки тысяч, понадобится нормализованная
  колонка `full_name_lower` с индексом. Сейчас — нет.
- **Порядок `last_seen`** в Python-варианте надо повторить явно, иначе
  список перестанет быть отсортированным по свежести.
