# План 031: опечатка в годе источника теряет перенос

**Приоритет:** средний. Найдено на реальных данных: одна ячейка, но
механизм сломается на любой похожей опечатке.

**Трудоёмкость:** S (~12 строк).

## Что произошло

В файле вуза `1-ochnoe.xls`, лист `ФЭЭиУ 1 курс`, строка 60,
колонка 3 (`ЭК-26-1`), ячейка содержит:

```
ч. Основы корпоративной культуры и деловое общение (лек)
Самойлова Л.П.  06.11.20226. - перенос на 18.11.2026
```

**`06.11.20226`** — опечатка в источнике: лишняя `6` в конце года.

## Что делает парсер

`parsers/vuz.py:249`:

```python
DATE_RE = re.compile(r"(\d{1,2})\.(\d{1,2})(?:\.(\d{2,4}))?")

def parse_date(text: str, year: int) -> datetime.date | None:
    for m in DATE_RE.finditer(text):
        day, month = int(m.group(1)), int(m.group(2))
        y = int(m.group(3)) if m.group(3) else year
        ...
        return datetime.date(y, month, day)
```

Регулярка жадно берёт **первые 4 цифры**: `2022`, и `finditer` находит:

```
('06.11.2022', '06', '11', '2022')   <- взято
('18.11.2026', '18', '11', '2026')   <- проигнорировано
```

`parse_date` возвращает `datetime.date(2022, 11, 6)` — дату из **2022
года**, четыре года назад.

## Последствие

В `substitution` лежат две записи на `2022-11-06`:

```
2022-11-06  ЭК-26-1@vuz  para=3  replace  Основы корпоративной культуры…
2022-11-06  МН-26@vuz    para=3  replace  Основы корпоративной культуры…
```

1. **Настоящий перенос на 18.11.2026 потерян.** Студент не узнает,
   что пару перенесли.
2. Мусорная замена висит в `substitution` вечно — в окно 14 дней она
   не попадёт, но и не удалится (замены пишутся по хешу файла, а файл
   не менялся).

Проверил на проде: это единственная такая ячейка из 11 листов.

## Что сделать

Не доверять году, который «не в диапазоне семестра». Простейшая защита
в `parse_date`:

```python
def parse_date(text: str, year: int) -> datetime.date | None:
    """Дата из ячейки: «09.11.2026» или «26.10» (год по умолчанию)."""
    for m in DATE_RE.finditer(text):
        day, month = int(m.group(1)), int(m.group(2))
        y = int(m.group(3)) if m.group(3) else year
        if y < 100:
            y += 2000
        # Год из опечатки («06.11.20226») не должен уводить дату
        # в прошлый семестр — иначе настоящая дата теряется.
        if not (year - 1 <= y <= year + 1):
            y = year
        try:
            return datetime.date(y, month, day)
        except ValueError:
            continue
    return None
```

С `year = 2026` это даст `2026-11-06` — верную дату начала переноса.

**Отдельно:** сейчас теряется вторая дата (`18.11.2026`) — целевая
дата переноса. Это осознанное упрощение (одна ячейка = одна замена),
но стоит его зафиксировать комментарием, чтобы не выглядело багом.

## Как проверить

```python
def test_typo_year_does_not_break_date():
    """«06.11.20226» — опечатка; дата должна остаться в текущем году."""
    assert vuz.parse_date("06.11.20226. - перенос", 2026) == datetime.date(2026, 11, 6)

def test_two_digit_year_still_works():
    """«06.11.26» — сокращённый год, должен разбираться как 2026."""
    assert vuz.parse_date("06.11.26", 2026) == datetime.date(2026, 11, 6)
```

Вживую: после фикса `substitution` не должна содержать `2022-11-06`.

## Риски

- **`year ± 1` — проверено, безопасно.** Прогнал все 11 листов:
  явно указанных годов ровно два — `2026` (139 раз) и `2022`
  (1 раз, та самая опечатка). Дат без года — 791, они берут год из
  шапки. То есть следующий календарный год в файле не встречается,
  и расширять окно не нужно.
- **Молчаливая подмена года** скрывает опечатку от админа. Правильнее
  было бы писать `log.warning` при подмене — тогда такие ячейки видны
  в логе, и источник можно поправить.
- **Мусорные строки останутся.** После фикса новые не появятся, но две
  старые (`2022-11-06`) надо удалить руками или миграцией.
