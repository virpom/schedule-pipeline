# План 133: частичный сбой синхронизации не доходит до админа

> **УСТАРЕЛ 28.10.2026.** Механизм уже стоит: `_step` копит
> `failed`, поллер вызывает `_report_partial_failure` с ключом
> `partial`, отдельно есть `_report_parse_failure`. Проверено на
> проде: `last_sync_ok` свежий, `alert_hash_*` пусты, «Листок
> замен» снова отдаёт 200 (2.5 МБ).

**Приоритет:** средний. Прямо сейчас в проде 6 часов не работает
синхронизация замен, и админ об этом не знает.

**Трудоёмкость:** S (~15 строк).

## Живой случай

Проверил только что на проде:

```
ochoe          HTTP 200, 52550 байт
zameny         HTTP 404,  162 байт   <-- файл удалён с сайта
bells_monday   HTTP 200, 16032 байт
bells_standard HTTP 200, 15989 байт
```

`Листок замен.docx` отдаёт 404 уже **6 часов**. `last_sync_ok` застыл
на `2026-10-26T15:48:12`, `substitution` для колледжа не обновлялась
с 23 октября (96 строк).

## Как это обрабатывается сейчас

`sync_once` (`sync_eios.py:245`) оборачивает каждый шаг:

```python
async def _step(name: str, coro) -> None:
    try:
        await coro
    except Exception as exc:
        log.warning("не удалось обновить %s: %s", name, exc)
        failed.append(name)
```

404 попадает в `except`, пишется `failed = ["замены"]`, и в конце:

```python
if failed:
    changed["failed"] = failed
```

Возвращается результат, `poller.py:105` пишет:

```python
elif result and result.get("failed"):
    logging.warning("частичный сбой синхронизации: %s", result["failed"])
```

**И всё.** Никакой тревоги.

## Почему тревоги нет

`_report_failure` (`poller.py:17`) вызывается **только** в ветке полного
падения:

```python
try:
    result = await sync_eios.sync_once(session, repo, config)
except Exception as e:
    logging.warning("ЭИОС недоступен: %s", e)
    result = None
    await _report_failure(bot, session_pool, config, e)   # <- только здесь
```

Частичный сбой исключения не бросает — `_step` его проглотил. Значит
`_report_failure` не зовётся, `alerts.alert` не зовётся.

Проверил состояние тревог в базе:

```
alert_structure = ''
alert_site      — не существует (ни разу не слали)
```

**Ни одной тревоги за всё время**, при том что замены сломаны 6 часов.

## Что админ видит сейчас

`/stats` показывает:

```
⚠️ ЭИОС колледжа не отвечает (успех: с 26.10 15:48)
✅ Вуз: 26.10 21:57
```

Это **лучше, чем ничего**, но текст неверен: ЭИОС **отвечает**, 52550
байт очного расписания скачались. Не работает один файл из четырёх.

И главное — `/stats` надо **открыть**. Тревога приходит сама, сводка
нет.

## Что сделать

Тревожить админа и на частичный сбой. В `poller.py` после проверки
`result`:

```python
elif result and result.get("failed"):
    logging.warning("частичный сбой синхронизации: %s", result["failed"])
    async with session_pool() as db:
        await alerts.alert(
            bot, RequestsRepo(db), config, "partial",
            "Часть файлов не обновилась: "
            + ", ".join(result["failed"])
            + "\n\nОстальное расписание работает. Если файл удалён "
              "с сайта — замены не подтянутся, пока его не вернут.",
        )
```

И снимать тревогу, когда сбой прошёл:

```python
if result is not None and not result.get("failed"):
    ...
    await alerts.clear(bot, repo, config, "partial", "Все файлы снова обновляются.")
```

`alerts.alert` уже умеет не спамить: хранит хеш текста в `setting`
и молчит, пока текст тот же (`alerts.py:36`). То есть при 404 каждые
5 минут админ получит **одно** сообщение, а не 288 в сутки.

## Что проверил и признал корректным

**Разделение свежести колледж/вуз работает.** Проверил живьём:

```
колледж: is_stale=True,  last_ok=2026-10-26 15:48:12
вуз:     is_stale_vuz=False, last_ok_vuz=2026-10-26 21:57:10
```

Студент вуза не видит чужую проблему — это была отдельная правка,
она держится.

**Студент колледжа предупреждён.** `is_stale` = True, значит
`_day_text` добавит:

```
⚠️ Сайт колледжа не отвечает с 26.10 15:48. Замены с тех пор
не проверены — они могли появиться.
```

Формулировка тоже неточна (сайт отвечает), но пользователь хотя бы
знает, что замены не проверены.

**`mark_ok` не вызывается при частичном сбое — это правильно.**
`poller.py:103` требует `not result.get("failed")`. Значит `is_stale`
честно показывает проблему. Логика верная, не хватает только
уведомления.

**Материализация продолжается при сбое.** `poller.py:113` вызывается
всегда — окно дат сдвигается, расписание не «кончится» через две
недели. Правильно.

## Риски

- **`alerts.alert` использует хеш текста для дедупликации.** Если
  список сбойных файлов меняется (сегодня «замены», завтра «замены,
  звонки»), текст другой — придёт новое сообщение. Это желаемое
  поведение, но при нестабильном списке может стать шумно.
- **Тревога «частичный сбой» может маскировать полный.** Если сайт
  упал целиком, `_report_failure` пошлёт `structure`/`site`, а
  `partial` останется висеть с прошлого раза. Стоит снимать `partial`
  и в ветке полного падения.
