# План 071: тревога «структура сломалась» не срабатывает для расписания и замен

> **СДЕЛАНО 27.10.2026** (коммит `9df8ea4`).
>
> `_step` теперь ловит `EiosParseError` отдельно и копит `parse_failed`,
> формат `failed` не менялся — его читают три места в `poller.py`.
> В `poll_once` появился `_report_parse_failure` со своим ключом
> `structure`.
>
> Вторая часть тоже закрыта: сетевой сбой больше не снимает тревогу о
> структуре. `clear` вызывается только в ветке `elif not failed`, то
> есть когда разбор прошёл на всех файлах. Раньше мигающий сайт давал
> «проблема → восстановилось → проблема» каждый цикл.

**Приоритет:** высокий. Главный сценарий, ради которого писались тревоги,
не покрыт. Админ узнаёт о поломке парсера последним — или никогда.

**Трудоёмкость:** S (~8 строк).

## Проблема

`sync_eios.py:245` — каждый файл обновляется в изоляции:

```python
async def _step(name: str, coro) -> None:
    try:
        await coro
    except Exception as exc:  # noqa: BLE001
        log.warning("не удалось обновить %s: %s", name, exc)
        failed.append(name)
```

`except Exception` ловит **всё**, включая `EiosParseError`:

```python
if links.ochoe:
    await _step("очное расписание", _sync_ochoe(...))
if links.zameny:
    await _step("замены", _sync_zameny(...))
```

А `_report_failure` вызывается только из `poller.py:98` — когда
`sync_once` **бросил** исключение:

```python
except Exception as e:
    logging.warning("ЭИОС недоступен: %s", e)
    result = None
    await _report_failure(bot, session_pool, config, e)
```

## Карта: что реально доходит до тревоги

| Шаг | Обёрнут в `_step`? | Дойдёт до `_report_failure`? |
|---|---|---|
| `_fetch_links` | нет | **да** |
| `_sync_ochoe` (расписание) | **да** | нет |
| `_sync_zameny` (замены) | **да** | нет |
| `_download` звонков | нет | **да** |
| `parse_bells` | нет | **да** |

То есть `alert(kind="structure")` срабатывает **только для звонков**.
Если сайт поменяет структуру файла расписания или листка замен —
`EiosParseError` уйдёт в `failed`, и тревоги не будет.

## Почему это критично

Комментарий в `_report_failure` объясняет, зачем тревога вообще нужна:

> Изменившаяся структура сама не починится — нужен человек, иначе бот
> будет молча работать на старых данных, пока не кончится окно из
> 14 дней.

Именно этот сценарий и не покрыт. Бот продолжит отдавать старое
расписание, `is_stale` покажет «сайт не отвечает», и все — и админ, и
студенты — будут думать, что проблема в сети. А сайт жив, просто файл
другой.

## Что видит каждая сторона

**Админ:**

```
/stats → ⚠️ ЭИОС колледжа не отвечает (успех: 25.10 22:57)
```

Ни слова о структуре. Тревоги нет — `alert_structure` не менялся.

**Студент** (пока `last_ok` старше 30 минут):

```
⚠️ Сайт колледжа не отвечает с 25.10 22:57. Замены с тех пор не
проверены — они могли появиться.
```

Тоже про сеть. Хотя сайт отвечает и файлы скачиваются — не разбираются.

## Второй баг в том же месте: ложное «восстановилось»

`_report_failure` при **любой** не-parse ошибке вызывает `clear`:

```python
if isinstance(error, eios.EiosParseError):
    await alerts.alert(...)
else:
    await alerts.clear(bot, repo, config, "structure",
                       "Файлы снова разбираются.")
```

Ветка `else` — это сеть, таймаут, 5xx. Но она шлёт «Файлы снова
разбираются», хотя ничего не разбиралось и структура не менялась.

Сценарий:

1. Структура сломалась → `alert`, `alert_structure = <hash>`.
2. Сайт упал (сеть) → `clear`, `alert_structure = ""`, админу
   «✅ Восстановилось. Файлы снова разбираются.»
3. Сайт поднялся, структура всё ещё сломана → `alert` с тем же текстом,
   но ключ пуст, поэтому сообщение уходит **снова**.

Админ получает «проблема → восстановилось → проблема», хотя ничего не
восстанавливалось. При мигающем сайте это повторяется каждый цикл
(`poll_interval = 300`), и тревоги начинают игнорировать.

## Что сделать

**Часть 1 — прокинуть `failed` в тревогу.** `sync_once` уже собирает
список упавших шагов. Достаточно после него проверить, был ли там
именно parse-сбой:

```python
# poller.py, после sync_eios.sync_once
if result and result.get("failed"):
    failed = result["failed"]
    # Ошибка разбора — единственное, что само не пройдёт: сеть
    # восстановится, а структура файла — нет.
    if any("расписание" in f or "замены" in f for f in failed):
        async with session_pool() as db:
            await alerts.alert(
                bot, RequestsRepo(db), config, "structure",
                f"Файлы скачиваются, но не разбираются: {', '.join(failed)}.\n"
                f"Расписание работает на старых данных.")
```

Но это грубо: `failed` не говорит, **почему** шаг упал — сеть или
разбор. Лучше сохранить тип ошибки в `_step`:

```python
async def _step(name: str, coro) -> None:
    try:
        await coro
    except eios.EiosParseError as exc:
        log.warning("не разобрался %s: %s", name, exc)
        failed.append((name, "parse"))
    except Exception as exc:  # noqa: BLE001
        log.warning("не удалось обновить %s: %s", name, exc)
        failed.append((name, "network"))
```

Тогда в `poll_once`:

```python
parse_failed = [n for n, kind in (result.get("failed") or []) if kind == "parse"]
if parse_failed:
    await alerts.alert(bot, repo, config, "structure", ...)
```

**Часть 2 — не путать сеть с восстановлением.** В `_report_failure`
ветку `else` заменить на «ничего не делать»: сетевой сбой не должен
снимать тревогу о структуре.

```python
if isinstance(error, eios.EiosParseError):
    await alerts.alert(...)
# сеть/таймаут — молчим: тревога про структуру остаётся в силе,
# пока файлы снова не начнут разбираться
```

А `clear` вызывать только там, где разбор действительно прошёл — то
есть в ветке успеха `poll_once`, после `mark_ok`.

## Что учесть при правке

- **`changed["failed"]` читают три места**, все в `poller.py`
  (проверил `grep -n "failed" tests/ tgbot/`):

  ```
  poller.py:71   if vuz_result.get("failed"):        <- вуз, другой словарь
  poller.py:103  if result is not None and not result.get("failed"):
  poller.py:107  logging.warning(..., result["failed"])
  ```

  Тестов на формат `failed` нет. Но менять `list[str]` на список
  кортежей всё равно неудобно: строка 103 проверяет только
  непустоту (сработает), а 107 напечатает кортежи. Чище добавить
  отдельный ключ `changed["parse_failed"]` и не трогать существующий.
- **Тревога уже покрыта планом 028?** Нет. [План 028](028-alerts-underused.md)
  говорит «`alerts` покрывает 1 случай из 6» и предлагает добавить
  `alert` для `anchor_off`, `materialize`, `_rebuild`. Но он
  **не замечает**, что единственный существующий `alert` не получает
  главный случай — разбор расписания. Это разные дефекты: 028 про
  отсутствующие вызовы, этот — про то, что существующий вызов не
  достигается.
- **`_report_failure` всё ещё нужен** для `_fetch_links` и звонков —
  там `EiosParseError` доходит. Не удалять.

## Проверено и признано корректным

**`_step` глотает ошибки не зря.** Комментарий объясняет: «если листок
замен вернул 404, звонки всё равно должны обновиться. Иначе один битый
файл из трёх останавливает весь проход и сайт выглядит лежащим, хотя он
жив». Изоляция шагов правильная — проблема только в том, что результат
изоляции не доходит до тревоги.

**`mark_ok` не вызывается при `failed`** — верно, свежесть не
отмечается, если хоть что-то упало.

**Дедупликация в `alerts.alert`** работает: повтор с тем же текстом не
шлётся. Проблема не в ней, а в том, что `clear` сбрасывает ключ в пустую
строку и открывает дорогу повтору.

**Текст тревоги стабилен — спама не будет.** Проверил, что
`EiosParseError` даёт одинаковую строку на одинаковых данных:
`parse_ochoe(b'garbage')` дважды → `«Не удалось открыть xlsx: File is
not a zip file»`, побайтово равно. Пять из шести мест бросают
**статический** текст; три с `{exc}` подставляют сообщение библиотеки,
которое от прогона к прогону не меняется. Значит хеш в `alerts.alert`
не будет дёргаться сам по себе.

**Почему это не поймали тесты.** В `tests/test_alerts.py` семь тестов,
и все семь проверяют `alerts.py` **в изоляции** — отправку, дедуп,
`clear`, лимит длины. Ни одного теста на `_report_failure` нет
(`grep -rn "_report_failure" tests/` — пусто). Поэтому ошибка в
вызывающем коде живёт: модуль корректен, а вызывают его неправильно.

Тест, который её поймал бы, простой: `poll_once` с сетевой ошибкой
после `alert_structure != ""` должен **не** очищать ключ. Такой тест
надо добавить вместе с правкой.

## Риски

- **Правка контракта `failed`.** Если делать через отдельный ключ
  `parse_failed`, тесты не сломаются. Если менять формат — надо
  поправить `tests/test_sync_eios.py` и `poll_once:107`.
- **Слишком много тревог.** Если структура сломана надолго, `alert`
  шлёт один раз (дедупликация по хешу). Но если текст будет включать
  имя упавшего файла, а падают разные файлы по очереди — сообщения
  будут разные. Лучше фиксированный текст без списка имён, либо
  сортированный список.
