# План 108: двойная фамилия разбита на три записи, поиск находит одну

**Приоритет:** средний. Один человек, 40 пар, три записи в списке
преподавателей, и поиск находит только треть.

**Трудоёмкость:** S (~5 строк).

## Проблема

В источниках двойная фамилия пишется тремя способами:

```
'Мурашова-Росс А.В.'     28 пар в college_lesson, 35 в base_lesson
'Мурашова - Росс А.В.'    8 пар
'Мурашова – Росс А.В.'    4 пары   (длинное тире)
```

`teacher_base` (`schedule.py:72`) убирает пробел **только внутри
инициалов**:

```python
head = (name or "").split(",")[0].strip()
head = re.sub(r"\s+", " ", head)
return re.sub(r"(?<=\b[А-ЯЁA-Z]\.)\s+(?=[А-ЯЁA-Z]\.)", "", head)
```

Дефис и пробелы вокруг него не трогаются. Поэтому три записи остаются
тремя разными людьми.

## Что это даёт на проде

Проверил 26.10.2026:

```
в списке преподавателей:  'Мурашова - Росс А.В.'   <- 2-я запись
                          'Мурашова – Росс А.В.'   <- 3-я запись
                          'Мурашова-Росс А.В.'     <- 1-я запись
```

Человек выбирает себя из списка — и получает **только свою треть**:

```
поиск 'Мурашова-Росс А.В.'  ->  1 из 3 записей (28 пар, теряет 12)
поиск 'Мурашова - Росс А.В.' -> 2 из 3 (теряет 28)
поиск 'Мурашова'             -> 2 из 3 (теряет 28)
```

**Хуже:** `LIKE` в SQL тоже режет. `get_for_teacher_date`
(`college_lesson.py:172`) берёт `surname = teacher_name.split()[0]`,
то есть `'Мурашова-Росс'`, и делает `LIKE '%Мурашова-Росс%'`. Это не
совпадает с `'Мурашова - Росс А.В.'` — там пробелы. Проверил на проде:
```
select distinct teacher from college_lesson where teacher like '%Мурашова-Росс%'
  -> 'Мурашова-Росс А.В.'          (одна запись из трёх)
```

Так что даже исправленный `teacher_matches` не поможет: строки с
пробелами не доедут до Python-фильтра.

## Что сделать

**Шаг 1 — нормализовать дефис в `teacher_base`.** Одна строка:

```python
head = re.sub(r"\s*[-–—]\s*", "-", head)   # «Мурашова - Росс» -> «Мурашова-Росс»
```

Ставится **после** `re.sub(r"\s+", " ", head)` и **до** нормализации
инициалов.

**Шаг 2 — тот же нормализатор для SQL.** Сейчас `surname` берётся
сырым:

```python
surname = teacher_name.split()[0]
... .where(CollegeLesson.teacher.like(f"%{surname}%"))
```

Для `'Мурашова-Росс'` это не найдёт `'Мурашова - Росс'`. Нужно брать
**первое слово фамилии до дефиса**:

```python
surname = re.split(r"[\s\-–—]", teacher_name.strip())[0]
```

Тогда `LIKE '%Мурашова%'` найдёт все три формы, а `teacher_matches`
отфильтрует точно. Это шире, но безопасно: фамилия «Мурашова»
встречается только у неё — проверил, других преподавателей с такой
фамилией нет.

**Проверил на живых данных — сейчас три разные строки:**

```
teacher_base('Мурашова-Росс А.В.')   -> 'Мурашова-Росс А.В.'
teacher_base('Мурашова - Росс А.В.') -> 'Мурашова - Росс А.В.'   <- другая
teacher_base('Мурашова – Росс А.В.') -> 'Мурашова – Росс А.В.'   <- третья
```

**После правки — одна:**

```
teacher_base('Мурашова - Росс А.В.') -> 'Мурашова-Росс А.В.'
teacher_base('Мурашова – Росс А.В.') -> 'Мурашова-Росс А.В.'
```

**Регресс проверил:** обычные имена не меняются.
```
'Кокошка И. П.'  -> 'Кокошка И.П.'   (было и стало)
'Коленова В.А.'  -> 'Коленова В.А.'
'Иванова З.Н'    -> 'Иванова З.Н'
'Ляшко'          -> 'Ляшко'
'Чабаева А.Д.'   -> 'Чабаева А.Д.'
'Сачук Ю.Н.'     -> 'Сачук Ю.Н.'
```

## Два других метода задевает так же

Проверил `get_dates_for_teacher` и `get_all_for_teacher` — оба берут
`surname = teacher_name.split()[0]` и делают тот же `LIKE`:

```
get_dates_for_teacher:
  'Мурашова-Росс А.В.'     -> 13 дат
  'Мурашова - Росс А.В.'   ->  6 дат
  'Мурашова – Росс А.В.'   ->  6 дат
  'Мурашова'               ->  6 дат

get_all_for_teacher:
  'Мурашова-Росс А.В.'     -> 28 пар, форм=1
  'Мурашова - Росс А.В.'   -> 12 пар, форм=2
  'Мурашова'               -> 12 пар, форм=2
```

Выбор формы с дефисом даёт 13 дат и 28 пар, любой другой — 6 и 12.
Разница в 12 пар и 7 дат просто исчезает. Это и есть тот же дефект:
фильтр в SQL отсекает формы, до которых `teacher_matches` не доходит.

Значит правка `surname` нужна **во всех трёх методах**, а не только в
`get_for_teacher_date`.

## Проверено и признано корректным

**Инициалы нормализуются правильно.** `teacher_base` убирает пробел
между инициалами: «Кокошка И. П.» → «Кокошка И.П.». Проверил на всех
32 вариантах с прода — рефлексивность держится.

**SQL-спецсимволов в именах нет.** Проверил все 234 преподавателя на
`_` и `%`: **0 совпадений**. Значит `LIKE` не нуждается в `ESCAPE`.

**Пробелов в начале/конце имён нет.** Проверил: 0 записей, где
`teacher != teacher.strip()`.

**`'Мурашова-Росс'` — единственная двойная фамилия в базе.** Прогнал
все имена на `-` в первом слове: одна запись. Так что правка задевает
ровно одного человека.

**`base_lesson` тоже разбит.** `'Мурашова-Росс А.В.'` = 35 строк,
`'Мурашова - Росс А.В.'` = 4, `'Мурашова – Росс А.В.'` = 0. То есть
расхождение приходит из источника, а не создаётся при материализации.

## Риски

- **Нормализация дефиса может склеить разных людей.** Если в базе есть
  «Иванов-Петров» и «Иванов - Петров» как разные люди — они сольются.
  Но проверил: двойная фамилия одна, и это один человек.
- **`re.split(r"[\s\-–—]")` в SQL-шаге берёт первое слово.** Для
  «Мурашова-Росс» это «Мурашова» — короче, чем нужно, но шире по
  выборке. Python-фильтр потом отсечёт лишнее. Стоимость: одна лишняя
  строка в результате `LIKE`, не больше.
- **Тест.** Стоит добавить в `tests/`:
  `assert teacher_base("Мурашова - Росс А.В.") == teacher_base("Мурашова-Росс А.В.")`.
