# План 128: `docs/SOURCE-EIOS.md` — правило чётности стоит на двух точках

**Приоритет:** средний. Не дефект кода, а **непроверенное допущение**,
на котором держится вся выдача расписания.

**Трудоёмкость:** S (добавить проверку, ~20 строк теста).

## Что утверждает документ

`docs/SOURCE-EIOS.md:286`:

```
## 4. 🔴 Чётность недели НЕ совпадает с ISO

**Обе даты инвертированы.** Гипотеза `parity = (ISO_week + 1) % 2`
подтверждается на обеих:

| Дата | ISO+1 | Совпадает с колледжем |
|---|---|---|
| 2026-10-24 | 44 → чётная | ✅ |
| 2026-10-26 | 45 → нечётная | ✅ |

**Вывод:** в `week_parity()` нужен `parity_offset=1`, либо иной механизм.
Но двух точек мало для уверенности — **нужно накопить больше наблюдений**.
```

Документ сам признаёт: **две точки — мало.**

## Сколько накопилось за три дня

Проверил базу:

```
substitution source='site':  2 даты, 96 записей
даты: 2026-10-24, 2026-10-26
```

**Ровно те же две даты.** Больше не появилось — и не могло: файл
`Листок замен.docx` отдаёт 404 с 15:53 сегодняшнего дня. Новые
наблюдения не поступают.

То есть правило `PARITY_OFFSET = 1` (`schedule_layer.py:14`) до сих
пор проверено на двух точках, как и в день открытия.

## Почему это важно

`week_parity()` определяет, **какие пары показывать студенту**. Если
offset неверен, весь колледж видит расписание чужой недели — не
ошибку в одной паре, а половину предметов.

Проверил, что сейчас всё согласовано:

```
группа АТ-26
  2026-10-26: слой=3 пар, college_lesson=3, совпадает=True
  2026-10-27: слой=4 пар, college_lesson=4, совпадает=True
```

Слой и материализация дают одно и то же. Но оба используют **один и
тот же** `week_parity` — совпадение доказывает только внутреннюю
непротиворечивость, не верность относительно колледжа.

## Чем можно проверить независимо

**Верх/низ ячейки xlsx** — независимый источник. Документ сам его
описывает (`:89-130`):

```
#### Случай B — ячейка НЕ объединена, 38+15 штук
верхняя (TOP)  -> чётная неделя
нижняя  (BOT)  -> нечётная неделя
```

Доказательство тоже построено на заменах 26.10 — то есть **на том же
единственном наблюдении**. Круг замкнулся: обе «независимые» проверки
опираются на одну дату.

## Что сделать

**1. Зафиксировать проверку тестом на фикстуре.** Взять `Очная
форма.xlsx`, найти группу с непустыми TOP и BOT, и проверить, что для
заведомо чётной даты `get_day_slots` возвращает TOP, а для нечётной —
BOT. Фикстура не зависит от листка замен.

**Но фикстуры для этого нет.** В `tests/fixtures/` лежат только
файлы вуза:

```
1-ochnoe.xls
2-ochno-zaochnoe.xls
```

`Очная форма.xlsx` колледжа в тестах отсутствует — `test_eios_parser.py`
не грузит файлы вообще. Значит сначала надо положить фикстуру
(52 550 байт), и только потом писать тест.

```python
def test_parity_matches_xlsx_top_bottom():
    # ДП-26, среда, 1 пара: TOP и BOT — разные предметы
    # 2026-10-21 (ISO 43, offset 1 -> 44) -> чётная -> TOP
    # 2026-10-28 (ISO 44, offset 1 -> 45) -> нечётная -> BOT
```

**2. После починки файла замен — сверить новые даты.** Когда
`Листок замен.docx` вернётся, первые же замены на новую дату дадут
третье независимое наблюдение.

**3. Записать в документе текущее состояние.** Сейчас `:311` говорит
«нужно накопить больше наблюдений» — это честно, но читатель не знает,
что с 26.10 накопление остановилось.

## Что проверил и признал верным

**Правило работает на известных датах:**

```
2026-10-24 Суббота     ISO 43 -> EVEN   (колледж: чётная) ✅
2026-10-26 Понедельник ISO 44 -> ODD    (колледж: нечётная) ✅
2026-10-27 Вторник     ISO 44 -> ODD
2026-11-02 Понедельник ISO 45 -> EVEN
2026-11-09 Понедельник ISO 46 -> ODD
```

**Числа объёма почти сошлись.** Документ (`:187`, на 23.10):
37 групп, 658 пар, 65 преподавателей. Проверил сейчас: **37 групп,
704 пары, 63 преподавателя**. Групп ровно столько же; пар стало больше
на 46 — файл обновился за три дня; преподавателей на 2 меньше —
возможно, переименование или уход. Расхождение объяснимое.

**Заочка не подключена — и это правильно.** `eios.py:153` извлекает
`zaochnoe` из страницы, но `sync_eios.py` его не читает: используются
только `ochoe` и `zameny`. Документ (`:432`) фиксирует решение
«заочку пока не берём». Проверил: файл при этом **доступен** — HTTP
200, 50 139 байт, сигнатура `PK\x03\x04` (настоящий docx). То есть
подключить её можно, когда дойдут руки; сейчас это осознанный пропуск,
а не поломка.

**Структура xlsx описана верно.** Случай A (объединённая ячейка, одна
пара на обе недели) и случай B (две строки — две недели) — парсер
`parsers/eios.py` реализует именно так (`_cell_lessons`, `split_by_weeks`).

## Риски

- **Тест на TOP/BOT может оказаться тавтологией.** Если фикстура
  взята из того же файла, что парсит прод, и парсер написан по тому же
  допущению — тест подтвердит допущение, а не реальность. Единственная
  настоящая проверка — новая дата из листка замен.
- **`PARITY_OFFSET = 1` может сломаться при смене семестра.** Сдвиг на
  1 подразумевает, что колледж нумерует недели иначе с начала учебного
  года. В феврале правило может не действовать — документ этого не
  оговаривает.
