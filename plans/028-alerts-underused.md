# План 028: тревоги покрывают 1 случай из 6, `STALE_AFTER` не связан с интервалом

**Приоритет:** средний. Первое — почему админ узнаёт о поломках
последним; второе — предупреждение, которое привыкают игнорировать.

**Трудоёмкость:** S (~25 строк).

## Проблема 1: `alerts` умеет много, используется в одном месте

`alerts.py` — продуманный модуль: дедупликация по хешу текста, разные
`kind` не глушат друг друга, отдельное «восстановилось». Докстринг
обещает:

```
``kind`` — короткий ключ проблемы (``structure``, ``site``), чтобы
разные проблемы не глушили друг друга.
```

По факту вызов **один** (`poller.py:29`), и `kind="structure"`:

```python
if isinstance(error, eios.EiosParseError):
    await alerts.alert(bot, repo, config, "structure", ...)
else:
    await alerts.clear(bot, repo, config, "structure", ...)
```

Не покрыто ничем, кроме `logging`:

| Сбой | Где | Что видит админ |
|---|---|---|
| `VuzParseError` | `poller.py:84` | `logging.exception` в логе |
| частичный сбой колледжа | `poller.py:100` | `logging.warning` |
| `anchor_off` (якорь уехал) | `poller.py:80` | `logging.error` |
| падение `materialize` | `poller.py:120` | `logging.exception` |
| падение `_rebuild` | `editor.py:874` | ничего (проглочено) |
| сбой сети | намеренно | — (комментарий объясняет) |

Второй `kind`, который упомянут в докстринге (`site`), не используется
вообще.

**Почему это важно:** лог читают, когда уже сломано. Всё это — ровно
те случаи, когда расписание молча работает на старых данных, пока
студенты не начнут жаловаться. План 016 про VUZ — частный случай.

## Проблема 2: `STALE_AFTER` зашит, но зависит от `poll_interval`

`source_state.py:27`:

```python
# Сколько ждём, прежде чем считать данные устаревшими. Три интервала опроса
# по умолчанию (300 с) — запас на разовый сбой сети, но не на сутки.
STALE_AFTER = datetime.timedelta(minutes=30)
```

Комментарий сам говорит «три интервала по умолчанию», то есть константа
выведена из `poll_interval = 300`. Но `poll_interval` настраивается
через `/setpoll` и **не ограничен сверху** (план 026, п.4).

```
/setpoll 3600   -> интервал 60 мин > STALE_AFTER 30 мин
                -> между опросами is_stale() почти всегда True
                -> каждый экран показывает «данные устарели»
                -> студенты привыкают игнорировать предупреждение
```

Порог срабатывания даже без злого умысла: `/setpoll 1800` — ровно
граница.

```python
async def stale_after(repo: RequestsRepo) -> datetime.timedelta:
    """Порог устаревания — три интервала опроса, но не меньше 30 минут."""
    interval = int((await repo.settings.get_all()).get("poll_interval") or 300)
    return datetime.timedelta(seconds=max(interval * 3, 1800))
```

И в `is_stale` / `is_stale_vuz` использовать её вместо константы.

## Как проверить

```python
def test_alert_on_vuz_parse_error():
    """Поломка парсера вуза должна дойти до админа, а не остаться в логе."""

def test_stale_threshold_follows_poll_interval():
    """При /setpoll 3600 данные не считаются устаревшими сразу после опроса."""
```

Вживую: `/setpoll 3600` → экран не должен показывать «устарело»
сразу после успешной синхронизации.

## Риски

- **Больше тревог — больше шума.** Дедупликация по хешу текста спасает
  от спама одинаковыми сообщениями, но разные тексты (например, разные
  группы в ошибке) пройдут. Стоит проверить, что тексты стабильны.
- **`max(interval * 3, 1800)`** — при `poll_interval = 86400` порог
  станет трое суток, и предупреждение перестанет быть полезным. Это
  следствие отсутствия верхней границы в `/setpoll`; чинить там
  (план 026), а не здесь.
- **`repo.settings.get_all()` в `is_stale`** — лишний запрос на каждый
  экран. Сейчас `is_stale` вызывается в `_day_text` (раз на экран);
  кэшировать не стоит, но знать.
