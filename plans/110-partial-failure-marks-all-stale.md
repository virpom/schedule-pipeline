# План 110: один битый файл помечает устаревшим всё расписание

**Приоритет:** высокий. Прямо сейчас, в 20:45, **все студенты колледжа**
(233 подписчика, из них 37 колледжных групп) видят в каждом ответе
«сайт не отвечает», хотя их расписание обновляется нормально.

**Трудоёмкость:** S (~8 строк).

## Что происходит

С 15:53 сайт отдаёт **404 на файл замен** (план 105). Остальные четыре
файла живы. `_step` в `sync_eios.py:245` ловит ошибку и складывает имя
шага в `result["failed"]`.

`poller.py:103`:

```python
if result is not None and not result.get("failed"):
    async with session_pool() as db:
        await source_state.mark_ok(RequestsRepo(db))     # <- :105
elif result and result.get("failed"):
    logging.warning("частичный сбой синхронизации: %s", result["failed"])
```

`mark_ok` **не вызывается**, если упал хотя бы один файл.

## Что из этого следует

`last_sync_ok` застыл на `2026-10-26T15:48:12`. `STALE_AFTER` = 30 минут
(`source_state.py:26`), значит `is_stale()` возвращает `True` уже
**пять часов**.

`user.py:668` дописывает предупреждение в каждый ответ:

```python
if stale and last_ok is not None:
    text += format_stale_warning(last_ok)
```

Студент видит:

```
📅 Понедельник, 26 октября

1) Математика
   Иванова З.Н. · 201
...

⚠️ Сайт колледжа не отвечает с 26.10 15:48.
Замены с тех пор не проверены — они могли появиться.
```

## Проверил: расписание при этом свежее

```
last_sync_ok        = 2026-10-26T15:48:12    <- застыло
last_sync_ok_vuz    = 2026-10-26T20:45:25    <- живое

eios_hash_ochoe     = f57d998d...   (обновляется)
eios_hash_zameny    = aa67e550...   (обновляется)

college_lesson: 26.10 = 269 строк, 27.10 = 297, 28.10 = 282
substitution:   последняя запись 11:34:12, 247 строк — застыло
```

Постоянное расписание обновляется каждый цикл. Застыли **только
замены** — ровно то, о чём предупреждение и говорит. Но текст
утверждает больше: «сайт не отвечает». Сайт отвечает.

## Что это стоит

**37 колледжных групп × каждый просмотр расписания** — ложная тревога.
Студент не может отличить реальную проблему от этой, потому что текст
всегда один и тот же. Через неделю он перестанет читать
предупреждение — и пропустит настоящее.

Это классическая ошибка: индикатор, который горит всегда, не
индикатор.

## Что сделать

Различать «данные не обновились» и «сайт недоступен». Частичный сбой —
это первое, но не второе.

**Минимальная правка в `poller.py`:**

```python
ALL_STEPS = {"очное расписание", "замены"}

if result is not None:
    failed = set(result.get("failed") or [])
    async with session_pool() as db:
        repo = RequestsRepo(db)
        # Сайт отвечает, если доехал хоть один файл. Когда упали все —
        # это уже недоступность, и свежесть отмечать нельзя.
        if failed != ALL_STEPS:
            await source_state.mark_ok(repo)
    if failed:
        logging.warning("частичный сбой синхронизации: %s", sorted(failed))
```

**Почему не просто «убрать условие».** Проверил `sync_once`
(`sync_eios.py:227`): при полном обрыве `_fetch_links` (`:239`) бросает
исключение — `result` будет `None`, это ловится. Но если сайт жив, а
упали **все три файла** (например, поменялись ссылки), `result` вернётся
с `failed` = все имена, а не `None`. Наивная правка «отмечать всегда,
когда `result is not None`» в этом случае соврёт.

**Ещё одна дыра, которую стоит закрыть заодно.** Звонки
(`sync_eios.py:261-263`) **не обёрнуты в `_step`**:

```python
if links.bells_monday:
    data = await _download(session, links.bells_monday)      # <- не ловится
    slots += await asyncio.to_thread(eios.parse_bells, data, "MONDAY")
```

Если звонки упадут, исключение вылетит из `sync_once` целиком —
`result` станет `None`, и очное расписание, уже записанное в базу,
потеряет отметку свежести. Обернуть в `_step` так же, как остальные.

**Что при этом теряется:** предупреждение о том, что замены не
обновлялись. Оно уходит. Но правду о заменах должен говорить план 105 —
отдельной тревогой админу, а не ложным «сайт лежит» студенту.

## Проверено и признано корректным

**`schedule_file.content_hash` — не хэш, а флаг.** Проверил все 23
строки: с 02.10 по 08.10 лежат настоящие sha256 (старый парсер), с
23.10 по 08.11 — `eios-2026-10-23`. `sync_eios.py:469` пишет дату
вместо хэша. Но `content_hash` нигде не сравнивается: единственное
использование — `get_hash(date) is not None` (`user.py:674`). Значит
это флаг «день опубликован», и работает он верно. Имя столбца
вводит в заблуждение, поведение — нет.

**Три «опубликованных, но пустых» дня — воскресенья.** Проверил
25.10, 01.11, 08.11: все `isoweekday() == 7`. Пар нет, флаг стоит —
корректно.

**`schedule_editor` здоров.** Обе записи активны, `user_id` —
первичный ключ, дублей быть не может. Проверил схему.

**Групповые чаты — не дефект.** `chats` пуста, но механизм полный:
админ-команда (`admin.py:395`), хранение, рассылка (`poller.py:210`).
Ни один чат не подключён — невостребованная функция, не поломка.

## Риски

- **После правки реальный обрыв замен станет невидимым студенту.**
  Сейчас он хотя бы видит что-то. Убирая предупреждение, нужно
  закрыть план 105, иначе замена молчания на молчание.
- **`ALL_STEPS` нужно держать в синхроне с `_step`.** Если появится
  четвёртый файл, а константу не обновят, условие «упали все» станет
  неверным. Надёжнее сверять с длиной списка ссылок, но это уже
  переделка `sync_once`. На первое время хватит константы с
  комментарием.
- **Звонки вне `_step` — отдельный дефект.** Правка выше его только
  упоминает. Если не обернуть, падение звонков обнулит `result` и
  перечеркнёт всю остальную работу прохода.
