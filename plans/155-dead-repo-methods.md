# План 155: четыре мёртвых метода в репозиториях

> **СДЕЛАНО 28.10.2026** (коммит `f28667f`). count_dates удалён, остальные три пункта закрыты раньше.

**Приоритет:** низкий. Ничего не ломает, но каждый читатель кода тратит
время на разбор того, что никогда не выполняется.

**Трудоёмкость:** S (~15 минут, удаление).

## Что нашёл

Проверил grep'ом каждый публичный метод репозиториев на вызовы в
`tgbot/`, `infrastructure/`, `common/`.

### 1. `CollegeLessonRepo.count_dates` (`college_lesson.py:127`)

```python
async def count_dates(self) -> int:
    result = await self.session.execute(select(func.count(func.distinct(CollegeLesson.date))))
    return result.scalar_one()
```

**Вызовов в проде: 0.** Рядом живёт `get_latest_date` — он используется
трижды в `admin.py` (`:554`, `:636`, `:659`).

### 2. `SubstitutionRepo.get_dates` (`substitution.py:60`)

**Вызовов в проде: 0.** Только тесты: `test_sync_eios.py:358`, `:377`,
`test_poller_vuz.py:47`.

Докстринг говорит:

```
"""Даты, на которые есть замены, начиная с указанной.

Нужно для рассылки: листок замен выдаётся сразу на несколько дней
вперёд (например, на субботу и понедельник), и уведомлять надо про
каждую из этих дат, а не про фиксированное окно «сегодня + 2 дня».
"""
```

**Докстринг устарел.** Рассылка перешла на `digest_by_date`, и
`poller.py:139` прямо объясняет почему:

```
# Материализация применяет и замены, и базовое расписание, поэтому
# отпечаток даты ловит изменения из обоих источников. Отдельный
# список дат замен больше не нужен: дата без замены тоже бывает
# изменённой, и пересечение с get_dates() её бы выбросило.
```

То есть метод не просто не используется — он **сознательно заменён**,
и докстринг об этом не знает.

### 3. `NoLessonsRepo.replace_date` (`no_lessons.py:16`)

**Вызовов в проде: 0.** Файл 21 строка, из них 11 — этот метод.

Заменяет строки `no_lessons` на дату. Никто не зовёт. Таблица
`no_lessons` на проде — **4 строки**, заполнена вручную и больше не
меняется.

План 141 уже отмечал, что таблица мёртвая. Здесь — что **метод записи**
в неё тоже мёртвый.

### 4. `DaySnapshotRepo` — нет метода чтения

```python
class DaySnapshotRepo(BaseRepo):
    async def save(...)   # пишет
    async def exists(...) # проверяет наличие
```

**Чтения нет вообще.** `403` строки в `day_snapshot` пишутся и никогда
не читаются. План 120 это описал; план 138 — что из-за этого история
показывает не то.

Дополнительно: план 120 в примере кода ссылается на
`repo.snapshots.get_dates(user.group)` — **такого метода не существует**.
Если кто-то возьмётся за план 120 буквально, получит `AttributeError`.

## Почему это стоит убрать

**Ложные ориентиры.** `get_dates` с докстрингом «нужно для рассылки» —
прямая ловушка. Человек, разбирающийся в рассылке, найдёт метод,
увидит докстринг и решит, что рассылка работает через него. На самом
деле нет.

**Тесты держат мёртвый код живым.** `get_dates` покрыт двумя тестами
(`test_sync_eios.py:358`, `:377`). Они зелёные, создают впечатление,
что метод нужен. Удаление метода потребует удалить и тесты — это
правильно, но требует решения.

**`DaySnapshotRepo` без чтения** — половина замысла. Либо достроить
(план 138), либо честно признать, что архив пишется в стол.

## Что сделать

```python
# infrastructure/database/repo/college_lesson.py
-    async def count_dates(self) -> int: ...

# infrastructure/database/repo/substitution.py
-    async def get_dates(self, since): ...

# infrastructure/database/repo/no_lessons.py
-    async def replace_date(self, date, rows): ...
```

И удалить `test_sync_eios.py:350-380` (два теста на `get_dates`),
`test_poller_vuz.py:47` (использует его в фикстуре).

**`DaySnapshotRepo`** не удалять — план 138 собирается его
использовать. Но добавить в план 120 пометку, что `get_dates` надо
написать, а не вызвать.

## Что проверил и признал корректным

**`get_latest_date` живой** — три вызова в `admin.py` (`:554`, `:636`,
`:659`), показывает «данные до ...» в админке.

**`get_all_lessons` живой** — один вызов, `user.py:924` (поиск
преподавателя). Дорогой (61 мс), но используется.

**`get_all_for_teacher` и `get_all_for_group` живые** — по одному
вызову в `subject_answer` (`user.py:900`, `:902`).

**`get_teachers_vuz` живой** — два вызова в `_teacher_letter_kb`.

**`_resolve_groups` не теряет замены** — проверил на проде: групп в
`substitution` 65, все 65 есть в `base_lesson`, потерь 0.

**`replace_substitutions` не стирает замены при сбое** — проверил
порядок: `_sync_zameny:298` сначала `_download` (при 404 бросает
исключение), потом `parse`, потом `replace`. До `delete` дело не
доходит. На проде 247 строк замен целы, `eios_hash_zameny` сохранён.

**`_merge_para_clash` теряет `room` и `group`** — проверил, но это
документированный shortcut: `room` у вуза пустой и до склейки (все 5
склеенных строк имеют `room=''`), а `group` в `materialize_day` берётся
из внешней переменной цикла, не из слота. Влияния на пользователя нет.

## Риски

- **Удаление `get_dates` потребует правки тестов** — три места. Если
  тесты задумывались как заготовка под план 120, лучше не удалять, а
  переписать докстринг.
- **`count_dates` может понадобиться** в `/stats` при следующей
  доработке. Проверил `_build_stats` (`admin.py:108`) — там
  `count_lessons()`, не `count_dates`.
