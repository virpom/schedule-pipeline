# План 039: история расписания теряется — `day_snapshot` пишется, но не читается

> **СДЕЛАНО 27.10.2026** (коммит `f76e076`), все три части.
>
> 1. `_hist_page` объединяет даты из `college_lesson` и архива;
>    `cb_hist_date` при пустом дне берёт снимок через `_snapshot_lessons`
>    (`SimpleNamespace` + обязательный `group`).
> 2. `save` пишет 8 полей вместо 4: добавлены `action`, `changed`,
>    `comment`, `para_end`, `time_note`. Без `action` отмена при чтении
>    выглядела бы как состоявшаяся пара.
> 3. `days_back` 3 → 14, пустые дни сохраняются.
>
> Проверено на проде: 503 снимка за 20–26.10, из них 20–22.10
> отсутствуют в `college_lesson` — теперь они видны в истории.
>
> Снимки, сохранённые до этой правки, содержат только 4 поля:
> `action` у них пустой, поэтому старая отмена (если попадёт в окно)
> покажется обычной парой. В текущем архиве отмен нет — проверено.

**Приоритет:** средний. Данные уже собираются, но недоступны — работа
делается впустую, а студент не может посмотреть прошедшие дни.

**Трудоёмкость:** M (~40 строк).

## Проблема

В проекте **две** таблицы истории, и они не связаны:

```
college_lesson   <- читает «История» (user.py:767, 771)
day_snapshot     <- пишет poller.py:237, НИКТО НЕ ЧИТАЕТ
```

`_hist_page` строит список дат так:

```python
if _is_teacher(user):
    dates = await repo.college_lessons.get_dates_for_teacher(user.teacher_name)
else:
    dates = await repo.college_lessons.get_dates_for_group(user.group)
past = sorted((d for d in dates if d < datetime.date.today()), reverse=True)
```

Только `college_lesson`. А `day_snapshot` — архив, который
`snapshot_past_days` пишет каждый час:

```python
async def snapshot_past_days(repo, days_back: int = 3) -> int:
    for delta in range(1, days_back + 1):
        date = today - datetime.timedelta(days=delta)
        ...
        slots = await get_day_slots(repo, group, date)
        if not slots:
            continue
        await repo.snapshots.save(date, group, slots)
```

Зачем: «если сайт обновит файл задним числом, история потерялась бы».

## Что это даёт на практике

Проверил прод. `college_lesson`:

```
2026-10-02  2026-10-03  2026-10-05  2026-10-06  2026-10-07  2026-10-08
2026-10-23  2026-10-24  ...дальше будущее
```

**Пробел 9–22 октября — 14 дней.** `day_snapshot` за тот же период:

```
2026-10-20: 34 группы
2026-10-21: 95 групп
2026-10-22: 107 групп
2026-10-23: 95 групп
2026-10-24: 72 группы
```

Три дня (20, 21, 22) **есть в архиве, но не видны в «Истории»**.
`payload` выглядит так:

```json
[{"para": 2, "subject": "Деловая культура",
  "teacher": "Молчанова Н.А.", "room": ""}, ...]
```

Данные пригодны для показа — не хватает только чтения. Но **`payload`
неполный**: `save` (`day_snapshot.py:12`) пишет четыре поля из восьми,
которые есть у `Slot`:

```python
payload = json.dumps([
    {"para": ..., "subject": ..., "teacher": ..., "room": ...}
    for l in lessons
])
```

Теряются `changed`, `action`, `comment`, `group`. Что это значит при
чтении архива:

- **Отменённая пара выглядит как обычная.** `get_day_slots` для
  `action == SUB_CANCEL` кладёт в слот `subject`/`teacher`/`room`
  **базовой** пары и ставит флаг в `action` (`schedule_layer.py:77`).
  В `payload` флага нет — при чтении отмена неотличима от пары.
- **Перенос (`add`) теряет признак** — та же причина.
- **Комментарий старосты теряется** — в `payload` его нет.
- **`group` нет** — это уже замечено ниже (строка про `group=user.group`).

Проверил на проде, насколько это уже проявилось: в архиве 403 снимка
за 20–24.10, отменённых пар (`action='cancel'`) в `substitution` — 22,
но ни одна не попала в архивный диапазон (они на 07.10). То есть
**дефект латентный**: как только архив начнут читать, первая же отмена
в его окне покажется как состоявшаяся пара.

Чинить стоит вместе с чтением: добавить в `save` четыре поля. Это
дешевле сделать до того, как архив начнут показывать студентам —
переписывать уже сохранённое будет нечем.

## Почему пробел возник

Это **не баг кода**, а простой бота. Контейнер запущен
`2026-10-25 13:49 UTC`, `restarts=0` — до этого он стоял.
`college_lesson` за 2–8 октября остался с прошлого периода работы,
23–24 октября — с периода перед текущим.

**Последствие реальное:** 9–19 октября потеряны навсегда. Их нет ни
в `college_lesson`, ни в `day_snapshot` — восстанавливать не из чего.
20–22 октября спасти ещё можно, они в архиве.

## Что сделать

**Часть 1 — читать архив в истории.** В `_hist_page` объединить
источники:

```python
dates = set(await repo.college_lessons.get_dates_for_group(user.group))
dates |= set(await repo.snapshots.get_dates_for_group(user.group))
past = sorted((d for d in dates if d < datetime.date.today()), reverse=True)
```

И в `cb_hist_date` — если в `college_lesson` на дату пусто, брать из
снимка:

```python
lessons = await _user_lessons(repo, user, date)
if not lessons:
    snap = await repo.snapshots.get(date, user.group)
    if snap:
        lessons = snap          # list[dict] вместо ORM-объектов
```

Тут есть тонкость: `_fmt` ждёт объекты с атрибутами
(`lesson.para`, `lesson.subject`). Проще обернуть dict в
`SimpleNamespace` — тогда `format_day` работает без изменений:

```python
from types import SimpleNamespace
lessons = [SimpleNamespace(**d, group=user.group)
           for d in json.loads(snap.payload)]
```

**`group=user.group` обязателен.** В `payload` поля `group` нет, и без
него `format_day` получает `grp=None` → `cg=None` → звонки берутся
по fallback `I_IV`. А у 2–3 курса 2-я пара заканчивается в **12:20**,
не в 12:40:

```
п2: I_IV=10:45–12:40, II_III=10:45–12:20   <- единственное отличие
```

Проверил рендером: без `group` студент 2 курса увидит `10:45–12:40`,
с `group` — правильное `10:45–12:20`. Разница 20 минут.

**Часть 2 — увеличить глубину архива.** `days_back=3` означает, что
если бот простоит 4 дня, дыра закроется навсегда. Разумнее 14 —
столько же, сколько вперёд материализуется `college_lesson`:

```python
async def snapshot_past_days(repo, days_back: int = 14) -> int:
```

Цена: первый прогон после простоя сохранит 14 дней × 129 групп =
до 1800 записей вместо 390. Разовая операция, дальше только
недостающие (есть `if await repo.snapshots.exists(date, group)`).

**Часть 3 — не терять пустые дни.** Сейчас:

```python
if not slots:
    continue        # пустой день не сохраняется
```

Из-за этого нельзя отличить «пар не было» от «бот не работал».
Правильнее писать пустой `payload` — тогда история честная:

```python
await repo.snapshots.save(date, group, slots)   # даже если []
```

## Проверено и признано корректным

**`snapshot_past_days` правильно читает слои.** Он зовёт
`get_day_slots` (`schedule_layer.py:42`), а тот собирает из
`base_lesson` + `substitution` — то есть фиксирует то, что было
актуально на момент снимка, а не копирует `college_lesson`. Это верно:
если сайт обновит файл задним числом, снимок сохранит прежнюю версию.

**`exists()` защищает от перезаписи.** `snapshots.save` использует
`on_conflict_do_update`, но вызывается только после `exists()` —
то есть первая запись дня не перезаписывается. Задумка верная:
история должна фиксироваться один раз.

**Воскресенья пропускаются осознанно** (`if date.isoweekday() == 7`).

**Замер на проде.** Архив остановился на пяти датах и дальше не растёт
вглубь:

```
2026-10-20   34
2026-10-21   95
2026-10-22  107
2026-10-23   95
2026-10-24   72
----------------
итого      403 записей, 119 групп
```

При этом `college_lesson` содержит **20 дат**. Всё, что раньше 20.10, не
попало в архив и уже не попадёт: `days_back=3` смотрит только на три
дня назад, а они уехали. Подтверждает часть 2 — глубины не хватает.

**Архив уже содержит данные, которых нет больше нигде.** Сверил
`payload` с живым `college_lesson` по всем 403 снимкам:

```
совпадает              104
расходится               0
нет в college_lesson   299
```

Расхождений ноль — снимки верные. А 299 отсутствуют потому, что за
**20, 21 и 22 октября** в `college_lesson` вообще нет строк:

```
2026-10-20    0 строк   ← в архиве 34 снимка
2026-10-21    0 строк   ← в архиве 95
2026-10-22    0 строк   ← в архиве 107
2026-10-23  110 строк   ← в архиве 95
```

То есть архив — **единственный** источник расписания за эти три дня.
`schedule_file` подтверждает разрыв:

```
02-08.10   md5-хэши (старый формат)
09-22.10   ничего
23.10-07.11  eios-<дата>
```

Бот не материализовал две недели. `snapshot_past_days` успел схватить
20–22.10, пока они были в его трёхдневном окне, — и это ровно тот
случай, ради которого архив заводили.

Именно поэтому «просто удалить мёртвый код» — неправильный вывод:
архив надо не удалять, а начать читать.

**Стоимость архива невелика.** 403 записи за 5 дней, `payload` ~300
байт → ~25 КБ/день, ~9 МБ/год. Для SQLite приемлемо.

## Риски

- **`SimpleNamespace` не имеет `changed`/`action`.** `format_day`
  читает их через `getattr(..., default)`, так что зачёркивания
  отменённых пар в архивной истории не будет. Это приемлемо: снимок
  хранит только `para, subject, teacher, room`. Если нужно точнее —
  расширять `save()`, но это уже переписывание архива.
- **`get_dates_for_group` придётся добавить в `DaySnapshotRepo`.**
  Сейчас там только `save` и `exists`.
- **Увеличение `days_back` до 14 замедлит первый тик** после деплоя:
  129 групп × 14 дней × запрос `get_day_slots` ≈ 1800 запросов.
  На проде один `get_day_slots` — единицы миллисекунд, то есть
  порядка 3–5 секунд разово. `bell_loop` и `poller_loop` в это время
  не блокируются (разные задачи), но лучше делать это не в
  `poller_loop`, а отдельной задачей при старте.
