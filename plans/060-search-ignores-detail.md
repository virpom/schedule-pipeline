> **СДЕЛАНО 27.10.2026** вместе с планом 037 (коммит `fd87e08`).
>

> этого плана — `group_answer` не принимал `user` — тоже сделана: обе
> сигнатуры получили `user`.
**Приоритет:** низкий. Текст подробности, не данные.

**Трудоёмкость:** S (~2 строки).

> **Поправка.** Это **тот же дефект**, что «Часть 1» в
> [плане 037](037-search-ignores-detail.md) — там уже разобрано, что
> `detail` не передаётся ни в `user.py:947`, ни в `user.py:978`, и что
> 52 человека из 227 видят не свой режим. Отдельный план не нужен,

> в 037 нет: `group_answer` не принимает `user` в сигнатуре.

## Проблема

`user.py:947` — поиск преподавателя:

```python
await message.answer(
    f"👨‍🏫 «{q}»:\n\n" + format_teacher_results(entries, bell, lunches),
    reply_markup=BACK_KB,
)
```

И `user.py:975` — поиск группы:

```python
await message.answer(
    f"👥 «{group}» — неделя:\n\n" + format_teacher_results(entries, bell, lunches),
    reply_markup=BACK_KB,
)
```

Оба не передают `detail`. Сигнатура (`common/schedule.py:334`):

```python
def format_teacher_results(entries, bell, lunches, detail: str = DETAIL_BRIEF) -> str:
```

Значит **всегда `DETAIL_BRIEF`** — без времени пар.

## Почему это заметно

У 26 человек в базе `bell_detail = 'full'`, ещё 26 — `'lunch'`. Проверил
распределение:

```
brief  ×175
lunch  ×26
full   ×26
```

Эти люди получают подробное расписание на экране дня — со временем
каждой пары — а в поиске то же расписание без времени. Один и тот же
день выглядит по-разному в двух экранах.

Пример: студент с `full` открывает «Сегодня» — видит «1 пара 09:00–10:35,
Математика». Нажимает «Преподаватель», ищет того же преподавателя —
видит «1 пара · Математика», без времени.

## Что сделать

Передать настройку пользователя:

```python
await message.answer(
    f"👨‍🏫 «{q}»:\n\n" + format_teacher_results(entries, bell, lunches, user.bell_detail),
    reply_markup=BACK_KB,
)
```

То же в `group_answer` — но там `user` не инжектится, надо добавить в
сигнатуру:

```python
async def group_answer(message: Message, repo: RequestsRepo, user: User, state: FSMContext):
```

Middleware уже инжектит `user` — проверено по `subject_answer` и
`teacher_answer`, где параметр есть.

## Проверено и снято: ложная находка про `matched[-12:]`

Заподозрил ошибку в `teacher_answer` (`user.py:938`):

```python
scope = upcoming if upcoming else matched[-12:]
```

Решил, что `matched` не отсортирован, и `[-12:]` берёт случайные
строки. Проверил репозиторий (`college_lesson.py:88`):

```python
async def get_all_lessons(self) -> list[CollegeLesson]:
    result = await self.session.execute(
        select(CollegeLesson).order_by(CollegeLesson.date, CollegeLesson.para)
    )
```

**Сортировка есть** — по дате, потом по паре. Значит `matched`
сохраняет порядок, и `[-12:]` действительно берёт последние по дате,
как и задумано. Находки нет.

Единственный побочный эффект: `[-12:]` может разрезать один день
посередине — покажет 12 пар из 13 за день. Мелочь, не баг.

## Проверено и признано корректным

**Производительность `get_all_lessons` не проблема.** Замерил на
проде:

```
get_all_lessons: 3927 строк за 64 мс
фильтр в Python: 4 строк за 2.4 мс
get_for_teacher_range: 4 строк за 3.2 мс
```

Загрузка всей таблицы в 20 раз медленнее точечного запроса, но 64 мс —
незаметно для человека. Переписывать на `get_for_teacher_range` не
обязательно. Хотя если таблица вырастет до 50 000 строк (при
материализации 14 дней это займёт годы), станет ~800 мс.

**Семантика поиска у `teacher_answer` отличается от
`get_for_teacher_range`,** но это не баг. `teacher_answer` ищет
подстроку в поле `teacher`:

```python
matched = [l for l in lessons if q.casefold() in (l.teacher or "").casefold()]
```

То есть по запросу «В.А.» найдёт «Коленова В.А.». `get_for_teacher_range`
использует `teacher_matches`, который сравнивает фамилию и инициалы
умнее. Для пользовательского поиска подстрока даже удобнее — можно
набрать «колен» и получить всех Коленовых.

**История: «Раньше» есть, «Новее» нет** — но масштаб мал. Проверил
прод: 8 прошедших дат, это 2 страницы по 5. Листать вглубь больше
одного раза не придётся. Найдётся, когда история накопится, но сейчас
не мешает.

**Комментарий в `_hist_page` честно объясняет пустую историю:**

> У вуза история короче: college_lesson материализуется вперёд на 14
> дней, а назад заполняется только по мере прошествия. Поэтому «Больше
> расписания нет» на первом заходе — норма, а не ошибка.

**Курсор истории в `callback_data`, а не в FSM** — комментарий:

> переживает рестарт и не путается, если человек листает с двух
> устройств.

Правильное решение: `MemoryStorage` теряет состояние при рестарте
(находка про FSM), а курсор в кнопке — нет.

## Риски

- **Добавление `user` в `group_answer`** меняет сигнатуру. Middleware
  инжектит — безопасно.
- **`detail='full'` увеличит длину ответа поиска.** Сейчас поиск
  возвращает до 5 дней. При `full` каждый день длиннее на ~4 строки
  времени. Лимит 4096 не близко (проверено в плане 058), но стоит
  проверить после правки.
