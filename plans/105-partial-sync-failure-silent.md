# План 105: 404 на файле замен не поднимает тревогу — бот молчит часами

**Приоритет:** высокий. Замены не обновлялись **8 часов** (11:34 → 19:49),
админ не узнал. Студенты видели устаревшие замены и не знали об этом.

**Трудоёмкость:** S (~15 строк).

## Что случилось

26.10.2026 в 15:53 по местному сайт колледжа удалил файл замен, оставив
ссылку на странице. Проверил в 19:49:

```
ochoe       200  52550 байт
zameny      404  ?            <- файла нет
zaoch       200  50139 байт
bells_mon   200  16032 байт
bells_std   200  15989 байт
```

`extract_links` честно достаёт URL со страницы — он там есть. Но
`_download` получает 404 и бросает `ClientResponseError`.

Дальше `_step` ловит исключение и **только логирует**:

```python
async def _step(name: str, coro) -> None:
    try:
        await coro
    except Exception as exc:  # noqa: BLE001
        log.warning("не удалось обновить %s: %s", name, exc)
        failed.append(name)
```

`sync_once` возвращает `{"failed": ["замены"]}`, `poll_once` пишет
`logging.warning("частичный сбой синхронизации: %s", ...)` — и всё.

**За 8 часов это повторилось 47 раз**, и ни одной тревоги.

## Почему тревога не сработала

`_report_failure` (`poller.py:16`) вызывается **только** когда
`sync_once` бросил исключение целиком:

```python
try:
    result = await sync_eios.sync_once(session, repo, config)
except Exception as e:
    result = None
    await _report_failure(bot, session_pool, config, e)
```

Частичный сбой возвращается нормальным `result`, а не исключением.
Значит `_report_failure` не зовётся никогда — даже когда не обновился
критичный файл.

Проверил на проде: `alert_structure` в `setting` — **пустая строка**.
Тревоги не было.

## Что это значит для студентов

`substitution` не менялась с `2026-10-26 11:34:12` (8 часов). В ней 15
будущих дат, ближайшая — сегодняшняя, 57 записей.

**Студент предупреждение видит — но текст неверный.** Проверил
цепочку: `source_state.is_stale()` при `STALE_AFTER = 30 минут`
(`source_state.py:26`) уже с 16:18 возвращает `True`, и
`user.py:668` дописывает:

```python
if stale and last_ok is not None:
    text += format_stale_warning(last_ok)
```

`format_stale_warning` (`common/schedule.py:303`) рисует:

```
⚠️ Сайт колледжа не отвечает с 26.10 15:48.
Замены с тех пор не проверены — они могли появиться.
```

Сайт **отвечает**: `ochoe`, `zaoch`, звонки — все 200. Не отвечает
один файл замен. Студент читает «сайт не отвечает» и думает, что
проблема на его стороне или у колледжа всё лежит. Это дезинформация,
хоть и в безопасную сторону.

## Что сделать

**Различать «сайт недоступен» и «один файл отдал 404».** Это разные
вещи: первое пройдёт само, второе — нет. `_step` уже знает имя шага;
нужно донести его до поллера.

Минимальная правка — в `poll_once`, после получения `result`:

```python
if result and result.get("failed"):
    logging.warning("частичный сбой синхронизации: %s", result["failed"])
    await alerts.alert(
        bot, repo, config, "structure",
        "Часть файлов не обновилась: "
        f"<code>{', '.join(result['failed'])}</code>\n\n"
        "Остальное расписание работает на последних данных. "
        "Если так больше суток — проверь страницу расписания: "
        "возможно, файл переименовали или убрали.",
    )
```

`alerts.alert` уже дедуплицирует по хешу текста (`alerts.py:36`) — 47
одинаковых сообщений не придут, придёт одно. Когда файл вернётся,
`_report_failure` вызовет `alerts.clear(...)` и админ узнает, что
отпустило.

**Но `_report_failure` сейчас зовёт `clear` только в ветке исключения.**
Нужно добавить `clear` и в успешную ветку:

```python
if result is not None and not result.get("failed"):
    ...
    await alerts.clear(bot, repo, config, "structure", "Файлы снова разбираются.")
```

## Проверено и признано корректным

**Остальные файлы живы.** Проверил все пять URL: `ochoe`, `zaoch`,
`bells_monday`, `bells_standard` отдают 200. Сломан только `zameny`.
Значит это не «сайт лёг», а «один файл убрали».

**`extract_links` не виноват.** Ссылка на странице есть, парсер её
достаёт правильно. Проблема в том, что за ссылкой ничего нет.

**Данные не потеряны.** `replace_substitutions` вызывается только
после успешного скачивания и разбора. При 404 до неё не доходит —
старые 247 записей целы. Проверил: `substitution` = 247, как и было.

**Материализация продолжает работать.** `poll_once` вызывает
`materialize` всегда, даже при сбое. `college_lesson` = 3927 строк,
20 дат, `max(date)` = 2026-11-07 — окно не сжалось.

**`source_state.mark_ok` не вызывается — и это правильно.** При
`result["failed"]` свежесть не отмечается, поэтому `is_stale()`
срабатывает через 30 минут. Студент получает предупреждение, хоть и с
неточным текстом. Проверил: с 16:18 (15:48 + 30 мин) `is_stale` =
`True`.

**Админ тревоги не получил — и это дыра.** `is_stale` читают только
`user.py` и `/stats` (`admin.py:159`). Никто не пишет админу сам.
Админ узнал бы, лишь открыв `/stats` вручную.

## Риски

- **Тревога на каждый временный 404.** Если сайт на минуту отдал 404
  при перезаписи файла, админ получит сообщение. Дедупликация спасает
  от повтора, но не от ложного срабатывания. Компромисс: слать тревогу
  только если сбой держится два цикла подряд (нужен счётчик в
  `setting`, как `site_down`).
- **`alert_structure` занят другой тревогой.** Сейчас этим ключом
  пользуется `EiosParseError` («структура изменилась»). Если слать оба
  в один ключ, они будут глушить друг друга по хешу. Стоит отдельный
  ключ — `alert_partial`.
