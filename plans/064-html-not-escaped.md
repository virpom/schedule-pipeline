# План 064: текст из редактора и с сайта не экранируется в HTML

**Приоритет:** высокий. Один символ `<` ломает экран дня у всей группы.

**Трудоёмкость:** M (~10 правок в двух файлах + тесты).

## Проблема

`main.py:56`:

```python
Bot(token, default=DefaultBotProperties(parse_mode="HTML"))
```

Весь бот отправляет сообщения в режиме HTML. Значит любой текст,
попавший в сообщение, интерпретируется как разметка.

Пользовательский текст приходит в двух потоках и **нигде не
экранируется**:

**1. Редактор — ввод старосты** (`editor.py:931`):

```python
async def on_subject(message: Message, repo: RequestsRepo, state: FSMContext):
    subject = (message.text or "").strip()
    if not subject:
        await message.answer("Напиши название предмета текстом.")
        return
    await state.update_data(subject=subject)
    ...
    await message.answer(
        f"{EDITOR_TITLE}\n\nПредмет: <b>{subject}</b>\n\n"
```

`on_teacher` (`:948`) и `on_room` (`:958`) делают то же самое.

**2. Парсеры — текст с сайта колледжа и вуза.** `format_day`
(`common/schedule.py:255`):

```python
line = f"{p}) <b>{time_str}</b>  {lesson.subject}{mark}"
```

`lesson.subject` — то, что распарсили с сайта или ввёл староста.
Никакого `html.escape`.

## Что произойдёт

Проверил на проде: сейчас в данных **0 вхождений** `<` и `&` — во всех
шести полях (`college_lesson.subject/teacher/room`,
`base_lesson.subject/teacher/room`). Поэтому проблема ещё не
проявилась. Но код к ней готов.

Сценарий 1 — староста вводит предмет с математикой:

```
Математика < 5
```

`format_day` даёт:

```
2) <b>09:50–10:35</b>  Математика < 5
```

Telegram отвечает:

```
BadRequest: can't parse entities: Unsupported start tag " 5" at byte offset ...
```

Сообщение **не отправляется вообще**. Студент группы видит ошибку
вместо расписания. Глобального обработчика нет (находка 25) — экран
зависает.

Сценарий 2 — на сайте колледжа переименовали предмет:

```
Физика & Химия
```

`&` без `;` — та же ошибка.

Сценарий 3 — намеренно или случайно валидный тег:

```
<b>Физика</b>
```

Отрендерится как жирный текст. Не опасно, но искажает данные: студент
видит не то, что в базе.

## Седьмое поле: `no_lessons.note`

Проверял список полей и нашёл ещё один источник, который план пропускал.
Староста может оставить заметку на пустой день — она хранится в
`no_lessons.note` (`String(256)`) и попадает в текст здесь
(`common/schedule.py:283`):

```python
def empty_day(date, note: str | None = None) -> str:
    text = f"{day_header(date)}\n\nЗанятий нет 🙌"
    if note:
        text += f"\n<i>{note}</i>"      # <- без escape
    return text
```

Ввод — `editor.py`, тот же путь, что и `on_subject`: `note = (message.text
or "").strip()`, без очистки. Значит `<` в заметке ломает разметку так
же, как `<` в предмете.

Замер на проде:

```
no_lessons: 4 строки
  ПРк-25  2026-10-07  «Занятий нет. Смотреть расписание на 08.10.2026»
  ЭК-25   2026-10-07  то же
  ЮР-25А  2026-10-07  то же
  ПРф-25  2026-10-08  то же
с '<' или '&': 0
макс. длина:   46 из 256
```

Дефект латентный, как и остальные шесть. В список правок добавить
`note=escape(note)` при записи и `escape` при выводе в `empty_day`.

## Почему это не косметика

Один староста, введя «С/х < 5 га», ломает расписание **всей группе**.
Откатить он не сможет — экран дня не открывается ни у кого, включая
его самого. Выбраться можно только через `/group` и повторный ввод.

Парсерный поток опаснее: там правка приходит с сайта, и никто её не
проверяет.

## Что сделать

**Экранировать при вставке, а не при отправке.** Проще и надёжнее —
на границе доверия, то есть там, где текст попадает в базу:

```python
from html import escape
```

В `on_subject`/`on_teacher`/`on_room` (`editor.py`):

```python
subject = escape((message.text or "").strip())
```

В `_save_base`/`_save_sub` — уже не нужно, они получают из FSM.

**В парсерах** — экранировать в `materialize`/`materialize_day`
(`sync_eios.py`), где данные ложатся в `college_lesson`:

```python
from html import escape
...
subject=escape(slot.subject),
teacher=escape(slot.teacher or ""),
room=escape(slot.room or ""),
```

**Альтернатива — экранировать в `format_day`** (`common/schedule.py`).
Хуже: там 7 мест вставки, легко забыть одно. И данные в базе останутся
с сырыми `<`, что сломает любой другой потребитель (экспорт, поиск,
будущий веб).

## Проверено

**Данные сейчас чистые.** Запрос по всем шести полям:

```sql
select count(*) from college_lesson where subject like '%<%' or subject like '%&%'
```

Ответ: `0` для каждого поля. Значит находка латентная — но она
сработает на первом же вводе.

**Длина полей не проверяется, но это отдельная проблема.**
`subject` объявлен `String(256)`, `teacher` — `String(128)`, `room` —
`String(64)`. SQLite игнорирует длину `VARCHAR` (это ограничение для
других СУБД), поэтому в `subject` можно записать 5000 символов. Тогда
экран дня пробьёт лимит 4096 и Telegram вернёт `message is too long` —
тот же зависший экран, но по другой причине. Проверка длины нужна
вместе с этой правкой:

```python
if len(subject) > 256:
    await message.answer("Слишком длинное название (макс. 256 символов).")
    return
```

Аналогично `teacher` → 128, `room` → 64.

## Связанные находки

- **25** — нет глобального обработчика ошибок: любой `BadRequest` даёт
  вечный спиннер;
- **9** — `_rebuild` глотает ошибку;
- **1** — пустой разбор стирает расписание.

Все четыре складываются в один сценарий: текст ломает отправку, ошибка
не перехватывается, экран зависает.

## Риски

- **Экранирование в парсерах меняет данные в базе.** Если где-то есть
  поиск по `subject` (`subject_answer`, `get_all_for_group`), он будет
  искать по `&lt;` вместо `<`. Проверил: поиск идёт через
  `casefold() in`, то есть по подстроке — пользователь, набравший
  «математика», всё равно найдёт. Но если в предмете есть `<`, он
  найдётся только по «&lt;». Это редкий случай, но стоит знать.
- **Двойное экранирование.** Если экранировать и при вставке, и в
  `format_day`, получится `&amp;lt;` — текст покажет `&lt;`. Выбрать
  одно место. Рекомендую границу вставки.
- **Старые данные.** 0 вхождений сейчас, но если появятся — их надо
  будет переэкранировать миграцией. Пока не нужно.
